1. AWS Global Infrastructure

Definition

Beginner: AWS Global Infrastructure is the massive worldwide network of physical data centers, network equipment, and edge servers that power every AWS service you use. Think of it as the backbone — the physical foundation that makes cloud computing possible globally.

Official AWS: AWS operates the broadest global cloud infrastructure, spanning Regions, Availability Zones, Local Zones, Wavelength Zones, and Edge Locations designed for fault tolerance, low latency, and high availability at global scale.

Exam: AWS Global Infrastructure has 3 primary tiers — Regions (top), Availability Zones (within a Region), and Edge Locations (CloudFront CDN/Route53). Each tier serves different architectural purposes. Know which services are Regional vs. Global.

Why It Exists

  • Problem solved: A single data center creates a single point of failure, legal compliance issues, and high latency for global users.
  • Business value: Enables global application deployment with low latency, data residency compliance, and disaster recovery across geographies.
  • Architectural value: Allows architects to design for fault isolation (AZ-level), regional isolation (Region-level), and global distribution (Edge-level).

Region Deep Dive

An AWS Region is a geographic cluster of data centers. Each Region is completely independent and isolated from other Regions. This means a disaster in us-east-1 does NOT affect eu-west-1.

  • Each Region consists of 2 or more (usually 3) Availability Zones
  • Regions are connected via the AWS global backbone network (private fiber, not public internet)
  • Data does NOT replicate across Regions automatically — you must explicitly configure cross-region replication
  • Services are launched in specific Regions; pricing varies by Region
  • Some services are Regional (VPC, EC2, RDS) and some are Global (IAM, Route 53, CloudFront)
Exam Trap: When a question says "replicate for disaster recovery," you must choose cross-region replication. Multi-AZ does NOT protect against an entire Region failure.

How to Choose a Region

  • Compliance & Data Residency: GDPR requires EU data stays in EU. Choose eu-west-1, eu-central-1, etc.
  • Latency: Place compute closest to your end users
  • Service Availability: Not all services launch in all Regions simultaneously
  • Cost: us-east-1 is typically cheapest; ap-southeast regions tend to cost more

An Availability Zone (AZ) is one or more discrete data centers with redundant power, networking, and connectivity within a Region. Key characteristics:

  • AZs are physically separated by a meaningful distance (kilometers apart) to minimize correlated failures
  • Connected via low-latency, high-bandwidth, private fiber — typically sub-2ms between AZs in the same Region
  • Each AZ has independent power, cooling, and physical security
  • AZ names are randomized per account — your us-east-1a may be a different physical AZ than my us-east-1a
  • Deploy across 2+ AZs for high availability; 3+ AZs for production systems
Architecture Rule: Minimum of 2 AZs for HA. For SAP-C02 scenarios, always deploy databases in Multi-AZ mode and distribute EC2 instances across 3 AZs when using Auto Scaling.

SAP-C02 Exam Tip: Shared Responsibility

  • On EC2: YOU patch the OS. AWS does NOT install OS patches for EC2.
  • On RDS: AWS patches the DB engine. You patch nothing at OS level.
  • On Lambda: AWS manages everything below the function code.
  • Encryption at rest on S3: Customer's decision to enable SSE-S3, SSE-KMS, or SSE-C.
  • Security Groups: Customer configures them — AWS just provides the capability.

7. AWS Well-Architected Framework

The Well-Architected Framework is AWS's guide to designing and evaluating cloud architectures. It consists of 6 pillars. In SAP-C02, many questions test your ability to identify which pillar a design decision belongs to and how to make the right trade-off.

┌────────────────────────────────────────────────────────────────┐ │ AWS WELL-ARCHITECTED FRAMEWORK │ │ │ │ ┌──────────────┐ ┌──────────────┐ ┌──────────────────────┐ │ │ │ Operational │ │ Security │ │ Reliability │ │ │ │ Excellence │ │ │ │ │ │ │ │ │ │ IAM, KMS, │ │ Multi-AZ, Backups, │ │ │ │ IaC, CI/CD, │ │ WAF, Shield, │ │ Health Checks, │ │ │ │ Runbooks │ │ GuardDuty │ │ Auto Scaling │ │ │ └──────────────┘ └──────────────┘ └──────────────────────┘ │ │ ┌──────────────┐ ┌──────────────┐ ┌──────────────────────┐ │ │ │ Performance │ │ Cost │ │ Sustainability │ │ │ │ Efficiency │ │ Optimization │ │ │ │ │ │ │ │ │ │ Reduce carbon │ │ │ │ Right-size, │ │ Reserved, │ │ footprint, efficient │ │ │ │ Caching, │ │ Spot, Saving │ │ resource usage │ │ │ │ Elasticity │ │ Plans │ │ │ │ │ └──────────────┘ └──────────────┘ └──────────────────────┘ │ └────────────────────────────────────────────────────────────────┘

Pillar 1: Operational Excellence

Running and monitoring systems to deliver business value, and continually improving processes and procedures.

  • Design Principles: Perform operations as code (IaC), make frequent small reversible changes, refine operations procedures frequently, anticipate failure, learn from all operational events
  • Key Services: CloudFormation, Systems Manager, CloudWatch, CloudTrail, AWS Config, CodePipeline, CodeDeploy
  • Exam pattern: Questions about how to automate deployments, rollback, or detect operational issues → Operational Excellence

Pillar 2: Security

Protecting information, systems, and assets while delivering business value through risk assessments and mitigation strategies.

  • Design Principles: Implement a strong identity foundation, enable traceability, apply security at all layers, automate security best practices, protect data in transit and at rest, keep people away from data, prepare for security events
  • Key Services: IAM, KMS, CloudTrail, GuardDuty, Security Hub, WAF, Shield, Macie, Inspector, Config
  • Exam pattern: Questions about encryption, audit, least privilege, detecting threats → Security pillar

Pillar 3: Reliability

Ensuring a workload performs its intended function correctly and consistently throughout its lifecycle.

  • Design Principles: Automatically recover from failure, test recovery procedures, scale horizontally, stop guessing capacity, manage change through automation
  • Key Services: Route 53, ELB, Auto Scaling, CloudWatch Alarms, Multi-AZ RDS, S3 (11 9s durability), AWS Backup
  • Exam pattern: Questions about RPO, RTO, fault tolerance, high availability → Reliability pillar

Pillar 4: Performance Efficiency

Using computing resources efficiently to meet system requirements and maintaining efficiency as demand changes and technologies evolve.

  • Design Principles: Democratize advanced technologies, go global in minutes, use serverless architectures, experiment more often, consider mechanical sympathy
  • Key Services: EC2 (right instance types), ElastiCache, CloudFront, Lambda, Aurora Serverless, DynamoDB DAX, S3 Intelligent-Tiering
  • Exam pattern: Questions about caching, right-sizing, reducing latency → Performance Efficiency

Pillar 5: Cost Optimization

Running systems to deliver business value at the lowest price point.

  • Design Principles: Implement cloud financial management, adopt a consumption model, measure overall efficiency, stop spending money on undifferentiated heavy lifting, analyze and attribute expenditure
  • Key Services: Cost Explorer, Budgets, Savings Plans, Reserved Instances, Spot Instances, Compute Optimizer, Trusted Advisor
  • Exam pattern: Questions about reducing costs, right-sizing, purchasing models → Cost Optimization

Pillar 6: Sustainability

Minimizing the environmental impacts of running cloud workloads.

  • Design Principles: Understand your impact, establish sustainability goals, maximize utilization, use more efficient hardware and software, use managed services, reduce downstream impact
  • Key Services: Graviton instances, Spot Instances (better server utilization), serverless, S3 lifecycle policies
  • Exam pattern: New pillar — questions about energy efficiency, Graviton processors, serverless for reduced idle compute

AWS Organizations — Core Concepts

AWS Organizations allows you to centrally manage multiple AWS accounts. It's essential for enterprise architectures.

Key Features

  • Consolidated Billing: All accounts' usage is aggregated for volume discounts and a single invoice
  • Service Control Policies (SCPs): Guardrails applied at OU or account level — limits what IAM can grant
  • AWS SSO Integration: Single sign-on across all member accounts
  • Organizational CloudTrail: Aggregate API activity logs across all accounts
  • RAM (Resource Access Manager): Share resources like VPC subnets across accounts without peering

9. Organizational Units (OUs)

OUs are containers within the organization hierarchy used to group accounts. You can apply SCPs to OUs (policies cascade down to child OUs and accounts).

Recommended OU Structure (AWS Best Practice)

Root
├── Security OU
│   ├── Log Archive Account      (all CloudTrail, Config logs aggregated here)
│   └── Security Tooling Account (GuardDuty, Security Hub, Macie master)
├── Infrastructure OU
│   ├── Network Account          (Transit Gateway, DNS, shared VPC)
│   └── Shared Services Account  (Artifactory, Jenkins, Active Directory)
├── Workloads OU
│   ├── Production OU
│   │   └── App-1-Prod Account

│       └── App-1-Dev Account
├── Sandbox OU
│   └── Developer Sandbox Accounts (less restrictive SCPs)
└── Suspended OU
    └── Accounts being decommissioned (deny all SCP)

10. Service Control Policies (SCPs)

┌─────────────────────────────────────────────────────────┐ │ HOW SCPs WORK │ │ │ │ SCP at Root ──► Applies to ALL accounts/OUs below │ │ SCP at OU ──► Applies to that OU and children │ │ SCP at Acct ──► Applies only to that account │ │ │ │ EFFECTIVE PERMISSIONS = │ │ SCP allows AND IAM policy allows │ │ │ │ Even if IAM grants AdministratorAccess, │ │ SCP can DENY that action. │ │ │ │ Management Account: SCPs do NOT apply to it! │ └─────────────────────────────────────────────────────────┘

SCP Types

  • Deny-list strategy (default): Attach FullAWSAccess SCP, then add explicit Deny SCPs to block unwanted actions
  • Allow-list strategy: Remove FullAWSAccess, create explicit Allow SCPs for only what's needed (more restrictive)

Common SCP Examples

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyLeaveOrganization",
      "Effect": "Deny",
      "Action": "organizations:LeaveOrganization",
      "Resource": "*"
    },
    {
      "Sid": "DenyNonApprovedRegions",
      "Effect": "Deny",
      "NotAction": [
        "cloudfront:*", "iam:*", "route53:*", "support:*"
      ],
      "Resource": "*",
      "Condition": {
        "StringNotEquals": {
          "aws:RequestedRegion": ["us-east-1", "eu-west-1"]
        }
      }
    }
  ]
}
Critical SCP Behavior: SCPs do NOT grant permissions — they only restrict them. An explicit Deny in an SCP ALWAYS wins, even against root account permissions in member accounts. The management account is EXEMPT from SCPs.

11. Multi-Account Strategy

Why use multiple accounts? Accounts are the strongest isolation boundary in AWS. Multiple accounts provide:

  • Blast radius reduction: A misconfiguration in one account doesn't affect others
  • Security isolation: Separate security contexts for production vs development
  • Billing clarity: Track costs per business unit, team, or environment
  • Service limit isolation: Each account has its own service quotas
  • Compliance: Keep regulated data in a separate account with tighter controls

12. Landing Zone

A Landing Zone is a pre-configured, secure, scalable, multi-account AWS environment based on best practices. It provides the foundation from which workloads are deployed.

Landing Zone Components

  • Account Factory: Automated provisioning of new accounts using templates
  • VPC Baseline: Standard VPC structure with approved CIDR ranges
  • Centralized Logging: All logs shipped to a dedicated Log Archive account
  • Security Baseline: GuardDuty, Security Hub, Config Rules enabled everywhere
  • IAM Identity Center: Central user access management across all accounts
  • Network Connectivity: Transit Gateway or AWS Network Firewall baseline
  • SCPs: Guardrails enforced across the entire organization

13. AWS Control Tower

AWS Control Tower automates the setup of a Landing Zone. It is the easiest way to set up and govern a secure, multi-account AWS environment.

# Create organization
resource "aws_organizations_organization" "org" {
  aws_service_access_principals = [
    "cloudtrail.amazonaws.com",
    "config.amazonaws.com",
    "sso.amazonaws.com",
    "controltower.amazonaws.com"
  ]
  feature_set = "ALL"
}

# Create Security OU
resource "aws_organizations_organizational_unit" "security" {
  name      = "Security"
  parent_id = aws_organizations_organization.org.roots[0].id
}

# Create Production OU
resource "aws_organizations_organizational_unit" "prod" {
  name      = "Production"
  parent_id = aws_organizations_organization.org.roots[0].id
}

# Create SCP — Deny non-approved regions
resource "aws_organizations_policy" "deny_regions" {
  name    = "DenyNonApprovedRegions"
  type    = "SERVICE_CONTROL_POLICY"
  content = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Effect   = "Deny"
      NotAction = [
        "cloudfront:*",
        "iam:*",
        "route53:*",
        "support:*"
      ]
      Resource  = "*"
      Condition = {
        StringNotEquals = {
          "aws:RequestedRegion" = ["us-east-1", "eu-west-1"]
        }
      }
    }]
  })
}

# Attach SCP to Production OU
resource "aws_organizations_policy_attachment" "prod_regions" {
  policy_id = aws_organizations_policy.deny_regions.id
  target_id = aws_organizations_organizational_unit.prod.id
}

15. Exam Tips & Cheat Sheet

SAP-C02 Exam Tips — AWS Foundations

  • AZ vs Region failure: Multi-AZ = AZ failure protection. Multi-Region = Region failure protection.
  • SCP + IAM: Effective permission = intersection of SCP and IAM. SCP does NOT grant, only restricts.
  • Management account: SCPs do NOT apply to the management account itself.
  • Control Tower: Automated Landing Zone setup. Guardrails = Preventive (SCP) or Detective (Config Rules).
  • S3 namespace: Globally unique names but buckets ARE Regional.
  • IAM is global: IAM roles, users, policies exist globally — not per-Region.
  • Edge Locations: Used by CloudFront and Route 53 — not compute services like EC2.
  • Consolidated billing: Usage aggregated for volume pricing. Payer account = management account.
  • Well-Architected: Know which pillar covers what. Reliability ≠ Performance. Cost ≠ Sustainability.
Regions vs AZs
  • 33+ Regions globally
  • 2+ AZs per Region (usually 3)
  • AZ = 1+ data centers
  • Region = isolated geography
  • No auto cross-region replication
SCP Rules
  • Does NOT grant permissions
  • Only restricts what IAM can grant
  • Management account exempt
  • Deny ALWAYS wins
  • Cascades down OU tree
Well-Architected Pillars
  • Operational Excellence
  • Security
  • Reliability
  • Performance Efficiency
  • Cost Optimization
  • Sustainability (new!)
Control Tower
  • Automates Landing Zone
  • Preventive = SCP
  • Detective = Config Rule
  • Creates Log Archive + Audit accounts
  • Enables IAM Identity Center
Global vs Regional Services
  • Global: IAM, Route 53, CloudFront
  • Regional: EC2, RDS, S3, VPC
  • AZ-specific: EBS, EC2 instances
  • S3 name = global, bucket = regional
Shared Responsibility
  • EC2 OS patches → Customer
  • RDS engine patches → AWS
  • Lambda runtime → AWS
  • Data encryption → Customer decides
  • Physical security → AWS always
Memory Trick: "OSRPCS" = Operational, Security, Reliability, Performance, Cost, Sustainability — the 6 Well-Architected pillars. Remember: "Ops Sec Rel Perf Cost Sustain"
Common Exam Mistakes:
  • Thinking Multi-AZ protects against Region failure — it does NOT
  • Thinking SCPs grant permissions — they only restrict
  • Forgetting that management account is exempt from SCPs
  • Confusing Control Tower guardrails: Preventive=SCP, Detective=Config Rule
  • Assuming all services are Regional — IAM, Route 53, CloudFront are Global
