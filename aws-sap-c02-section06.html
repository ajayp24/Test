1. Amazon RDS

Amazon RDS (Relational Database Service) is a managed relational database service supporting MySQL, PostgreSQL, MariaDB, Oracle, SQL Server, and Db2.

RDS MULTI-AZ ARCHITECTURE ┌────────────────────┐ │ Application Tier │ └─────────┬──────────┘ │ Writes/Reads → Primary Endpoint │ ┌─────────────▼──────────────┐ │ RDS Primary Instance │ │ AZ: us-east-1a │ │ Engine: MySQL 8.0 │ └─────────────┬──────────────┘ │ Synchronous Replication │ (always in-sync) ┌─────────────▼───────────────┐ │ RDS Standby Instance │ │ AZ: us-east-1b │ │ (No reads, no writes) │ └─────────────────────────────┘ Failover: • Primary fails → DNS endpoint switches to Standby • Automatic failover: 60-120 seconds • Application reconnects using same endpoint

RDS Key Facts

  • Multi-AZ: Synchronous replication. Standby cannot serve reads. Automatic failover 60–120 seconds.
  • Read Replicas: Asynchronous replication. Up to 15 replicas. CAN serve reads. Can be promoted to standalone.
  • Cross-Region Read Replica: Asynchronous. Up to 5 cross-region replicas per RDS instance.
  • Automated backups: Point-in-time recovery up to 35 days retention
  • Manual snapshots: Retained indefinitely (even after DB deletion)
  • Encryption: At rest (KMS) — must be enabled at creation. Cannot encrypt an existing unencrypted DB directly (snapshot → copy encrypted → restore).
  • Storage Auto Scaling: Automatically increase storage when 10% free space threshold hit
Exam Trap: RDS Multi-AZ standby CANNOT serve reads. If you need read scaling, add Read Replicas. Multi-AZ is for HA/availability, not read performance.

2. Amazon Aurora

Aurora is a MySQL and PostgreSQL-compatible relational database built for the cloud, offering up to 5x the throughput of MySQL and 3x PostgreSQL on the same hardware.

AURORA STORAGE ARCHITECTURE ┌───────────────────────────────────────────────────────────┐ │ AURORA CLUSTER │ │ │ │ ┌──────────────┐ ┌─────────────┐ ┌───────────────── │ │ │ Primary │ │ Replica 1 │ │ Replica 2 │ │ │ │ (R/W) │ │ (RO, AZ-b) │ │ (RO, AZ-c) │ │ │ │ AZ-a │ │ < 10ms lag │ │ < 10ms lag │ │ │ └──────┬───────┘ └──────┬──────┘ └────────┬────────┘ │ │ │ │ │ │ │ └─────────────────┴──────────────────┘ │ │ │ │ │ ┌──────────────────────▼────────────────────────────┐ │ │ │ Aurora Shared Storage Volume │ │ │ │ 6 copies across 3 AZs (2 copies per AZ) │ │ │ │ Auto-heal corrupt data │ │ │ │ 10 GB chunks, auto-scales to 128 TB │ │ │ └───────────────────────────────────────────────────┘ │ └───────────────────────────────────────────────────────────┘ Failover: Primary fails → Replica promoted < 30 seconds (vs RDS Multi-AZ: 60-120 seconds)

Aurora Features

  • Storage: 6 copies across 3 AZs; tolerates 2 copy failures for writes, 3 for reads
  • Replicas: Up to 15 Aurora Replicas; < 10ms replication lag
  • Endpoints: Cluster endpoint (writer), Reader endpoint (load-balanced across replicas), Custom endpoints
  • Backtrack: Rewind database to a point in time without restoring from backup (MySQL only)
  • Fast Clone: Create a database clone in minutes by sharing storage pages (copy-on-write)
  • Parallel Query: Pushes query processing to storage layer for analytics

Aurora Global Database

AURORA GLOBAL DATABASE PRIMARY REGION (us-east-1) SECONDARY REGION (eu-west-1) ┌──────────────────────┐ ┌──────────────────────────┐ │ Aurora Primary │ │ Aurora Secondary │ │ Cluster (R/W) │──async───►│ Cluster (Read Only) │ │ │ < 1 sec │ │ │ All writes here │ lag │ Up to 16 read replicas │ └──────────────────────┘ └──────────────────────────┘ Use cases: • Global application with reads close to users • DR: Promote secondary to primary in < 1 minute RTO • RPO: < 1 second (typically)

Aurora Serverless v2

  • Auto-scales from 0.5 to 128 Aurora Capacity Units (ACUs) in seconds
  • Scales in fine-grained 0.5 ACU increments (unlike v1 which doubled)
  • Eliminates need to provision peak capacity
  • Can have Serverless and provisioned instances in same cluster
  • Exam: "Variable workload" + "scale to zero" + "minimize database cost" → Aurora Serverless v2

3. Amazon DynamoDB

DynamoDB is a fully managed, serverless, key-value and document NoSQL database. Single-digit millisecond performance at any scale.

DYNAMODB ARCHITECTURE ┌─────────────────────────────────────────────────────┐ │ TABLE: Orders │ │ ┌──────────────────────────────────────────────┐ │ │ │ Partition Key: OrderId (required) │ │ │ │ Sort Key: CustomerId (optional) │ │ │ │ Attributes: Status, Amount, Date, ... │ │ │ └──────────────────────────────────────────────┘ │ │ │ │ Physical Storage: │ │ Item → Hash(PartitionKey) → Storage Partition │ │ Partitions split when > 10 GB or > 3000 RCU/1000WCU│ │ │ │ Capacity Modes: │ │ • Provisioned: Set RCU/WCU, auto-scale possible │ │ • On-Demand: Pay per request, instant scale │ └─────────────────────────────────────────────────────┘

DynamoDB Read/Write Units

UnitWhat It Gives YouConsistency
1 RCU (Read Capacity Unit)1 strongly consistent read OR 2 eventually consistent reads per second for items up to 4 KBStrongly or Eventually Consistent
1 WCU (Write Capacity Unit)1 write per second for items up to 1 KBN/A
1 Transactional Read2 RCUs per 4 KB itemACID transaction
1 Transactional Write2 WCUs per 1 KB itemACID transaction

DynamoDB Global Tables

Multi-region, multi-active replication. Each region can accept writes. Conflict resolution: last-writer-wins (timestamp). Sub-second replication between regions.

Global Tables vs Aurora Global: DynamoDB Global Tables = multi-active (any region can write). Aurora Global = active-passive (secondary regions are read-only). Use DynamoDB when you need multi-region WRITES.

DynamoDB Key Design Patterns

  • Hot partition: Avoid using sequential IDs or timestamps as partition keys — causes "hot partition" problem. Use high-cardinality attributes or add random suffix.
  • GSI (Global Secondary Index): Different partition/sort key than base table. Queries across different attributes. Eventually consistent reads. Cost: separate RCU/WCU.
  • LSI (Local Secondary Index): Same partition key, different sort key. Must be created at table creation. Can do strongly consistent reads. Max 5 LSIs per table.
  • DynamoDB Streams: Ordered record of item changes. Trigger Lambda for event-driven processing. 24-hour retention.
  • TTL (Time to Live): Auto-delete expired items. Good for session data, cache items, temporary data.

4. DynamoDB DAX (Accelerator)

DAX is an in-memory cache cluster for DynamoDB that provides microsecond read latency (vs millisecond DynamoDB). Fully compatible with DynamoDB API — just point SDK to DAX cluster endpoint.

  • Read cache only — writes go through to DynamoDB
  • Multi-AZ cluster (3 nodes minimum for HA)
  • TTL for cached items configurable
  • Does NOT help with write-heavy workloads or strongly consistent reads
  • Exam keyword: "microsecond latency" + DynamoDB → DAX
DAX vs ElastiCache: DAX = DynamoDB specific, API-compatible, in-cluster. ElastiCache = general purpose, works with any database/app, more flexible.

6. Amazon Redshift

Redshift is a fully managed petabyte-scale data warehouse. Columnar storage, massively parallel processing (MPP), and data compression make it ideal for analytics.

REDSHIFT ARCHITECTURE ┌────────────────────────────────────────────────────────────┐ │ REDSHIFT CLUSTER │ │ │ │ ┌────────────────┐ │ │ │ Leader Node │ ← Query planning, client connection │ │ └────────┬───────┘ │ │ │ Distributes query slices │ │ ┌────────▼───────────────────────────┐ │ │ │ Compute Nodes (1–128) │ │ │ │ ┌──────┐ ┌──────┐ ┌──────┐ │ │ │ │ │Node 1│ │Node 2│ │Node 3│ │ │ │ │ │Slice1│ │Slice2│ │Slice3│ │ │ │ │ └──────┘ └──────┘ └──────┘ │ │ │ └────────────────────────────────────┘ │ │ │ │ Redshift Spectrum: Query S3 data lake without loading │ │ RA3 nodes: Managed storage (S3), compute separate │ └────────────────────────────────────────────────────────────┘

Redshift Key Features

  • Columnar storage: Reads only the columns needed — massive performance for analytics
  • Redshift Spectrum: Query S3 data lake directly using Redshift SQL without loading data
  • Redshift Serverless: Auto-provisioned, auto-scaled, pay per query
  • Materialized Views: Pre-computed query results for complex queries
  • Data Sharing: Share live data with other Redshift clusters without copying
  • RA3 nodes: Managed storage on S3, compute separate — scale each independently
  • Enhanced VPC Routing: Force all COPY/UNLOAD traffic through VPC (not public internet)

9. Exam Tips & Cheat Sheet

SAP-C02 Databases — Critical Points

  • RDS Multi-AZ: HA, NOT performance. Standby cannot serve reads.
  • RDS Read Replicas: Performance. Can promote for DR. Asynchronous — possible lag.
  • Aurora vs RDS: Aurora = faster, cheaper storage, 15 replicas, sub-30s failover. Choose Aurora for high performance.
  • Aurora Global: RPO ~1 sec, RTO ~1 min. Multi-region read + DR.
  • DynamoDB Global Tables: Multi-active (write from any region). Use for globally distributed apps.
  • DAX: Microsecond reads. Only for eventually consistent DynamoDB reads. API-compatible.
  • ElastiCache Redis: Sorted sets = leaderboard. Pub/Sub. Persistence possible. Multi-AZ.
  • Redshift: Data warehouse (analytics). NOT for OLTP. Columnar. Use Spectrum for querying S3.
  • DynamoDB Hot Partition: Avoid low-cardinality partition keys. Add random suffix. Use write sharding.
  • Neptune: Graph = relationships. "Social network", "fraud detection", "recommendation".
  • DocumentDB: MongoDB-compatible managed service. JSON documents.
  • Timestream: Time-series data. IoT metrics. 1000x cheaper than relational for time-series.
  • MemoryDB: Redis API with durability. Use as PRIMARY database, not just cache.
DB Selection Guide
  • Traditional SQL: RDS or Aurora
  • High-scale NoSQL: DynamoDB
  • Caching: ElastiCache Redis
  • Analytics/BI: Redshift
  • Graph: Neptune
  • MongoDB: DocumentDB
  • Time-series: Timestream
  • Immutable ledger: QLDB
HA & DR Patterns
  • RDS Multi-AZ: AZ failover 60-120s
  • Aurora Multi-AZ: AZ failover <30s
  • Aurora Global: Region failover <1min
  • DynamoDB: Multi-AZ by default
  • DynamoDB Global Tables: multi-active
  • Redshift: RA3 + snapshots to S3
Performance Patterns
  • DynamoDB slow reads → DAX (μs)
  • RDS read heavy → Read Replicas
  • Any DB slow reads → ElastiCache
  • DynamoDB writes slow → On-demand mode
  • Redshift analytics → columnar, compress
DynamoDB Limits
  • Max item size: 400 KB
  • GSI: up to 20 per table
  • LSI: up to 5 per table (created at table creation)
  • Partition: up to 3000 RCU + 1000 WCU
  • Streams: 24 hour retention
