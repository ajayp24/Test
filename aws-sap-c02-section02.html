1. IAM Architecture

┌──────────────────────────────────────────────────────────────────┐ │ IAM ARCHITECTURE │ │ │ │ ┌─────────┐ ┌─────────┐ ┌─────────────┐ ┌───────────────┐ │ │ │ IAM │ │ IAM │ │ IAM Role │ │ IAM Policy │ │ │ │ User │ │ Group │ │ │ │ │ │ │ │ │ │ │ │ Assumed by: │ │ Allow/Deny │ │ │ │ Long- │ │ Users │ │ - EC2 │ │ Action on │ │ │ │ term │ │ inherit │ │ - Lambda │ │ Resource with │ │ │ │ keys │ │ group │ │ - ECS Task │ │ Condition │ │ │ │ │ │ policy │ │ - Cross-Acct│ │ │ │ │ └────┬────┘ └────┬────┘ └──────┬──────┘ └───────┬───────┘ │ │ │ │ │ │ │ │ └────────────┴──────────────┴──────────────────┘ │ │ │ │ │ Effective Permissions = │ │ Union of all attached policies │ │ MINUS any explicit Deny │ └──────────────────────────────────────────────────────────────────┘

AWS Identity and Access Management (IAM) is a global service that controls who can authenticate to AWS (authentication) and what they can do (authorization). It is free and operates at the account level.

IAM Key Concepts

  • Principal: An entity that can make API requests — IAM user, role, AWS service, federated user
  • Authentication: Proving identity via access keys, passwords, or temporary tokens
  • Authorization: Evaluating policies to determine if an action is allowed
  • IAM is eventually consistent — changes can take seconds to propagate
  • IAM has no region — it is a global service, but sts:AssumeRole is regional

Policy Evaluation Logic

API Request Made │ ▼ 1. Is there an explicit DENY? ──► YES ──► DENY (stops here) │ NO ▼ 2. Is there an SCP allowing it? ──► NO ──► DENY │ YES ▼ 3. Is there a resource-based policy allowing it? ──► YES ──► ALLOW (if same account) │ NO ▼ 4. Is there an identity-based policy allowing it? ──► NO ──► DENY │ YES ▼ 5. Is there a Permission Boundary allowing it? ──► NO ──► DENY │ YES ▼ 6. Is there a Session Policy allowing it? ──► NO ──► DENY │ YES ▼ ALLOW
Critical Rule: An explicit DENY always wins. The default is DENY — you must explicitly ALLOW. SCPs AND IAM must both allow for an action to succeed (intersection, not union).

4. Permission Boundaries

A Permission Boundary is an advanced IAM feature that sets the maximum permissions an IAM entity (user or role) can have. The effective permissions are the intersection of the identity policy and the permission boundary.

Effective Permissions = Identity-based Policy ∩ Permission Boundary Example: Identity Policy allows: s3:*, ec2:*, rds:* Permission Boundary allows: s3:GetObject, s3:PutObject Effective Permission: s3:GetObject, s3:PutObject ONLY (ec2:* and rds:* are denied even though policy allows them)
Use Case: You want to delegate account creation to a DevOps team but prevent them from escalating their own privileges. Set a Permission Boundary on any role they create that prevents granting permissions beyond what they have.

KMS CLI Examples

# Create CMK
aws kms create-key \
  --description "Prod S3 encryption key" \
  --key-usage ENCRYPT_DECRYPT \
  --origin AWS_KMS

# Enable automatic rotation
aws kms enable-key-rotation --key-id arn:aws:kms:us-east-1:123:key/xxxxx

# Generate data key
aws kms generate-data-key \
  --key-id alias/my-key \
  --key-spec AES_256

# Encrypt data (under 4KB)
aws kms encrypt \
  --key-id alias/my-key \
  --plaintext fileb://secret.txt \
  --output text --query CiphertextBlob | base64 --decode > secret.enc

12. Network Security: WAF, Shield, Firewall Manager

AWS WAF (Web Application Firewall)

  • Operates at Layer 7 (HTTP/HTTPS)
  • Protects against: SQL injection, XSS, bad bots, geographic restrictions
  • Deployed in front of: CloudFront, ALB, API Gateway, AppSync, Cognito
  • Uses Web ACLs with Rules (managed rules from AWS or marketplace)
  • Managed Rules: AWS Managed Rules for common threats — enable out of the box
  • Rate limiting: Block IP after N requests per 5-minute window

AWS Shield

FeatureShield StandardShield Advanced

Resources protectedCloudFront, Route 53, ELB, EC2EC2, ELB, CloudFront, Route 53, Global Accelerator

AWS Firewall Manager

Centrally configure and manage WAF rules, Shield Advanced protections, Security Groups, and Network Firewalls across multiple accounts in an AWS Organization.

Exam Tip: When a question asks how to apply WAF rules consistently across 50 accounts in an Organization → Firewall Manager. It applies policies centrally and auto-remediates non-compliant resources.

13. Threat Detection Services

Amazon GuardDuty

Intelligent threat detection service using ML and threat intelligence. Analyzes:

  • VPC Flow Logs — unusual network traffic patterns
  • CloudTrail Events — suspicious API calls (crypto mining, data exfiltration)
  • DNS Logs — C2 communication, domain generation algorithms
  • S3 Data Events — unusual S3 access patterns
  • EKS Audit Logs — Kubernetes API anomalies
  • Lambda Network Activity — unusual function behavior
Key: GuardDuty requires NO agents, NO infrastructure changes. Enable with one click. Findings appear in GuardDuty console and can trigger EventBridge → SNS/Lambda for automated response.

Amazon Inspector

Automated vulnerability management for EC2, ECR container images, and Lambda functions.

  • Scans for OS/software CVEs, network reachability issues, unintended exposure
  • Integrated with ECR — scans container images on push
  • Integrates with Security Hub for consolidated findings

Amazon Macie

Uses ML to discover, classify, and protect sensitive data in S3. Detects PII (personal identifiable information), financial data, credentials in S3 objects.

Exam Tip: Macie = S3 data classification/PII discovery. GuardDuty = threat detection across services. Inspector = vulnerability scanning. Know the difference!

Amazon Detective

Security investigation service. Analyzes, investigates, and identifies root cause of security findings using graph analysis of VPC Flow Logs, CloudTrail, GuardDuty findings. Answer: "WHY did this happen?" after GuardDuty finds it.

14. AWS Security Hub

Centralized security findings aggregator across AWS accounts. Aggregates findings from:

  • GuardDuty, Inspector, Macie, IAM Access Analyzer, Firewall Manager
  • Third-party tools via ASFF (Amazon Security Finding Format)

Security Hub also runs Security Standards checks (CIS Benchmarks, PCI DSS, AWS Foundational Security Best Practices). Each check scores your environment against best practice.

  })

16. Exam Tips & Cheat Sheet

SAP-C02 IAM & Security — Critical Points

  • AssumeRole: Always use for cross-account access and AWS service access. Never long-term access keys for EC2/Lambda.
  • Permission Boundary: Limits maximum permissions. Does NOT grant. Union of identity + boundary.
  • SCP vs IAM: Both must allow. SCP is organizational ceiling.
  • Secrets Manager vs Parameter Store: Auto-rotation = Secrets Manager. Cost-sensitive config = Parameter Store.
  • CMK vs AWS Managed Key: CMK = you control key policy, can share cross-account, can audit usage. AWS Managed = simpler, no cross-account, free.
  • CloudHSM vs KMS: FIPS 140-2 Level 3 = CloudHSM. Regulatory requirement for dedicated HSM = CloudHSM.
  • GuardDuty: No agents needed. Detects threats. Does NOT block traffic (use WAF/NACL to block).
  • Macie: PII/sensitive data discovery in S3 only.
  • Inspector: CVE/vulnerability scanning. EC2, ECR, Lambda.
  • Security Hub: Aggregator/dashboard for all security findings. Runs compliance checks.
  • WAF: Layer 7 protection. Always in front of CloudFront or ALB — not EC2 directly.
  • Shield Advanced: DDoS response team + cost protection. $3000/month commitment.
  • Firewall Manager: Centrally apply WAF/Shield across all org accounts.
IAM Policy Evaluation

Explicit DENY wins → SCP allows? → Resource policy? → Identity policy? → Permission Boundary? → Session Policy?

Encryption Key Hierarchy
  • AWS Managed = free, no cross-acct
  • CMK = $1/mo, cross-acct possible
  • CloudHSM = dedicated, FIPS L3
Secrets Management
  • Auto-rotate → Secrets Manager
  • Config params → Parameter Store
  • Multi-region replica → Secrets Manager
Threat Detection
  • GuardDuty = threat detection
  • Inspector = vulnerability scan
  • Macie = PII in S3
  • Detective = root cause investigation
Common Exam Mistakes:
  • Confusing GuardDuty (detection) with WAF (prevention)
  • Thinking Inspector scans all services — it covers EC2, ECR, Lambda only
  • Forgetting Macie only works on S3
  • Using AWS Managed Keys for cross-account access — must use CMK
  • Thinking Permission Boundary grants permissions — it only limits them
  • Forgetting GetSessionToken requires MFA to be enforced properly
