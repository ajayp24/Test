🔐

IAM Deep Dive

Users, Groups, Roles, Policies — the foundation of AWS security
📚 Core Components
  • Users: Individual identities with long-term credentials (password, access keys). Map to a physical person or application.
  • Groups: Collection of users. Policies applied to a group apply to all members. Users can belong to multiple groups. Groups cannot contain other groups.
  • Roles: Temporary credentials for AWS services, cross-account access, or federated users. No permanent credentials — credentials are rotated automatically. EC2 instances, Lambda functions, and ECS tasks use roles.
  • Policies: JSON documents defining permissions. Components: Effect (Allow/Deny), Action (API calls), Resource (ARN), Condition (optional constraints).
📚 Policy Types
TypeAttached ToUse Case
Identity-basedUsers, Groups, RolesWhat this identity CAN do. Most common type.
Resource-basedResources (S3, SQS, Lambda, KMS)Who CAN access this resource. Includes Principal field. Enables cross-account access without assuming a role.
Permission BoundaryUsers or RolesSets the MAXIMUM permissions. Used for delegation — allow admins to create roles but cap their power.
Service Control Policy (SCP)Organization OUs/AccountsMaximum permissions for an entire AWS account. Does NOT apply to management account.
Session PolicySTS sessionsFurther restrict permissions for the current session when assuming a role.
📚 Policy Evaluation Logic
Evaluation Order (Must Know)

1. Explicit Deny → Always wins. If ANY policy says Deny, access is denied. Period.
2. SCP → Must allow (if in an organization).
3. Resource-based policy → If allows AND no explicit deny, access is granted (cross-account shortcut).
4. Permission Boundary → Must allow.
5. Identity-based policy → Must allow.
6. Session policy → Must allow (if applicable).
7. Implicit Deny → Default. If nothing allows, access is denied.

⚠ SAA-C03 Exam Traps
Trap: Cross-Account Access — Role vs Resource Policy

Option 1 — Assume Role: Target account creates a role with trust policy allowing the source account. Source uses sts:AssumeRole. The caller gives up their original permissions and takes on the role's permissions.
Option 2 — Resource-based policy: Target resource (S3, SQS, Lambda, SNS, KMS) has a resource policy allowing the source account's principal. The caller keeps their original permissions AND gains access to the resource. This is important when a Lambda in Account A needs to access DynamoDB in Account A AND S3 in Account B.

Trap: EC2 Instance Profile

An IAM Role alone cannot be attached to EC2. You need an Instance Profile (a container for the role). The console creates this automatically, but CloudFormation and CLI require explicit creation. If EC2 can't access AWS services, check: (1) Is a role attached via instance profile? (2) Does the role have the right permissions?

IAM Advanced

STS, Federation, Permission Boundaries, ABAC, and Cognito
📚 Key Concepts
  • STS (Security Token Service): Provides temporary credentials. Key APIs: AssumeRole (cross-account), AssumeRoleWithSAML (enterprise SSO), AssumeRoleWithWebIdentity (social login — prefer Cognito), GetSessionToken (MFA).
  • IAM Identity Center (SSO): Centralized workforce sign-on for multiple AWS accounts and business apps. Built on AWS Organizations. Supports SAML 2.0, Active Directory, built-in directory.
  • Amazon Cognito: User Pools (authentication for app users, returns JWT) + Identity Pools (authorization, exchanges tokens for temporary AWS credentials). Use for web/mobile apps.
  • Permission Boundaries: Maximum permission cap for IAM users/roles. Effective permissions = intersection of identity policy AND permission boundary. Used for delegated administration.
  • ABAC (Attribute-Based Access Control): Use tags for access control. Tag resources and principals, then write policies using aws:PrincipalTag and aws:ResourceTag conditions. Scales better than RBAC for large organizations.
🏢

AWS Organizations & SCPs

Centrally manage multiple AWS accounts
  • Organizations: Consolidate billing, create account hierarchy (OUs), apply policy guardrails (SCPs).
  • SCPs (Service Control Policies): Maximum permission guardrails for member accounts. SCPs do NOT affect the management account. SCPs do NOT grant permissions — they only restrict. Must have an Allow for anything to work (default is FullAWSAccess).
  • Consolidated billing: One bill for all accounts. Share Reserved Instances and Savings Plans across the organization automatically.
  • Delegated administrator: Designate a member account to manage a service org-wide (GuardDuty, Security Hub, CloudFormation StackSets) without using the management account.
Exam Trap: SCP Does Not Affect Management Account

Even if you apply a deny-all SCP to the organization root, the management account is exempt. This is a very common exam question. Best practice: never run workloads in the management account.

KMS & Encryption

Key management for encryption at rest and in transit
📚 Core Concepts
  • KMS Key Types: AWS Managed (free, auto-rotated yearly), Customer Managed ($1/mo, full control, configurable rotation), AWS Owned (internal, not visible).
  • Symmetric vs Asymmetric: Symmetric (AES-256, single key, most common, never leaves KMS) vs Asymmetric (RSA/ECC, public+private key pair, public key can be downloaded).
  • Envelope Encryption: KMS encrypts a Data Key. The Data Key encrypts your data. Required for data > 4 KB. Use GenerateDataKey API.
  • Key Policies: Resource-based policies on KMS keys. Default policy gives root user full access. Without a key policy, NO ONE can access the key (not even IAM policies).
  • Cross-account KMS: Key policy must allow the external account. The external account's IAM policy must also allow KMS access. Both are required.
  • S3 Bucket Keys: Reduce KMS API calls by up to 99% for S3 SSE-KMS. Generates a bucket-level key that re-encrypts data keys locally.
📚 Encryption Across Services

VPC Fundamentals

Subnets, Route Tables, Internet Gateway, NAT Gateway
📚 Key Architecture Components
  • VPC: Your private network in AWS. Defined by a CIDR block (e.g., 10.0.0.0/16). Regional resource. Max 5 VPCs per region (soft limit).
  • Subnets: AZ-level. Public subnet = route to IGW. Private subnet = no direct route to internet. One subnet = one AZ.
  • Internet Gateway (IGW): Enables internet access for public subnets. One IGW per VPC. Horizontally scaled, redundant, highly available.
  • NAT Gateway: Allows private subnet resources to access the internet (outbound only). Managed by AWS. AZ-specific — deploy one per AZ for HA. Up to 45 Gbps bandwidth. Uses Elastic IP.
  • NAT Instance: EC2 instance acting as NAT. Self-managed. Cheaper but less reliable. Must disable source/destination check. Legacy — use NAT Gateway instead.
  • Route Tables: Control traffic routing. Each subnet is associated with one route table. Public subnet route table has 0.0.0.0/0 → IGW. Private subnet has 0.0.0.0/0 → NAT Gateway.
  • Elastic IP: Static public IPv4 address. You own it until you release it. Max 5 per region.
  • CIDR Blocks: Min /28 (16 IPs), max /16 (65,536 IPs). AWS reserves 5 IPs per subnet (first 4 + last 1).

When to Use NACLs

NACLs are used when you need to explicitly DENY traffic (e.g., block a specific IP range). Security Groups can only Allow. The exam loves this distinction: "Block traffic from a specific IP" → NACL deny rule.

Exam Trap: S3 Has Both Types

S3 supports both Gateway Endpoints (free, route table based) and Interface Endpoints (paid, ENI based). Gateway Endpoint is preferred (free) unless you need: on-premises access via VPN/DX, cross-region access, or private DNS resolution from outside the VPC.

📚 AWS PrivateLink (Endpoint Services)

Expose your service to other VPCs/accounts privately. Your service sits behind a Network Load Balancer. Consumers create an Interface Endpoint in their VPC to connect. No VPC peering, no public internet, no route table changes. Scales to thousands of consumer VPCs.

Exam Decision

"Privately access AWS services from VPC" → VPC Endpoints.
"Expose your service to hundreds of customer VPCs" → PrivateLink (your NLB + their Interface Endpoint).
"Connect two VPCs for full network connectivity" → VPC Peering or Transit Gateway.

⚠ Exam Traps
Alias Record vs CNAME

CNAME: Maps hostname to hostname (www.example.com → elb1234.us-east-1.elb.amazonaws.com). Cannot be used for the zone apex (naked domain).
Alias: AWS-specific. Maps hostname to an AWS resource. Can be used for zone apex (example.com → ALB). Free of charge for queries. Targets: ELB, CloudFront, S3 website, API Gateway, VPC Interface Endpoint, Global Accelerator, Route 53 record in the same hosted zone. Cannot target EC2 DNS name.

Geolocation vs Latency-based

Geolocation: Routes by user's physical location (country/continent). Used for content localization or geo-restrictions. A user in France ALWAYS gets the European endpoint.
Latency-based: Routes by network latency. A user in France might get the US endpoint if latency is lower. Used for best performance.

📚 Other EC2 Concepts
  • AMI (Amazon Machine Image): Pre-configured template for EC2. Includes OS, software, configuration. Region-specific but can be copied across regions. Create custom AMIs for faster boot (pre-baked configuration).
  • User Data: Bootstrap script that runs once at instance launch. Install updates, software, download files. Runs as root.

  • Instance Store: Physically attached disk. Highest I/O performance. Ephemeral — data lost when instance stops/terminates. Use for cache, buffer, temp data.

Auto Scaling Groups & Launch Templates

Automatically scale EC2 capacity to match demand
📚 Key Concepts
  • Launch Template: Defines instance configuration (AMI, instance type, key pair, security groups, user data, IAM role). Supports versioning and inheritance. Preferred over Launch Configuration (legacy).
  • ASG Settings: Minimum size, maximum size, desired capacity. ASG maintains desired count by launching/terminating instances.
  • Scaling Policies:
    • Target Tracking: Set a target metric value (e.g., average CPU = 50%). ASG adjusts to maintain target. Simplest and most common.
    • Step Scaling: Define scaling steps based on CloudWatch alarm thresholds. More granular control.
    • Simple Scaling: Add/remove fixed number of instances when alarm fires. Waits for cooldown period. Legacy.
    • Scheduled Scaling: Scale based on known time patterns (e.g., scale up at 9am weekdays).
    • Predictive Scaling: ML-based. Forecasts traffic and pre-scales ahead of time.
  • Health Checks: EC2 (default), ELB, or custom. Unhealthy instances are terminated and replaced.
  • Cooldown Period: Default 300 seconds. Prevents ASG from launching/terminating additional instances while a scaling action is taking effect.
  • Lifecycle Hooks: Perform custom actions when instances launch (Pending:Wait) or terminate (Terminating:Wait). Use for: install software, drain connections, save logs.
  • Instance Refresh: Rolling update of all instances in the ASG. Specify minimum healthy percentage. Used when updating AMI or launch template.

AWS Lambda

Serverless compute for event-driven architectures
📚 Key Facts for SAA-C03
  • Timeout: Max 15 minutes (900 seconds). If longer processing needed, use Step Functions, ECS, or Batch.
  • Memory: 128 MB – 10 GB. CPU scales proportionally with memory.
  • Concurrency: 1,000 per region (default). Reserved concurrency to guarantee capacity. Provisioned concurrency to eliminate cold starts.
  • VPC: By default, Lambda has internet access but no VPC access. When placed in VPC for RDS/ElastiCache access, Lambda loses internet — need NAT Gateway or VPC Endpoints.
  • Triggers: API Gateway, S3, SQS, DynamoDB Streams, Kinesis, SNS, EventBridge, CloudWatch Events, ALB, Cognito, and many more.
  • Layers: Package shared dependencies. Up to 5 layers. Total uncompressed size (code + layers) ≤ 250 MB.
  • Container images: Up to 10 GB. Must implement Lambda Runtime API.
  • Lambda@Edge / CloudFront Functions: Run code at CloudFront edge locations for request/response manipulation.

Trap: ALB + Static IP

Amazon S3 Deep Dive

Object storage with unlimited scalability
📚 Core Facts
  • Object size: 0 bytes to 5 TB. Single PUT max 5 GB. Use multipart upload for >100 MB (required for >5 GB).
  • Durability: 99.999999999% (11 nines) across all storage classes.
  • Availability: 99.99% for Standard, varies by class.
  • Consistency: Strong read-after-write consistency for all operations.
  • Versioning: Protect against accidental deletes. Deleting a versioned object creates a delete marker. Suspending versioning doesn't delete existing versions.
  • S3 Object Lock: WORM (Write Once Read Many). Governance mode: Special permissions can override. Compliance mode: No one (including root) can override until retention expires. Legal Hold: no expiration until removed.
  • Transfer Acceleration: Uses CloudFront edge locations for faster uploads. Special endpoint: bucket.s3-accelerate.amazonaws.com.
  • S3 Select / Glacier Select: Query data in-place with SQL. Reduces data transfer.
  • S3 Byte-Range Fetches: Download specific byte ranges in parallel. Speed up downloads or retrieve partial data.
  • Event Notifications: Trigger on object events (create, delete). Targets: SNS, SQS, Lambda, EventBridge.

Amazon RDS & Aurora

Managed relational databases with HA and scaling
📚 RDS Key Concepts
  • Engines: MySQL, PostgreSQL, MariaDB, Oracle, SQL Server, Amazon Aurora.
  • Multi-AZ: Synchronous standby replica in another AZ. Automatic failover (DNS stays same). For high availability, NOT read scaling. Zero downtime when enabling Multi-AZ (snapshot → restore to standby → sync).
  • Read Replicas: Asynchronous replication. Up to 15 (Aurora) or 5 (others). For read scaling. Can be cross-region. Can be promoted to standalone DB (breaks replication). In same region: free data transfer. Cross-region: paid.
  • RDS Proxy: Connection pooling. Reduces database connection overhead. Critical for Lambda → RDS. Enforces IAM auth. Reduces failover time by 66%. Must be in VPC.
  • Automated Backups: Point-in-time recovery (PITR). Retention: 1-35 days. Transaction logs backed up every 5 min. Restore creates a new DB instance.
  • Manual Snapshots: User-triggered. Persist until manually deleted (even if DB is deleted).
  • Encryption: At-rest with KMS (must be enabled at creation). Cannot encrypt an unencrypted DB directly — snapshot, copy with encryption, restore.
📚 Amazon Aurora
  • Cloud-native. 5x MySQL / 3x PostgreSQL performance.
  • Storage: Auto-scales 10 GB to 128 TB. 6 copies across 3 AZs. Self-healing. Striped across 100s of volumes.
  • Writer + Readers: 1 writer endpoint, up to 15 read replicas with reader endpoint (load balanced). Failover promotion in <30 seconds.
  • Aurora Serverless v2: Auto-scales compute instantly based on demand. Scales to zero (v2). Pay per ACU-second.
  • Aurora Global Database: Cross-region read replicas. 1 primary region (read/write), up to 5 secondary regions (read-only). Replication lag <1 second. Promote secondary to primary for DR (RPO <1 second, RTO <1 minute).
  • Aurora Machine Learning: Integrate with SageMaker and Comprehend directly from SQL queries.
Multi-AZ vs Read Replicas

Multi-AZ: HA (automatic failover). Sync replication. Standby is NOT readable. Used for availability.
Read Replica: Read scaling. Async replication. IS readable. Can be cross-region. Used for performance.

Amazon DynamoDB

Serverless NoSQL with single-digit millisecond performance
  • Key-value + document. Max item size 400 KB. Serverless, auto-scaling.
  • Capacity modes: Provisioned (RCU/WCU, predictable) or On-Demand (pay per request, unpredictable).
  • DAX: In-memory cache, microsecond reads. Write-through. Runs in VPC.
  • Global Tables: Multi-region, active-active. Requires Streams enabled. Last writer wins.
  • DynamoDB Streams: Ordered stream of item changes. 24-hour retention. Trigger Lambda for event-driven architectures.
  • TTL: Auto-delete expired items at no WCU cost.
  • Transactions: ACID across up to 100 items. 2x the cost.
  • GSI (Global Secondary Index): Different partition key. Created anytime. Has own RCU/WCU. Eventually consistent only.
  • LSI (Local Secondary Index): Same partition key, different sort key. Must be created at table creation. Supports strongly consistent reads.
  • Export to S3: Export table data to S3 without affecting performance. Uses PITR. For analytics with Athena.

Application Integration & Decoupling

Decoupling is a fundamental architecture principle. SQS for queuing, SNS for pub/sub fan-out, EventBridge for event routing, Step Functions for orchestration, and Kinesis for real-time streaming.

📩

Amazon SQS

Fully managed message queuing
  • Standard: Unlimited throughput. At-least-once delivery. Best-effort ordering.
  • FIFO: Exactly-once processing. Strict ordering per message group. 300 msg/s (3,000 with batching). Queue name must end in .fifo.
  • Message size: Max 256 KB. Use SQS Extended Client Library for up to 2 GB (stores in S3).
  • Visibility Timeout: Default 30s, max 12 hours. Set to ≥6x Lambda timeout when using Lambda consumer.
  • Long Polling: Reduce empty responses. Set WaitTimeSeconds 1-20s. Always enable.
  • DLQ: Messages exceeding maxReceiveCount sent to DLQ. Same type as source queue. DLQ Redrive: move messages back to source queue.
  • Delay Queue: Delay delivery up to 15 minutes.
  • Temporary Queue: Request-response pattern using virtual queues on a single real queue.
SQS + ASG Pattern

Use CloudWatch metric ApproximateNumberOfMessagesVisible to trigger ASG scaling. More messages → more consumers. This is a very common SAA-C03 exam pattern for decoupled, auto-scaling architectures.

📣

Amazon SNS & Fan-Out

Pub/sub messaging for push-based event distribution
  • Pub/Sub: publisher → topic → all subscribers get the message simultaneously.
  • Subscribers: SQS, Lambda, HTTP/HTTPS, Email, SMS, Kinesis Data Firehose.
  • Filter Policies: JSON attribute-based filtering. Subscribers only get matching messages.
  • FIFO Topics: Ordered, deduplicated. Can only deliver to SQS FIFO queues.
  • SNS + SQS Fan-Out: Publish once to SNS, deliver to multiple SQS queues. Each queue processes independently. Most common architecture pattern for the exam.
  • S3 Event → SNS → multiple SQS: S3 can only send event notification to one SNS topic per event type. Use SNS + SQS fan-out to process the event in multiple ways.
🔨

Amazon EventBridge

Serverless event bus for event-driven architectures
  • Event bus receiving events from AWS services, SaaS partners, and custom apps.
  • Rules: Match events using JSON patterns. Route to 5+ targets per rule.
  • Targets: Lambda, SQS, SNS, Step Functions, Kinesis, ECS, CodePipeline, SSM, API Gateway, and more.
  • Schedule: Cron or rate-based scheduled events (replacement for CloudWatch Events).
  • Archive & Replay: Store events for replay. Debugging, testing, disaster recovery.
  • Schema Registry: Discover and store event schemas. Generate code bindings.
  • Cross-account/cross-region: Send events between buses in different accounts and regions.
EventBridge vs SNS

EventBridge is better for: complex routing rules, SaaS integration, event archive/replay, schema discovery. SNS is better for: high throughput fan-out, simple pub/sub, mobile push, email/SMS notifications.

Cost Optimization Strategies

Reduce spend while maintaining performance and reliability
📚 Key Strategies
  • Right-sizing: Use AWS Compute Optimizer and Cost Explorer right-sizing recommendations to identify over-provisioned instances. Downsize or switch to Graviton (ARM) for ~20% savings.
  • Reserved capacity: RIs and Savings Plans for steady-state workloads (up to 72% savings). Convertible RIs for flexibility.
  • Spot Instances: Up to 90% savings for fault-tolerant batch jobs, CI/CD, data analysis.
  • S3 Lifecycle Policies: Transition infrequent data to cheaper storage classes. Delete obsolete data. Use Intelligent-Tiering for unknown patterns.
  • Auto Scaling: Scale in during low demand. Use predictive scaling.
  • Serverless: Lambda, Fargate, DynamoDB On-Demand, Aurora Serverless — pay only for what you use.
  • Data transfer optimization: Keep traffic within the same AZ (free). Use VPC Endpoints to avoid NAT Gateway data processing charges. Use CloudFront to reduce origin fetches.
  • NAT Gateway costs: Data processing charges can add up. Use VPC Gateway Endpoints (free) for S3/DynamoDB instead of routing through NAT Gateway.

Real SAA-C03 Scenario Walkthroughs

Practice with exam-style questions
Scenario 1: A company has a web application running on EC2 behind an ALB. They want to ensure the application survives an AZ failure with minimal downtime. What architecture should they implement?
Multi-AZ deployment: ALB + ASG across at least 2 AZs + RDS Multi-AZ
Deploy the ALB across multiple AZs. Configure the ASG to span at least 2 AZs with a minimum of 2 instances. Use RDS Multi-AZ for automatic database failover. Store session data in ElastiCache (Multi-AZ Redis) or DynamoDB instead of on the instances. If one AZ goes down, the ALB routes to healthy instances in the other AZ, and RDS fails over to the standby.
Scenario 2: A company needs to migrate a 50 TB Oracle database to Aurora PostgreSQL. The source database must remain online during migration. How should they approach this?
AWS DMS + AWS SCT (Schema Conversion Tool)
This is a heterogeneous migration (Oracle → PostgreSQL). Step 1: Use SCT to convert the Oracle schema to PostgreSQL-compatible schema. Step 2: Use DMS with continuous replication (CDC) to migrate data while keeping the source online. Step 3: When ready, cut over to Aurora PostgreSQL. DMS handles full load + ongoing changes.
Scenario 3: A company stores 10 TB of log data in S3 Standard. Only the last 30 days are actively queried. Data must be retained for 7 years for compliance. How should they optimize costs?
S3 Lifecycle Policy: Standard → Standard-IA after 30 days → Glacier Flexible Retrieval after 90 days → Glacier Deep Archive after 365 days
Active data (first 30 days) stays in Standard. Infrequently accessed data transitions to Standard-IA (cheaper, per-GB retrieval fee). After 90 days, move to Glacier Flexible Retrieval for archive. After 1 year, move to Glacier Deep Archive (cheapest, 12-48 hour retrieval) for long-term compliance retention. This multi-tier approach minimizes cost while meeting the 7-year retention requirement.
Scenario 4: A Lambda function accesses an RDS database in a VPC. Under load, the database runs out of connections. How should this be resolved?
Use Amazon RDS Proxy for connection pooling
Lambda creates new connections on each invocation, potentially exhausting the database's max_connections. RDS Proxy maintains a pool of database connections and reuses them across Lambda invocations. The Lambda function connects to RDS Proxy instead of directly to RDS. RDS Proxy also reduces failover time by 66% and supports IAM authentication. Both Lambda and RDS Proxy must be in the same VPC.
Scenario 5: A company wants to process orders from multiple sources. Each order must be processed exactly once and in the correct order per customer. Failed orders should be captured for analysis. What architecture?
SQS FIFO queue (MessageGroupId = customerId) + Lambda consumer + DLQ for failures
SQS FIFO provides exactly-once processing and strict ordering within a message group. Setting MessageGroupId to the customer ID ensures each customer's orders are processed in sequence. Lambda event source mapping polls the queue. Set visibility timeout ≥ 6x Lambda timeout. Configure a FIFO DLQ with maxReceiveCount to capture orders that fail processing after multiple retries.

Top 25 SAA-C03 Exam Traps

The most commonly tested gotchas
  1. Multi-AZ = HA (availability), Read Replicas = scaling (performance). Don't confuse them.
  2. Security Groups are stateful, NACLs are stateless. NACLs for deny rules, SGs for allow.
  3. S3 Gateway Endpoint is free. Interface Endpoints cost money. Always prefer Gateway for S3/DynamoDB.
  4. NAT Gateway = managed, per-AZ. Deploy one per AZ for HA. NAT Instance = self-managed, legacy.
  5. Direct Connect is NOT encrypted. VPN is encrypted. For encrypted DX, add VPN on top.
  6. VPC Peering is non-transitive. Transit Gateway is transitive.
  7. ALB has no static IP. Use NLB or Global Accelerator for static IPs.
  8. Cross-zone LB: ALB free/always-on, NLB disabled by default.
  9. Alias records work at zone apex, CNAME does not. Alias targets cannot be EC2.
  10. Geolocation ≠ Latency-based routing. Geo = location, Latency = network performance.
  11. EBS is single-AZ. Must snapshot → copy to another AZ/region.
  12. EFS is Linux only. FSx for Windows for SMB.
  13. Cannot encrypt an unencrypted EBS/RDS directly. Snapshot → copy with encryption → restore.
  14. S3 replication requires versioning on both buckets. Only new objects replicated.
  15. S3 Glacier retrieval times matter: Instant (ms), Flexible (min-hrs), Deep Archive (12-48 hrs).
  16. RDS Proxy for Lambda → RDS connection pooling. Prevents connection exhaustion.
  17. Aurora Global Database for cross-region DR. RPO <1s, RTO <1min.
  18. SCP does NOT affect the management account.
  19. KMS Encrypt API limited to 4 KB. Use GenerateDataKey for envelope encryption.
  20. Spot Instances can be reclaimed. Never for databases or critical persistent workloads.
  21. Placement groups: Cluster = low latency (same rack), Spread = HA (diff hardware, max 7/AZ).
  22. Lambda in VPC loses internet. Need NAT GW or VPC Endpoints.
  23. API Gateway timeout is 29 seconds. Lambda can run 15 min but API GW cuts at 29s.
  24. SQS visibility timeout ≥ 6x Lambda timeout.
  25. S3 SSE-KMS subject to KMS quota. Use S3 Bucket Keys for high-throughput.
