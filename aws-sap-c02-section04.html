Launch Templates (preferred over Launch Configurations)

5. AWS Lambda

LAMBDA EXECUTION FLOW Trigger Lambda Service Your Code (API GW, S3, ──► Execution Environment Init ──► handler(event, context) EventBridge, (Cold Start) │ SQS, etc.) ──► Reuse warm environment ──► Process event (Warm Start) │ Return response │ Lambda runtime → Trigger response Cold Start: Container init + runtime init + code init (100ms – several seconds) Warm Start: Reuse existing container (milliseconds)

Lambda Key Facts for SAP-C02

  • Max timeout: 15 minutes (900 seconds)
  • Max memory: 10,240 MB (10 GB)
  • vCPU allocation: Linear with memory (1 vCPU at 1,769 MB)
  • Deployment package: 50 MB (zipped), 250 MB unzipped, 10 GB container image
  • Concurrency: Default 1,000 concurrent executions per region (soft limit)
  • Reserved concurrency: Guarantee a function gets N concurrent executions
  • Provisioned concurrency: Pre-warm execution environments to eliminate cold starts
  • VPC access: Lambda can be deployed in a VPC — needs ENI in private subnet
  • Layers: Share code/libraries across functions (max 5 layers, 250 MB total)
  • Ephemeral storage (/tmp): 512 MB to 10,240 MB

Lambda Scaling Model

LAMBDA CONCURRENCY SCALING Request 1 ──► Execution Env 1 (warm) ──► Response Request 2 ──► Execution Env 2 (warm) ──► Response Request 3 ──► Execution Env 3 (new) ──► Response ← Cold Start ... Request N ──► Throttled (429) if > concurrency limit Burst limit: 3,000 concurrent initially, then +500/minute until account limit Account limit: 1,000 concurrent (default, region-wide) Reserved concurrency: Set aside N for this function Provisioned concurrency: N pre-warmed envs always ready

Lambda with SQS — Event Source Mapping

# Create SQS trigger for Lambda
aws lambda create-event-source-mapping \
  --function-name my-function \
  --event-source-arn arn:aws:sqs:us-east-1:123:my-queue \
  --batch-size 10 \
  --maximum-batching-window-in-seconds 5 \
  --function-response-types ReportBatchItemFailures \
  --scaling-config MaximumConcurrency=100

# Lambda Function Code (Python)
import json

def handler(event, context):
    failed_message_ids = []

    for record in event['Records']:
        try:
            body = json.loads(record['body'])
            process_message(body)
        except Exception as e:
            failed_message_ids.append({'itemIdentifier': record['messageId']})

    # Return only failed items for retry (partial batch response)
    return {'batchItemFailures': [{'itemIdentifier': id} for id in failed_message_ids]}

6. ECS & EKS — Container Compute

CONTAINER COMPUTE DECISION TREE Do you need Kubernetes? ├── YES → EKS (Elastic Kubernetes Service) │ ├── Self-managed nodes (EC2) │ ├── Managed node groups (EC2, AWS manages) │ └── Fargate (serverless, no nodes to manage) │ └── NO → Do you need full control over infrastructure? ├── YES → ECS with EC2 launch type └── NO → ECS with Fargate (serverless) Serverless containers? → Fargate (works with both ECS and EKS) Batch/ML training workloads? → AWS Batch (manages compute fleet for batch jobs)

ECS Architecture

  • Cluster: Logical grouping of compute (EC2 instances or Fargate)
  • Task Definition: Blueprint for containers — image, CPU, memory, ports, environment
  • Service: Runs and maintains N tasks; integrates with ALB/NLB for load balancing
  • Task: Running instance of a task definition — one or more containers
  • Container Agent: Runs on EC2 launch type nodes to report to ECS control plane

ECS Task IAM Role vs EC2 Instance Profile

Critical Security: Always use ECS Task IAM Role (task-level credential), NOT the EC2 Instance Profile (which grants the same permissions to ALL tasks on that instance). This follows least-privilege — each task gets its own role with specific permissions.

7. AWS Batch & Elastic Beanstalk

AWS Batch

Fully managed batch computing service. Automatically provisions optimal compute (EC2, Spot) for batch jobs defined as containers.

  • Job Definition: What to run (Docker image, vCPU, memory)
  • Job Queue: Where jobs wait; mapped to a compute environment
  • Compute Environment: EC2/Spot fleet that runs jobs
  • Integrates with Step Functions, EventBridge for scheduling
  • Supports array jobs (run same job multiple times with different indices)

Elastic Beanstalk

Platform-as-a-Service (PaaS) that deploys and manages applications with automatic provisioning of EC2, ALB, Auto Scaling, CloudWatch.

  • Supports: Java, .NET, Node.js, Python, Ruby, PHP, Go, Docker
  • Deployment policies: All at once, Rolling, Rolling with additional batch, Immutable (new ASG), Blue/Green (swap environment URLs)
  • Blue/Green in Beanstalk: Swap CNAME of two environments — instant zero-downtime switch
  • Retains full control: Underlying EC2, RDS, ELB are accessible and configurable

9. Exam Tips & Cheat Sheet

SAP-C02 Compute — Critical Points

  • Spot Instances: 2-minute warning before interruption. Use for stateless, batch, fault-tolerant workloads. NOT for databases or stateful applications.
  • Dedicated Host vs Dedicated Instance: BYOL (per-socket/core licensing) → Dedicated Host. Just compliance isolation → Dedicated Instance (cheaper).
  • Lambda timeout max = 15 minutes. Long-running tasks → Step Functions, ECS, Batch.
  • Lambda cold starts: Mitigate with Provisioned Concurrency. Memory increase also helps (more vCPU = faster init).
  • Fargate: No EC2 to manage. Serverless containers. More expensive per compute unit but less operational overhead.
  • ECS Task Role: Always use task-level IAM roles, not instance profile for container security.
  • EKS vs ECS: EKS = Kubernetes (existing K8s workloads, complex scheduling). ECS = AWS native, simpler, less overhead.
  • Savings Plans > Reserved Instances for flexibility. Compute Savings Plans apply across EC2 families, regions, OS, Lambda, and Fargate.
  • Cluster Placement Group: HPC, low latency. Single AZ = risk. Spread: max 7/AZ. Partition: large distributed systems.
  • Auto Scaling: Target Tracking is simplest and usually the right answer. Predictive scaling for cyclical patterns.
EC2 Instance Selection
  • T-family: burstable, dev/test
  • M-family: general purpose
  • C-family: CPU-intensive
  • R-family: memory-intensive
  • I-family: high local IOPS
  • P/G-family: GPU workloads
  • Graviton (g suffix): best price/perf
Purchasing Decision
  • Steady 1yr+ → Reserved or Savings Plans
  • Fault-tolerant batch → Spot (90% off)
  • Dev/test → On-Demand or Spot
  • BYOL per-socket → Dedicated Host
  • Multi-service commitment → Compute SP
Serverless vs Containers
  • Lambda: event-driven, 15min max
  • Fargate: longer tasks, stateless
  • ECS EC2: full control, cheaper at scale
  • EKS: Kubernetes required
  • Batch: large-scale batch jobs
Lambda Limits
  • Timeout: 15 minutes max
  • Memory: 128MB–10GB
  • Concurrency: 1000 default/region
  • /tmp storage: 512MB–10GB
  • Layers: 5 max, 250MB total
