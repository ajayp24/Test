1. Amazon CloudWatch

CloudWatch is AWS's native observability service for monitoring metrics, collecting logs, setting alarms, and creating dashboards.

CLOUDWATCH CAPABILITIES ┌────────────────────────────────────────────────────────────┐ │ AMAZON CLOUDWATCH │ │ │ │ Metrics Logs Alarms │ │ ┌──────────┐ ┌──────────────┐ ┌────────────────┐ │ │ │ EC2 CPU │ │ App logs │ │ CPU > 80% │ │ │ │ RDS conn │ │ VPC Flow logs│ │ → SNS → PagerD │ │ │ │ Lambda │ │ CloudTrail │ │ → Auto Scale │ │ │ │ Custom │ │ API GW logs │ │ → Stop EC2 │ │ │ │ metrics │ │ EKS logs │ └────────────────┘ │ │ └──────────┘ └──────────────┘ │ │ │ │ Dashboards Insights Contributor Insights │ │ (custom views) (query logs) (identify top talkers) │ │ │ │ Events/Scheduler → EventBridge (migrated there) │ └────────────────────────────────────────────────────────────┘

CloudWatch Key Concepts

  • Namespace: Container for metrics (e.g., AWS/EC2, AWS/RDS, custom/myapp)
  • Metric: Time-series data point (e.g., CPUUtilization). Resolution: 1-minute (standard), 1-second (high-resolution)
  • Dimension: Name/value pair that uniquely identifies a metric (InstanceId=i-1234)
  • Alarm States: OK, ALARM, INSUFFICIENT_DATA
  • Metric Math: Create expressions from multiple metrics (e.g., ErrorRate = Errors/Requests × 100)
  • CloudWatch Agent: Installed on EC2 to collect custom metrics (memory, disk) and logs
  • CloudWatch Logs Insights: Serverless log querying with query language

CloudWatch Alarms

EC2 Metrics NOT in CloudWatch by default: Memory utilization and disk I/O are NOT collected by default. Must install CloudWatch Agent on EC2 to collect these. This is a common exam trap.

CloudWatch Logs Insights Query Example

# Query for Lambda cold starts in last 1 hour
fields @timestamp, @message
| filter @message like /Init Duration/
| stats count(*) as coldStarts by bin(5m)
| sort @timestamp desc

# Find top 10 error sources in API logs
fields @timestamp, errorType, errorMessage
| filter level = "ERROR"
| stats count(*) as errorCount by errorType
| sort errorCount desc
| limit 10

# Calculate P99 Lambda duration
filter @type = "REPORT"
| stats pct(@duration, 99) as p99Duration,
        pct(@duration, 95) as p95Duration,
        avg(@duration) as avgDuration
        by bin(5m)

2. AWS CloudTrail

CloudTrail records AWS API calls made in your account for governance, compliance, and auditing. Every API call = one CloudTrail event.

CLOUDTRAIL ARCHITECTURE API Call Made (by any principal) │ ▼ CloudTrail ├── Management Events (control plane) │ └── CreateEC2, DeleteS3Bucket, AttachRolePolicy │ (enabled by default, stored 90 days in console) │ ├── Data Events (data plane — disabled by default, extra cost) │ └── S3:GetObject, PutObject, DynamoDB:PutItem │ └── Insights Events (detect unusual activity) └── Unusual API call rate, error rate Storage: Event History: 90-day free in console Trail: Send to S3 bucket (long-term), CloudWatch Logs, EventBridge Organization Trail: One trail for ALL accounts in organization Managed from management account Member accounts cannot disable it

3. AWS Config

AWS Config continuously monitors and records AWS resource configurations and allows you to evaluate them against desired configurations (compliance rules).

AWS CONFIG FLOW Resource Changes → Config Recorder → Configuration Items (CIs) │ (history of all changes) ▼ Config Rules (evaluate compliance) ├── AWS Managed Rules (100+ pre-built) │ e.g., "ec2-instances-in-vpc" │ "s3-bucket-public-write-prohibited" │ "rds-storage-encrypted" │ └── Custom Rules (Lambda-backed) │ Results: COMPLIANT / NON_COMPLIANT │ Auto Remediation (SSM Automation) e.g., Encrypt unencrypted EBS volume

AWS Config vs CloudTrail

  • Config: "What is the current state of my resources? Were they always compliant?"
  • CloudTrail: "Who made this API call? When? From where?"
  • Use both: Config for compliance state + CloudTrail for who changed what
Config Aggregator: Aggregate Config data from multiple accounts and regions into a single view. Used in Organizations for centralized compliance visibility.

5. AWS X-Ray

X-Ray provides distributed tracing for applications, helping analyze and debug production and distributed applications (microservices, serverless).

X-RAY DISTRIBUTED TRACE Request: POST /checkout │ API Gateway ──► Lambda (5ms) ──► RDS (120ms) │ │ │ X-Ray SDK │ traces each segment │ Service Map shows: ┌─────────┐ ┌────────┐ ┌──────────┐ │ Browser │──►│ API GW │──►│ Lambda │──► RDS │ 250ms │ │ 15ms │ │ 200ms │ 120ms └─────────┘ └────────┘ └──────────┘ X-Ray identifies bottleneck: RDS is slowest component

X-Ray Key Concepts

  • Trace: End-to-end request from client to all services it touches
  • Segment: Work done by one service (e.g., Lambda function execution)
  • Subsegment: Finer-grained call within a segment (e.g., DynamoDB call within Lambda)
  • Sampling: Not all requests traced (cost/performance). Default: 5% + 1 per second guaranteed
  • Service Map: Visual diagram of all connected services and their health
  • Integration: Lambda, API Gateway, ECS, EKS, EC2, Elastic Beanstalk, SNS, SQS

6. Amazon OpenSearch Service

Managed OpenSearch (successor to Elasticsearch) for log analytics, full-text search, and real-time application monitoring.

  • Ingest from CloudWatch Logs, Kinesis Data Firehose, DMS, Lambda
  • Kibana/OpenSearch Dashboards for visualization
  • Use for: Application log analysis, security event correlation, full-text search, operational dashboards
  • Not a replacement for CloudWatch — works alongside it for richer analytics

CloudWatch Cross-Account Observability

# Set up cross-account log sharing
# In source account (Prod): Share logs to monitoring account
aws logs put-subscription-filter \
  --log-group-name "/aws/lambda/my-function" \
  --filter-name "CrossAccountShare" \
  --filter-pattern "" \
  --destination-arn "arn:aws:logs:us-east-1:MONITORING_ACCOUNT:destination:CentralLogs"

# In monitoring account: Create CloudWatch Logs destination
aws logs put-destination \
  --destination-name "CentralLogs" \
  --target-arn "arn:aws:kinesis:us-east-1:MONITORING_ACCOUNT:stream/central-logs" \
  --role-arn "arn:aws:iam::MONITORING_ACCOUNT:role/CWLtoKinesisRole"

8. Exam Tips & Cheat Sheet

SAP-C02 Observability — Critical Points

  • CloudWatch vs CloudTrail: CloudWatch = monitor performance metrics + logs. CloudTrail = audit API calls. Different purposes.
  • EC2 Memory not in CloudWatch by default. Must install CloudWatch Agent.
  • CloudTrail 90 days: Event history in console. For longer retention, configure a Trail to S3.
  • Organization Trail: Single trail for all accounts. Member accounts cannot disable. Management account only can create.
  • Config vs CloudTrail: Config = what state is my resource in? CloudTrail = who changed it?
  • Config Auto-Remediation: Non-compliant resource → Config Rule → SSM Automation document → Fix it.
  • Session Manager: No bastion host, no SSH port 22, sessions logged. Best practice for EC2 access.
  • X-Ray: Distributed tracing. Use SDK or daemon. Sampling controls cost. Service Map = visual health.
  • Trusted Advisor: Full checks = Business/Enterprise support. Basic = 7 free checks.
  • Audit Manager: Continuously collect evidence for compliance frameworks (SOC2, PCI, HIPAA). NOT a real-time monitoring tool.
Observability Tools
  • Metrics → CloudWatch
  • Logs → CloudWatch Logs
  • Traces → X-Ray
  • API audit → CloudTrail
  • Config compliance → AWS Config
  • Log search/viz → OpenSearch
Systems Manager Use Cases
  • No SSH needed → Session Manager
  • Config data → Parameter Store
  • OS patching → Patch Manager
  • Run scripts at scale → Run Command
  • Auto-remediate → Automation
  • Asset inventory → Inventory
CloudWatch Alarms
  • States: OK, ALARM, INSUFFICIENT_DATA
  • Targets: SNS, Auto Scaling, EC2 action
  • Composite alarms: AND/OR logic
  • High-res metrics: 1 second granularity
  • Custom metrics: PutMetricData API
Governance Services
  • CloudTrail: who did what API call
  • Config: is resource compliant
  • Audit Manager: compliance evidence
  • Trusted Advisor: best practice checks
  • Control Tower: Landing Zone governance
