Chapter 1

Multi-Account & Governance

At the Professional level, AWS expects you to design across accounts, not inside a single one. This chapter covers the governance layer that sits above everything else: Organizations, SCPs, Control Tower, and the strategies that tie them together.

🏢

AWS Organizations

Centrally manage and govern multiple AWS accounts
📚 Definition

AWS Organizations is a free account-management service that lets you consolidate multiple AWS accounts into a single organization that you create and centrally manage. It provides a hierarchical grouping of accounts through Organizational Units (OUs), enables consolidated billing across all member accounts, and allows you to apply Service Control Policies (SCPs) for centralized permission guardrails.

Every organization has exactly one management account (formerly called the master account) that serves as the root of the hierarchy. All other accounts are member accounts. The management account is the only account that can create or invite other accounts, create OUs, apply policies, and manage the organizational structure.

💡 Why It Exists

Without Organizations, managing dozens or hundreds of AWS accounts means separate billing, separate security policies, no centralized governance, and manual coordination everywhere. Organizations solves this by providing:

  • Consolidated billing: A single payer account receives one bill for all member accounts. This automatically qualifies you for volume pricing discounts, Reserved Instance sharing, and Savings Plans sharing across the entire organization.
  • Account-level isolation: Each workload or team gets its own account, providing hard resource and security boundaries. An account is the strongest blast-radius limiter in AWS.
  • Centralized governance: SCPs let you set maximum permission guardrails that apply to every IAM principal in member accounts — even the root user of a member account cannot bypass an SCP.
  • Automated account provisioning: Create new accounts programmatically via API, enabling landing zone automation and Infrastructure as Code patterns.
  • Integration hub: Many AWS services (CloudTrail, Config, GuardDuty, Security Hub, AWS Backup, RAM, SSO) offer organization-wide delegation — Organizations is the glue.
🏗 Where It Is Used in Real Architecture
  • Enterprise landing zones: Every AWS landing zone (Control Tower or custom) is built on top of Organizations. Typical OU structure: Security, Infrastructure, Sandbox, Workloads (Prod / Non-Prod), Suspended.
  • Consolidated billing & cost allocation: Finance teams tag costs, and Organizations aggregates them across all accounts under one payer. Cost Explorer and CUR reports show org-wide spend.
  • Centralized security baselines: Security teams use the organization-wide integration to enable GuardDuty, Security Hub, AWS Config rules, and CloudTrail in every account automatically.
  • Shared services architectures: A networking account hosts Transit Gateway and shares it via RAM across the org. A shared-services account hosts CI/CD pipelines and container registries.
  • Regulatory compliance: In highly regulated industries (financial services, healthcare), SCPs enforce region restrictions, encryption requirements, and service whitelists/blacklists across the board.
✅ When to Choose It
  • You have more than one AWS account (even two is enough to benefit).
  • You need consolidated billing to aggregate spend and share RIs/Savings Plans.
  • You want to enforce security guardrails that even account root users cannot override.
  • You need to create new accounts automatically as part of a CI/CD or onboarding pipeline.
  • You are deploying organization-aware services like AWS SSO, CloudTrail org trail, or GuardDuty multi-account.
  • Any SAP-C02 question mentioning "multiple accounts," "central governance," or "consolidated billing" — Organizations is always the answer.
❌ When NOT to Choose It
  • You only have a single personal account and no plans to expand — Organizations adds no value with one account (though it does not cost anything).
  • You want to restrict permissions within a single account — use IAM policies and permission boundaries instead. Organizations operates at the account level, not the user level.
  • You need to merge two existing organizations — AWS does not support merging. You must move accounts from one org to another, one at a time (leave org → invite to new org).

⚠ SAP-C02 Exam Traps
Trap 1: Management Account is NOT Restricted by SCPs

SCPs do not affect the management account. They only restrict member accounts. If an exam question says "prevent all accounts including the management account from doing X," SCPs alone won't work. You need IAM policies on the management account itself.

Trap 2: SCPs Are Not Grants — They Are Guardrails

An SCP does not grant permissions. It sets the maximum available permissions. A user still needs an IAM policy that explicitly allows the action. Think of SCPs as a ceiling: they can lower what's possible but never raise it.

Trap 3: "Consolidated Billing Only" vs "All Features"

Organizations has two modes. Consolidated billing only gives you one bill but no SCPs, no tag policies, no AI opt-out policies. All features enables everything. The exam almost always assumes All Features mode. If a question mentions SCPs, you need All Features enabled.

Trap 4: You Cannot Merge Organizations

If asked "how to bring two organizations together," the answer is never "merge." You must remove accounts from one org and invite them to the other. Each account can only belong to one organization at a time.

Trap 5: Removing an Account Requires a Valid Payment Method

A member account cannot leave the organization unless it has its own payment method configured. This is a common stumbling block in real-world operations and occasionally appears in exam scenarios about account migration.

See "share Reserved Instances across accounts"? → Consolidated billing via Organizations (RI sharing is on by default).

See "automate new account creation"? → Organizations CreateAccount API or Control Tower Account Factory.

🔬 Example Scenario
A large enterprise is migrating to AWS and plans to have 200+ accounts across multiple business units. They need a single consolidated bill, want to enforce that no account can launch resources in non-approved regions, and need a security account that centrally manages GuardDuty and Security Hub findings for every account. How should they architect this?
Answer: AWS Organizations with All Features enabled
Step 1: Create an AWS Organization in All Features mode with a management account dedicated solely to billing and org management (no workloads).
Step 2: Create OUs: Security, Infrastructure, Workloads/Prod, Workloads/Non-Prod, Sandbox, Suspended.
Step 3: Apply an SCP at the organization root that denies all actions in non-approved regions (e.g., allow only us-east-1 and eu-west-1). Exempt global services (IAM, CloudFront, Route 53, etc.) from the region restriction.
Step 4: In the Security OU, create a Security Tooling account. Designate it as a delegated administrator for GuardDuty and Security Hub. This account will aggregate findings from all member accounts without needing the management account.
Step 5: Enable organization-wide CloudTrail trail from the management account, storing logs in the Log Archive account (also in the Security OU).
Step 6: Use the Organizations CreateAccount API (or Control Tower Account Factory) to provision new accounts with baseline guardrails automatically.

Service Control Policies (SCPs)

Centralized permission guardrails for your entire organization
📚 Definition

Service Control Policies (SCPs) are a type of organization policy within AWS Organizations that let you set the maximum available permissions for IAM users and roles in member accounts. SCPs are JSON policy documents that follow IAM policy syntax but operate at the organization, OU, or individual account level. They act as a permission boundary — they filter what actions are allowed but never grant permissions themselves.

SCPs use an inheritance model: a policy attached to the organization root applies to every OU and account beneath it. A policy attached to a specific OU applies to all accounts (and nested OUs) within it. The effective permissions for any account are the intersection of all SCPs applied at every level from the root down to that account, combined with that account's own IAM policies.

By default, when you enable SCPs, AWS attaches a FullAWSAccess SCP at the root, which allows everything. You then layer restrictive SCPs (deny statements) on top to create guardrails. This is the recommended deny-list strategy. Alternatively, you can remove the FullAWSAccess policy and build an allow-list strategy where you explicitly permit only the services you want — but this is harder to manage at scale.

💡 Why It Exists

IAM policies alone cannot enforce organization-wide rules. An IAM administrator in any account can grant themselves AdministratorAccess. Without SCPs, there is no ceiling — the only limit is what IAM allows. SCPs solve this by creating an organizational ceiling that no one in a member account can break through, not even the account root user.

  • Preventive guardrails: Stop actions before they happen. Unlike detective controls (AWS Config) that catch violations after the fact, SCPs prevent the API call from succeeding in the first place.
  • Region restriction: Ensure workloads only run in approved regions for data sovereignty and compliance (e.g., GDPR requires EU-only).
  • Service restriction: Prevent member accounts from using unapproved services (e.g., no launching SageMaker in sandbox accounts).
  • Security baseline enforcement: Prevent anyone from disabling CloudTrail, deleting VPC flow logs, turning off GuardDuty, or leaving the organization.
  • Root user lockdown: Restrict the root user of member accounts from performing actions (SCPs affect root in member accounts, unlike IAM policies which cannot restrict root).
🏗 Where It Is Used in Real Architecture
  • Landing zone guardrails: Control Tower uses SCPs behind the scenes to implement its mandatory and strongly recommended guardrails (e.g., deny disabling CloudTrail, deny deleting AWS Config rules).
  • Region lockdown: Applied at the organization root to restrict all member accounts to a set of approved regions. Global services (IAM, STS, CloudFront, Route 53, WAF Global, Organizations, etc.) are exempted using condition keys.
  • Sandbox controls: On the Sandbox OU, SCPs limit expensive services (e.g., deny ec2:RunInstances for instance types larger than t3.large), prevent production-grade resources, and block networking to corporate networks.
  • Security OU protections: SCPs on the Security OU prevent log deletion, CloudTrail modification, and GuardDuty detector deletion to ensure tamper-proof security tooling.
  • Quarantine / incident response: A "Suspended" OU with a deny-all SCP ("Effect": "Deny", "Action": "*", "Resource": "*") is used to instantly quarantine a compromised account by moving it into that OU.
  • Compliance mandates: Financial institutions use SCPs to ensure encryption is always required (deny s3:PutObject without server-side encryption header), or prevent public S3 buckets.
✅ When to Choose It
  • You need to enforce a hard rule that no one in member accounts can bypass, including the account root user.
  • You want preventive controls (block the action) rather than detective controls (alert after the action).
  • You need to restrict which AWS regions, services, or actions are available across multiple accounts at once.
  • You want to protect critical security configurations (CloudTrail, Config, GuardDuty) from being tampered with.
  • You need to implement a quarantine mechanism for compromised accounts.
  • Any exam question that says "prevent," "deny," "restrict," or "ensure nobody can" across member accounts → think SCPs.
❌ When NOT to Choose It
  • To grant permissions: SCPs cannot grant. They only restrict. You still need IAM policies to allow actions. If an SCP allows s3:* but no IAM policy grants it, the user still cannot access S3.
  • To restrict the management account: SCPs do not affect the management account. Use IAM policies directly on the management account instead.
  • To control IAM Identity Center (SSO) permission sets: SCPs apply to the target account, not to the SSO configuration itself. They can limit what an SSO user can do in the target account, but they do not manage SSO assignments.
  • For resource-level policies in a single account: Use IAM policies, resource policies, or permission boundaries for single-account, single-user restrictions.
  • For detection and remediation: SCPs prevent actions but cannot detect violations or auto-remediate. Use AWS Config rules + remediation for that.
  • For data-plane restrictions: SCPs generally control control-plane API calls. For data-plane restrictions (e.g., S3 object access patterns), use bucket policies and IAM.

📊 Common SCP Patterns (Policy Examples)
Pattern 1: Region Restriction

Deny all actions in non-approved regions while exempting global services:

{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "DenyNonApprovedRegions",
    "Effect": "Deny",
    "NotAction": [
      "iam:*", "sts:*", "organizations:*",
      "cloudfront:*", "route53:*", "waf:*",
      "budgets:*", "support:*"
    ],
    "Resource": "*",
    "Condition": {
      "StringNotEquals": {
        "aws:RequestedRegion": ["us-east-1", "eu-west-1"]
      }
    }
  }]
}
Pattern 2: Protect CloudTrail

Prevent anyone from stopping logging or deleting trails:

{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "ProtectCloudTrail",
    "Effect": "Deny",
    "Action": [
      "cloudtrail:StopLogging",
      "cloudtrail:DeleteTrail",
      "cloudtrail:UpdateTrail"
    ],
    "Resource": "*"
  }]
}
Pattern 3: Deny-All Quarantine SCP

Attach to a Suspended OU to immediately isolate compromised accounts:

{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "DenyEverything",
    "Effect": "Deny",
    "Action": "*",
    "Resource": "*"
  }]
}
Pattern 4: Prevent Leaving the Organization

Stop member accounts from removing themselves:

{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "DenyLeaveOrg",
    "Effect": "Deny",
    "Action": "organizations:LeaveOrganization",
    "Resource": "*"
  }]
}
Pattern 5: Require Encryption on S3

Deny unencrypted object uploads across all accounts:

{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "DenyUnencryptedS3",
    "Effect": "Deny",
    "Action": "s3:PutObject",
    "Resource": "*",
    "Condition": {
      "StringNotEquals": {
        "s3:x-amz-server-side-encryption": "aws:kms"
      }
    }
  }]
}

⚠ SAP-C02 Exam Traps
Trap 1: SCPs Do NOT Affect the Management Account

This is the most tested SCP trap. If a question says "prevent ALL accounts including the management account from doing X," SCPs cannot do this alone. You need IAM policies on the management account. Best practice: run no workloads in the management account to minimize this risk.

Trap 2: SCPs Do NOT Grant Permissions

A common distractor answer says "add an SCP that allows EC2 access." That is not how SCPs work. An SCP that says Allow ec2:* only means EC2 is not blocked by the SCP. The user still needs an IAM policy that explicitly grants EC2 access. Effective permissions = SCP ∩ IAM.

Trap 3: SCPs Affect the Root User of Member Accounts

Unlike IAM policies (which cannot restrict the root user), SCPs do restrict the root user of member accounts. This is a key differentiator. If the exam asks "how to prevent the root user of a member account from doing X," SCPs are the answer.

Trap 4: Region Restriction Requires Exempting Global Services

If you deny all actions outside approved regions without exempting global services (IAM, STS, Organizations, CloudFront, Route 53, WAF Classic global, Support, Billing), you will break the account. The NotAction + aws:RequestedRegion condition pattern is the correct approach. Watch for exam answers that use Action: "*" without exemptions — that is a trap.

Trap 5: SCP Limits

Each SCP document can be at most 5,120 characters (including whitespace). You can attach a maximum of 5 SCPs per OU or account. If you need more conditions, you must split across multiple SCPs. Some exam scenarios test whether you know these limits exist.

Trap 6: SCPs Do NOT Affect Service-Linked Roles

Service-linked roles (SLRs) are used by AWS services themselves. SCPs restrict IAM principals in the account but do not prevent actions performed by service-linked roles. If the exam says "an SCP blocks X but the service still performs X," this is likely because the service uses an SLR.

Trap 7: "Allow List" vs "Deny List" Strategy Confusion

Deny-list (recommended): Keep the default FullAWSAccess and add deny statements for what you don't want. Easy to manage.
Allow-list: Remove FullAWSAccess and explicitly allow only what you want. Very restrictive but hard to maintain — any new service requires updating the SCP. Exam questions about "least privilege at the org level" may hint at allow-list, but in practice deny-list is almost always the correct answer.

🔬 Example Scenario
A financial services company has 80 AWS accounts under AWS Organizations. Regulatory requirements mandate that all workloads must run only in eu-west-1 and eu-central-1. The security team also wants to ensure that nobody in any member account can disable CloudTrail logging or delete VPC flow logs. Additionally, if an account is suspected of being compromised, the security team needs a way to immediately freeze all activity in that account. How should the solutions architect implement this?
Answer: Three SCPs applied at different levels
SCP 1 — Region Restriction (attach at Organization Root): Use a Deny statement with NotAction to exempt global services (IAM, STS, CloudFront, Route 53, Organizations, Support, Billing) and a StringNotEquals condition on aws:RequestedRegion with values ["eu-west-1", "eu-central-1"]. This prevents any regional service API calls outside those two regions for all member accounts.

SCP 2 — Protect Security Services (attach at Organization Root): Deny cloudtrail:StopLogging, cloudtrail:DeleteTrail, cloudtrail:UpdateTrail, ec2:DeleteFlowLogs, and guardduty:DeleteDetector for all resources. This ensures no IAM principal in any member account can tamper with security logging.

SCP 3 — Quarantine (attach to Suspended OU): Create a Suspended OU with a Deny all SCP ("Effect": "Deny", "Action": "*", "Resource": "*"). When the security team suspects compromise, they move the account to this OU. The deny-all SCP takes effect immediately, freezing all API activity while preserving the account and its resources for forensic investigation.

Important: None of these SCPs affect the management account. Ensure the management account has equivalent IAM policies and runs no workloads. Consider designating a delegated administrator account in the Security OU for GuardDuty, Security Hub, and CloudTrail management.
A developer in a member account has AdministratorAccess IAM policy attached to their role. The account is in an OU with an SCP that denies ec2:RunInstances for instance types larger than m5.xlarge. The developer tries to launch an m5.4xlarge instance. What happens?
Answer: The request is DENIED
Even though the developer has AdministratorAccess (which grants Allow *), the SCP sets the maximum permissions ceiling. The SCP explicitly denies m5.4xlarge, so the final effective permission is Deny. This demonstrates that SCPs always win over IAM policies in member accounts — Effective = SCP ∩ IAM, and an explicit deny at any level trumps everything.
🔗 Related AWS Services

  • IAM Policies: Work together with SCPs. SCPs set the ceiling; IAM policies grant the actual permissions within that ceiling.
  • IAM Permission Boundaries: Similar concept but scoped to individual IAM users/roles within a single account. SCPs operate at the account/OU level.
  • AWS Control Tower: Uses SCPs to implement its guardrails. Managed SCPs are created and maintained by Control Tower automatically.
  • AWS Config: Provides detective controls (detect violations after the fact) as a complement to SCPs' preventive controls (block violations before they happen).
  • Tag Policies: Another organization policy type for enforcing tag standardization. Not the same as SCPs but managed through the same Organizations console.
  • Backup Policies: Organization-level backup policies that automate AWS Backup across accounts and OUs.
  • AI Services Opt-Out Policies: Organization-level policy to opt out of data usage for AI service improvement across all accounts.

AWS Control Tower

Automated, opinionated multi-account landing zone
📚 Definition

AWS Control Tower is a managed service that automates the setup and governance of a secure, well-architected multi-account AWS environment (a landing zone). It builds on top of AWS Organizations, AWS SSO (IAM Identity Center), AWS Config, and CloudFormation StackSets to create a pre-configured environment with best-practice guardrails already applied.

Control Tower creates a landing zone consisting of: a management account, a Log Archive account (centralized CloudTrail + Config logs), and an Audit account (cross-account security read access). It organizes accounts into a recommended OU structure and applies guardrails (preventive SCPs + detective Config rules) automatically.

💡 Why It Exists
  • Reduced setup time: Manually setting up Organizations + SCPs + Config + CloudTrail + SSO across accounts takes weeks. Control Tower does it in hours.
  • Account Factory: Self-service or automated provisioning of new accounts with pre-applied guardrails, network baselines, and SSO access. Backed by Service Catalog.
  • Managed guardrails: AWS maintains and updates guardrails. Categories: mandatory (always on), strongly recommended, and elective. Guardrails are either preventive (SCPs) or detective (Config rules).
  • Dashboard: A single-pane view showing compliance status of all accounts and OUs against enabled guardrails.
  • Customizations for Control Tower (CfCT): An AWS solution that lets you apply custom CloudFormation templates and SCPs automatically when new accounts are created via Account Factory.
🏗 Where It Is Used in Real Architecture
  • Enterprise customers starting fresh on AWS who want a governed landing zone without building from scratch.
  • Organizations that want Account Factory for self-service account vending to development teams.
  • Environments where compliance requires built-in guardrails that are auditable from a central dashboard.
  • Companies extending an existing Organization by enrolling existing accounts into Control Tower management.
✅ When to Choose It
  • You want a prescriptive, AWS-recommended landing zone with minimal custom work.
  • You need automated account provisioning with guardrails applied out of the box.
  • You want managed guardrails (AWS maintains the SCPs and Config rules for you).
  • Exam keyword: "automated landing zone," "account vending," "managed guardrails."
❌ When NOT to Choose It
  • You already have a mature custom landing zone with your own automation — Control Tower may conflict with existing SCPs and Config rules.
  • You need full control over every OU, SCP, and Config rule — Control Tower's managed guardrails may be too opinionated.
  • You only have 2-3 accounts and don't plan to grow — the overhead of Control Tower is not justified.
  • You need to support regions not yet supported by Control Tower (check the supported regions list).

IAM, Permission Boundaries, ABAC/RBAC

Identity, access control, and delegation strategies
📚 Definition

AWS Identity and Access Management (IAM) controls who (authentication) can do what (authorization) on which resources in your AWS account. IAM provides users, groups, roles, and policies. At the Professional level, the focus shifts from basic IAM to advanced patterns:

  • Permission Boundaries: An advanced IAM feature that sets the maximum permissions an IAM user or role can have. Even if a policy grants broader access, the effective permissions are the intersection of the identity policy and the permission boundary. Used to safely delegate IAM administration.
  • RBAC (Role-Based Access Control): Traditional model — create IAM policies for each job function (DevOps role, DBA role, ReadOnly role). Requires creating new policies when new resources or functions are added.
  • ABAC (Attribute-Based Access Control): Tag-based access control. Policies use condition keys like aws:ResourceTag, aws:PrincipalTag, and aws:RequestTag to grant access dynamically. A single policy can scale to many resources without modification — just tag them correctly.
💡 Why It Exists
  • Permission boundaries: Solve the delegation problem. You want a team lead to create IAM roles for their team, but you don't want them creating roles with more privileges than their own. A permission boundary caps what the created roles can do.
  • ABAC: Solves the scaling problem. In a large organization with hundreds of projects, RBAC requires hundreds of policies. ABAC requires one policy that uses tags. When a new project starts, you just tag resources and users — no policy changes needed.
  • IAM roles for services: EC2 instance profiles, Lambda execution roles, ECS task roles — the Professional exam tests your understanding of which role type to use where.
🏗 Where It Is Used in Real Architecture
  • Delegated IAM administration: Central security team sets permission boundaries. Team leads create IAM roles within those boundaries. Prevents privilege escalation.
  • ABAC for multi-tenant environments: Tag resources with Project=X, tag IAM roles with Project=X, and write one policy: "allow access only when PrincipalTag/Project matches ResourceTag/Project."
  • Cross-account role assumption: IAM roles with trust policies allowing principals from other accounts to assume them (see Cross-Account Access section).
  • Service-linked roles: AWS-managed roles that services create to act on your behalf (e.g., AWSServiceRoleForAutoScaling).

⚠ SAP-C02 Exam Traps
Trap 1: Permission Boundary ≠ SCP

Both are ceilings, but SCPs apply at the account level (all principals in the account). Permission boundaries apply to a specific IAM user or role. In a multi-account setup, you might use both: SCP at the org level + permission boundary at the role level.

Trap 4: IAM is Global

IAM is a global service, not regional. Users, roles, and policies exist globally. But some resources (like instance profiles) are associated with specific regions. Don't be tricked by answers suggesting "create IAM role in the same region."

IAM Identity Center & Federation

Centralized workforce access to multiple AWS accounts and apps
📚 Definition

AWS IAM Identity Center (formerly AWS SSO) provides centralized access management for human users across all AWS accounts in your organization and business applications. It integrates with external identity providers (IdPs) via SAML 2.0 or SCIM for automatic user/group provisioning.

Key concepts:

  • Permission Sets: Collections of IAM policies that define what a user can do in a target account. Assigned to users/groups for specific accounts. Control Tower creates permission sets like AWSAdministratorAccess, AWSReadOnlyAccess, etc.
  • Identity Source: Where users are stored — either IAM Identity Center's built-in directory, an external IdP (Okta, Azure AD, OneLogin), or AWS Managed Microsoft AD.
  • SAML 2.0 Federation: Allows federated sign-in to AWS using your corporate IdP. The IdP authenticates the user, sends a SAML assertion to AWS, and STS issues temporary credentials.
  • Web Identity Federation: For customer-facing apps. Users authenticate with social IdPs (Google, Facebook, Amazon) or any OIDC-compatible provider. Use Cognito User Pools + Identity Pools for this.
💡 Why It Exists
  • Eliminate IAM users: Instead of creating IAM users in every account, users sign in once via SSO and access any assigned account with temporary credentials. No long-lived access keys.
  • Single sign-on: One login for all AWS accounts and business applications (Salesforce, Slack, custom SAML apps).
  • Centralized assignment: Security team manages who has access to which accounts from one place, not in each account's IAM.
  • Automatic provisioning: SCIM syncs users and groups from your corporate IdP to IAM Identity Center automatically.

Cross-Account Access

Patterns for securely sharing resources and access between AWS accounts
📚 Definition

Cross-account access refers to the patterns and mechanisms that allow IAM principals in one AWS account to access resources in another account. There are three primary mechanisms:

  • IAM Role Assumption (AssumeRole): An IAM role in Account B has a trust policy allowing Account A. A principal in Account A calls sts:AssumeRole to get temporary credentials for Account B. This is the most common and recommended pattern.
  • Resource-Based Policies: Some services (S3, KMS, SQS, SNS, Lambda, API Gateway) support resource-based policies that directly grant access to principals in other accounts. No role assumption needed — the principal retains their original identity.
  • AWS RAM (Resource Access Manager): For sharing AWS resources (subnets, Transit Gateway, License Manager configs, Route 53 Resolver rules) across accounts within an Organization without copying them.

Trap 1: Resource Policy vs AssumeRole with KMS

For KMS cross-account access, you need both: the KMS key policy must allow the external account AND the external account must have an IAM policy allowing KMS actions. This two-sided requirement is heavily tested.

Multi-Account Strategy

Why and how to structure accounts, OUs, and workload isolation
📚 Definition

A multi-account strategy is the practice of using multiple AWS accounts — each serving a specific purpose — rather than putting everything in one account. AWS accounts are the strongest isolation boundary available. An account provides separate IAM namespaces, separate service quotas, separate billing, and separate blast radius. The SAP-C02 exam heavily tests your ability to design proper multi-account architectures.

💡 Why It Exists
  • Blast-radius containment: A misconfiguration or security breach in one account does not affect others.
  • Service quota isolation: Each account has its own service limits. A runaway workload in dev won't exhaust production limits.
  • Billing separation: Clear cost attribution per team, project, or environment.
  • Regulatory compliance: Certain workloads (PCI, HIPAA) require isolation from non-compliant workloads.
  • Team autonomy: Teams get their own accounts with appropriate guardrails, reducing the need for centralized IAM management.

Shared Services Account

Centralized infrastructure shared across all workload accounts
📚 Definition

A shared services account is a dedicated AWS account in the Infrastructure OU that hosts resources consumed by multiple workload accounts. Instead of duplicating services in every account, you centralize them and share access via cross-account mechanisms (RAM, VPC peering, PrivateLink, or cross-account IAM roles).

Trap 1: RAM Sharing ≠ Resource Policies

Deploy infrastructure templates across multiple accounts and regions
📚 Definition

VPC Fundamentals

Your isolated virtual network in AWS
📚 Definition

A Virtual Private Cloud (VPC) is a logically isolated network within an AWS region. It is the foundational networking construct — almost every AWS resource you launch sits inside a VPC. A VPC spans all Availability Zones (AZs) in a region. You define its IP address range using a CIDR block (e.g., 10.0.0.0/16), then subdivide it into subnets.

Key attributes: VPCs are regional. The maximum CIDR is /16 (65,536 IPs), minimum is /28 (16 IPs). You can associate up to 5 CIDR blocks per VPC. IPv6 is supported (AWS assigns a /56 block). VPCs do not span regions — for multi-region, you use VPC peering or Transit Gateway inter-region peering.

Trap 1: Non-Overlapping CIDRs

VPCs that need to peer, connect via Transit Gateway, or connect via VPN to on-prem must have non-overlapping CIDR blocks. This is one of the most common networking traps. If two VPCs have overlapping CIDRs, they cannot be peered.

If VPC-A peers with VPC-B and VPC-B peers with VPC-C, VPC-A cannot reach VPC-C through VPC-B. For transitive routing, use Transit Gateway.

Trap 3: 5 Reserved IPs per Subnet

AWS reserves 5 IPs in every subnet: network address, VPC router (.1), DNS server (.2), future use (.3), and broadcast. A /24 subnet has 251 usable IPs, not 256.

Subnets, Route Tables, NACLs, Security Groups

The four layers of VPC traffic control
📚 Definition
  • Subnets: Subdivisions of a VPC CIDR within a single AZ. A subnet is public if its route table has a route to an Internet Gateway; otherwise it's private.
  • Route Tables: Rules that determine where network traffic is directed. Each subnet must be associated with exactly one route table. The most specific route wins (longest prefix match).
  • NACLs (Network Access Control Lists): Stateless firewall at the subnet level. Evaluated in rule-number order. Must explicitly allow return traffic. Default NACL allows all; custom NACLs deny all by default.
  • Security Groups: Stateful firewall at the ENI (instance) level. Return traffic is automatically allowed. Default SG allows all outbound, denies all inbound. Can reference other security groups.

NAT Gateway, Internet Gateway, Egress-Only IGW

Controlling internet connectivity in and out of your VPC
📚 Definition
  • Internet Gateway (IGW): A horizontally scaled, redundant VPC component that allows communication between instances in your VPC and the internet. Attached at the VPC level. Required for public subnets. One IGW per VPC.
  • NAT Gateway: Allows instances in private subnets to initiate outbound internet connections (e.g., software updates) while preventing inbound connections. Deployed in a public subnet with an Elastic IP. Managed service, scales automatically up to 100 Gbps. Charges per hour + per GB processed.
  • Egress-Only Internet Gateway: The IPv6 equivalent of a NAT Gateway. Allows outbound IPv6 traffic from private instances but blocks inbound connections. No charge (unlike NAT Gateway).
⚠ SAP-C02 Exam Traps
Trap 1: NAT Gateway Cost Trap

NAT Gateway charges both hourly ($0.045/hr ~$32/month) AND per GB processed ($0.045/GB). High-volume traffic through NAT Gateway is expensive. Exam questions about "reducing network costs" often have the answer: use VPC endpoints (Gateway endpoints for S3/DynamoDB are free) to bypass NAT Gateway for AWS service traffic.

Trap 2: NAT Gateway is AZ-Specific

A NAT Gateway lives in one AZ. If that AZ goes down, instances in other AZs using that NAT Gateway lose internet access. Best practice: deploy one NAT Gateway per AZ and route each AZ's private subnet to its local NAT Gateway.

Trap 3: NAT Gateway vs NAT Instance

NAT Instance is legacy (EC2-based, self-managed). Exam may list it as a distractor. Always prefer NAT Gateway unless the question specifically asks about cost savings for low-throughput workloads (NAT Instance on a small EC2 can be cheaper).

⚡ Decision Shortcut
Quick Decision Rule

"Private instances need internet access (IPv4)" → NAT Gateway in a public subnet.

"Private instances need internet access (IPv6)" → Egress-Only Internet Gateway.

"Reduce NAT Gateway costs" → Use VPC Gateway endpoints for S3/DynamoDB traffic.

"Public-facing instances" → Internet Gateway + public IP/Elastic IP.

VPC Endpoints & PrivateLink

Access AWS services privately without traversing the internet
📚 Definition
  • Gateway Endpoint: A route-table entry that sends traffic to S3 or DynamoDB directly over the AWS private network. Free. Only works for S3 and DynamoDB. No ENI created — it's a route-table target. Does not support cross-region. Controlled by endpoint policies.

  • AWS PrivateLink: The underlying technology for Interface Endpoints. Also allows you to expose your own service (behind an NLB) to other VPCs or accounts privately. The consumer creates an Interface Endpoint to the provider's PrivateLink service.

Transit Gateway

Hub-and-spoke connectivity for VPCs, VPNs, and Direct Connect
📚 Definition

AWS Transit Gateway (TGW) is a regional network transit hub that connects VPCs, VPN connections, and Direct Connect gateways through a single gateway. It supports transitive routing (unlike VPC peering), making it the solution for connecting many VPCs without creating a full mesh. Key features: route tables for traffic segmentation, inter-region peering, multicast support, shared via RAM across accounts, ECMP (Equal-Cost Multi-Path) for VPN aggregated throughput.

AWS Direct Connect

Dedicated private network connection from on-premises to AWS
📚 Definition

AWS Direct Connect (DX) is a dedicated physical network connection between your data center and an AWS Direct Connect location. It provides consistent, low-latency, high-bandwidth connectivity that bypasses the public internet. Available in 1 Gbps, 10 Gbps, and 100 Gbps dedicated connections, or 50 Mbps to 10 Gbps hosted connections.

Key concepts:

  • Virtual Interfaces (VIFs): Private VIF connects to VPCs. Public VIF accesses AWS public services (S3, DynamoDB) without internet. Transit VIF connects to Transit Gateway.
  • Direct Connect Gateway (DXGW): Connects a DX connection to VPCs in multiple regions (up to 10 VGWs or 3 TGWs). Solves the "DX is in one region, VPCs are in many" problem.
  • LAG (Link Aggregation Group): Bundle multiple DX connections for aggregated throughput.

Amazon CloudFront

Global CDN for low-latency content delivery
📚 Definition

Amazon CloudFront is a global Content Delivery Network (CDN) with 400+ edge locations. It caches content at edge locations close to users for low latency. Supports static content (S3), dynamic content (API/app servers), video streaming (VOD and live), and WebSocket connections.

Key features: Origin Access Control (OAC) for secure S3 access (replaces OAI), signed URLs/cookies for private content, field-level encryption, custom SSL certificates (ACM), geo-restriction, and integration with WAF and Shield.

⚠ SAP-C02 Exam Traps
Trap 1: OAC Replaces OAI

Origin Access Identity (OAI) is legacy. The exam now prefers Origin Access Control (OAC) for restricting S3 bucket access to CloudFront only. OAC supports SSE-KMS, newer S3 features, and is the recommended approach.

Trap 2: Signed URLs vs Signed Cookies

Signed URL: One URL per file. Use when you want to restrict access to individual files or when your client doesn't support cookies. Signed Cookie: One cookie for multiple files. Use when you want to provide access to multiple restricted files (e.g., a subscriber area of a website).

Trap 3: CloudFront vs S3 Transfer Acceleration

CloudFront is for downloads (caching at edge). S3 Transfer Acceleration is for uploads (accelerated PUT). If the question is about speeding up uploads from clients worldwide, the answer is S3 Transfer Acceleration, not CloudFront.

Amazon SQS

Fully managed message queuing service
📚 Definition

Amazon Simple Queue Service (SQS) is a fully managed message queue for decoupling producers and consumers. Two queue types:

  • Standard Queue: Nearly unlimited throughput, at-least-once delivery, best-effort ordering. May deliver duplicates.

Key features: visibility timeout (prevents double processing), dead-letter queues (DLQ for failed messages), long polling (reduces empty responses), message retention up to 14 days, max message size 256 KB (use S3 + Extended Client Library for larger).

If the question says "messages must be processed in order" or "exactly once" → FIFO. If it says "maximum throughput" or "at-least-once is acceptable" → Standard. FIFO queue names must end with .fifo.

Trap 2: SQS Is Pull-Based, Not Push

Consumers poll SQS for messages. SQS does not push messages. If the question needs push-based delivery, use SNS (which can push to SQS, Lambda, HTTP endpoints, email, etc.).

Visibility timeout (default 30s, max 12h) is how long a message is hidden from other consumers after being read. Message retention (default 4 days, max 14 days) is how long SQS keeps an unprocessed message. If consumers are slow, increase visibility timeout — not retention.

Amazon RDS

Managed relational databases (MySQL, PostgreSQL, Oracle, SQL Server, MariaDB)
📚 Definition

Amazon RDS manages relational database engines. AWS handles patching, backups, replication, and failover. Key features: Multi-AZ (synchronous standby for HA — automatic failover, not for read scaling), Read Replicas (async replication for read scaling — up to 15 for Aurora, 5 for others, can be cross-region), automated backups (35-day retention, point-in-time recovery), manual snapshots (persist until deleted, shareable cross-account/region).

⚠ SAP-C02 Exam Traps
Trap 1: Multi-AZ ≠ Read Scaling

Multi-AZ is for availability (failover). The standby is NOT accessible for reads. For read scaling, use Read Replicas. Multi-AZ + Read Replicas can be combined.

Trap 2: Cross-Region Read Replicas for DR

A cross-region read replica serves double duty: read scaling in another region AND a DR strategy. In a disaster, promote the replica to a standalone database. This is a common exam pattern for "multi-region with low RPO."

Trap 3: Encryption at Rest

RDS encryption must be enabled at creation time. You cannot encrypt an unencrypted database in place. To encrypt: snapshot → copy snapshot with encryption → restore from encrypted snapshot. Read replicas of encrypted instances are automatically encrypted.

S3 Lifecycle, Replication, Object Lock

Automated data management, cross-region replication, and immutability
📚 Definition
  • Lifecycle Rules: Automatically transition objects between storage classes or expire them. Example: Standard → Standard-IA after 30 days → Glacier after 90 days → delete after 365 days.
  • S3 Replication: CRR (Cross-Region Replication) for DR and compliance. SRR (Same-Region Replication) for log aggregation or live replication between accounts. Requires versioning on both buckets. Can replicate to different storage class and different account.
  • S3 Object Lock: WORM (Write Once Read Many) protection. Governance mode: Users with special permissions can delete. Compliance mode: Nobody can delete, not even root, until retention expires. Used for SEC 17a-4, HIPAA, financial compliance.
⚠ SAP-C02 Exam Traps
Trap 1: Replication Does NOT Replicate Retroactively

Enabling replication only replicates new objects. Existing objects are NOT replicated. To replicate existing objects, use S3 Batch Replication.

Trap 2: Delete Markers in Replication

By default, delete markers are NOT replicated. If you want deletes to replicate, you must enable "delete marker replication." This is a security feature — prevents malicious deletion from propagating.

Trap 3: Compliance Mode Object Lock = Truly Immutable

In Compliance mode, no one (including root) can delete or overwrite the object until retention expires. If the exam says "regulatory requirement for immutable data," the answer is Object Lock in Compliance mode, not Governance mode.

Trap 4: Lifecycle Transition Waterfall

Objects can only transition "downward" in the storage class hierarchy. You cannot transition from Glacier back to Standard via lifecycle. To retrieve from Glacier, you must restore the object.

Security is the most heavily weighted domain in SAP-C02. This chapter covers threat detection, compliance, encryption, secrets management, and network security — the services you must know to answer ~30% of exam questions.

🕵

Amazon GuardDuty

Intelligent threat detection using ML and anomaly detection
📚 Definition

GuardDuty is a managed threat detection service that continuously monitors VPC Flow Logs, CloudTrail events, CloudTrail management events, DNS logs, EKS audit logs, S3 data events, RDS login events, and Lambda network activity for malicious behavior. Uses ML, anomaly detection, and integrated threat intelligence. Produces findings (ranked by severity) that can trigger EventBridge rules → Lambda/SNS for automated remediation.

⚠ SAP-C02 Exam Traps
Trap 1: GuardDuty = Detection, NOT Prevention

GuardDuty detects threats but does not block them. For automated remediation, use GuardDuty findings → EventBridge → Lambda (e.g., revoke security group, isolate instance, disable access key). For prevention, use WAF, NACLs, or Network Firewall.

Trap 2: Organization-Wide with Delegated Admin

GuardDuty supports Organizations integration. Designate a security account as delegated administrator. All findings from all member accounts aggregate there. The exam expects this pattern for "centralized threat detection across all accounts."

Trap 3: GuardDuty Does NOT Need CloudTrail Enabled

GuardDuty reads CloudTrail events independently (from its own data source). You don't need to have CloudTrail enabled in each account for GuardDuty to work (though you should for other reasons).

AWS Config

Resource configuration tracking and compliance auditing
📚 Definition

AWS Config continuously records the configuration of AWS resources and evaluates them against desired configurations using Config Rules. It provides a configuration history timeline, compliance dashboard, and auto-remediation (trigger SSM Automation documents to fix non-compliant resources). Supports Organizations with an aggregator for cross-account, cross-region compliance views.

⚠ SAP-C02 Exam Traps
Trap 1: Config = Detective Control (Not Preventive)

Config detects non-compliance after a resource is created/changed. It does NOT prevent non-compliant resources from being created. For prevention, use SCPs (preventive guardrails). Config + auto-remediation can fix violations quickly, but the violation happens first.

Trap 2: Config Aggregator for Multi-Account

A Config aggregator collects data from multiple accounts and regions into a single view. Deploy the aggregator in the security or audit account for organization-wide compliance monitoring.

Trap 3: Config vs CloudTrail

Config: "What does my resource look like now, and has it ever been compliant?" (configuration state). CloudTrail: "Who did what, when?" (API activity). They complement each other.

AWS CloudTrail

API activity logging and auditing across your AWS account
📚 Definition

CloudTrail records all API calls made in your AWS account (who, what, when, from where). Logs management events (control plane: CreateBucket, RunInstances) and optionally data events (data plane: GetObject, PutObject, Lambda Invoke). Supports organization trails for centralized logging across all org accounts. Logs can be sent to S3, CloudWatch Logs, and EventBridge.

⚠ SAP-C02 Exam Traps
Trap 1: Management Events vs Data Events

By default, CloudTrail logs management events only. Data events (S3 object operations, Lambda invocations) are NOT logged by default and cost extra. If the question says "log who accessed S3 objects," you need to enable data events.

Trap 2: CloudTrail Log Integrity Validation

CloudTrail can create a digest file for log integrity validation. This cryptographically proves logs haven't been tampered with. If the question mentions "tamper-proof audit logs" or "log integrity," enable log file validation.

Trap 3: 90-Day Event History vs Trail

CloudTrail provides a free 90-day event history in the console (management events only, not configurable). For long-term storage, cross-account delivery, or data events, you need a trail that delivers logs to S3.

AWS KMS

Managed encryption key creation and control
📚 Definition

AWS Key Management Service creates and manages cryptographic keys for encryption at rest and in transit. Key types: AWS managed keys (aws/service, auto-created), Customer managed keys (CMKs) (you create, control policy, enable rotation), AWS owned keys (used by AWS internally, invisible to you). Supports symmetric (AES-256) and asymmetric (RSA, ECC) keys. Envelope encryption: KMS encrypts data keys; data keys encrypt your data.

⚠ SAP-C02 Exam Traps
Trap 1: KMS Keys Are Regional

KMS keys exist in a single region. To use the same data in another region, you need a KMS key in that region. For cross-region replication of encrypted data (S3, EBS snapshots), you must specify a KMS key in the target region.

Trap 2: Key Policy + IAM Policy = Access

Every KMS key has a key policy (resource policy). Unlike most AWS resources, KMS access requires the key policy to allow access OR the key policy to delegate to IAM. If the key policy doesn't allow the account root, IAM policies alone won't work.

Trap 3: KMS Request Quotas

KMS has per-second request quotas (5,500-30,000 depending on region and key type). High-throughput encryption (S3, EBS) can hit these limits. Solutions: S3 Bucket Keys (reduces KMS calls by 99%), data key caching, or request a quota increase.

Trap 4: Cross-Account KMS Access

To allow cross-account access: (1) Key policy grants access to the external account, AND (2) IAM policy in the external account grants KMS actions. Both sides are required.

AWS WAF

Web Application Firewall for Layer 7 protection
📚 Definition

AWS WAF protects web applications from common exploits at Layer 7 (HTTP/HTTPS). Deploys on CloudFront, ALB, API Gateway, AppSync, and Cognito User Pool. Uses Web ACLs with rules: IP-based, geo-based, rate-based (DDoS), SQL injection, XSS, and AWS Managed Rule Groups (OWASP Top 10, Known Bad Inputs, Bot Control). Supports custom rules and rule groups.

⚠ SAP-C02 Exam Traps
Trap 1: WAF = Layer 7, NACL = Layer 4, Network Firewall = Layer 3-7

"Block SQL injection" → WAF. "Block a specific IP at network level" → NACL or WAF. "Deep packet inspection, IDS/IPS" → Network Firewall.

Trap 2: Rate-Based Rules for Layer 7 DDoS

WAF rate-based rules can block IPs that exceed a threshold (e.g., 2,000 requests in 5 minutes). This is the answer for "mitigate HTTP flood attacks" at the application layer. Shield handles network-layer DDoS.

Amazon CloudWatch

Metrics, logs, alarms, and dashboards for AWS resources
📚 Definition

CloudWatch collects metrics, logs, and events from AWS resources and applications. Key features: Metrics (standard metrics free at 5-min intervals; detailed monitoring at 1-min for extra cost; custom metrics up to 1-second resolution), Alarms (trigger SNS, Auto Scaling, EC2 actions), Logs (log groups/streams, metric filters, Logs Insights for querying), Dashboards (cross-account, cross-region), Contributor Insights (top-N analysis), Synthetics (canary scripts to monitor endpoints), Application Insights (.NET/SQL Server monitoring), and CloudWatch Evidently (feature flags/A/B testing).

⚠ SAP-C02 Exam Traps
Trap 1: Memory/Disk Metrics Require CloudWatch Agent

CloudWatch does NOT collect memory utilization or disk usage by default. You must install the CloudWatch Agent on EC2 instances to collect these. This is commonly tested.

Trap 2: Cross-Account CloudWatch

CloudWatch supports cross-account observability. You can create cross-account dashboards and set up a monitoring account that collects metrics from all workload accounts. Use this for centralized monitoring.

Trap 3: CloudWatch Logs Export to S3 is NOT Real-Time

The CreateExportTask API exports logs to S3 but is batch (can take up to 12 hours). For real-time log streaming, use CloudWatch Logs Subscription Filters → Kinesis Data Firehose → S3 (or directly to Lambda, OpenSearch).

CodePipeline, CodeBuild, CodeDeploy

AWS-native CI/CD pipeline
📚 Definition
  • CodePipeline: Orchestrates the CI/CD workflow. Connects source (CodeCommit, GitHub, S3, ECR) → build → test → deploy stages. Supports manual approval actions and cross-account deployments.
  • CodeBuild: Managed build service. Compiles code, runs tests, produces artifacts. Scales automatically. Uses buildspec.yml. Supports custom Docker images.
  • CodeDeploy: Automates deployments to EC2, Lambda, and ECS. Deployment strategies: In-place (EC2), Blue/Green (EC2, ECS), Canary/Linear/All-at-once (Lambda). Supports automatic rollback on failure.
⚠ SAP-C02 Exam Traps
Trap: Deployment Strategies

Blue/Green: Zero-downtime, instant rollback, full new environment. Canary: Small % of traffic to new version first. Rolling: Gradually replace instances. All-at-once: Fastest but riskiest. If the question says "zero downtime with instant rollback," the answer is Blue/Green.

Trap: Cross-Account Pipeline

CodePipeline can deploy to other accounts using cross-account IAM roles. The pipeline account assumes a role in the target account. Artifacts are shared via a cross-account S3 bucket with KMS encryption. This is a common multi-account CI/CD pattern.

Pilot Light: Only data replication is running (RDS read replica, Aurora Global). Compute is OFF. Scenario 1: A global e-commerce company needs to serve customers on 4 continents with sub-100ms latency. The application uses a relational database for orders and a shopping cart. The company wants active-active in 2 regions with automatic failover. How should they architect this?
Answer: Multi-region active-active architecture
Compute: ECS/Fargate in us-east-1 and eu-west-1 behind ALBs.
Database: DynamoDB Global Tables for shopping cart (active-active, sub-second replication). Aurora Global Database for orders (active-passive with write forwarding).
Caching: ElastiCache Redis in each region.
DNS: Route 53 latency-based routing to direct users to nearest region.
CDN: CloudFront for static assets.
Session: ElastiCache Redis or DynamoDB for session state (stateless app layer).
Failover: Route 53 health checks trigger failover. DynamoDB Global Tables auto-handle. Aurora secondary promoted in <1 min.
Scenario 2: A healthcare company is migrating 500 on-premises servers and 20 databases to AWS. They have 10 Gbps Direct Connect. Databases include Oracle (moving to Aurora PostgreSQL), MySQL (staying MySQL), and a 50 TB data warehouse (moving to Redshift). They need to maintain compliance (HIPAA) and minimize downtime. What migration approach?
Answer: Multi-tool migration strategy
Discovery: Migration Hub + Application Discovery Service to inventory servers and dependencies.
Servers (rehost): AWS MGN to lift-and-shift 500 servers to EC2 with continuous replication via DX.
Oracle → Aurora PostgreSQL: SCT for schema conversion + DMS with CDC for data migration with minimal downtime.
MySQL → Aurora MySQL: DMS only (homogeneous, no SCT needed).
Data warehouse → Redshift: SCT for schema + DMS or S3 staging with Snowball if DX bandwidth is insufficient for 50 TB.
Compliance: Encrypt everything with KMS CMKs. Enable CloudTrail, Config, GuardDuty. Use VPC endpoints for private access. S3 Object Lock for audit logs.
Tracking: Migration Hub dashboard for progress across all tools.
Scenario 3: A company suspects a developer account has been compromised. Unusual API calls from an unknown IP are appearing in CloudTrail. What should the security team do immediately?
Answer: Incident response playbook
Step 1 (Contain): Move the compromised account to the Suspended OU with a deny-all SCP. This immediately stops all API activity in the account.
Step 2 (Investigate): Review GuardDuty findings for the account. Check CloudTrail logs for the unknown IP — what actions were taken?
Step 3 (Eradicate): Rotate all IAM access keys and passwords in the account. Revoke any active IAM sessions. Check for persistence (new IAM users, roles, Lambda functions, EC2 instances).
Step 4 (Recover): Once clean, move the account back to its original OU. The SCP restrictions automatically lift.
Step 5 (Lessons): Enable IAM Access Analyzer, tighten permission boundaries, enable MFA enforcement via SCP.

Common Exam Traps

The 20 most frequently tested gotchas
  1. SCPs don't affect the management account — they only restrict member accounts.
  2. SCPs don't grant permissions — they are ceilings, not floors.
  3. VPC peering is not transitive — use Transit Gateway for transitive routing.
  4. NAT Gateway costs data processing fees — use VPC endpoints for S3/DynamoDB.
  5. Direct Connect is not encrypted — add VPN over DX or use MACsec for encryption.
  6. Gateway Endpoint works within VPC only — on-prem needs Interface Endpoint for S3.
  7. Multi-AZ is for HA, not read scaling — use Read Replicas for read scaling.
  8. Aurora Global Database ≠ cross-region read replica — different replication mechanisms.
  9. DynamoDB Global Tables are multi-active — reads AND writes in all regions.
  10. Lambda has a 15-minute timeout — longer workloads need ECS/Fargate or Step Functions.
  11. API Gateway has a 29-second timeout — use async patterns for long operations.
  12. S3 replication doesn't apply retroactively — use Batch Replication for existing objects.
  13. Object Lock Compliance mode = nobody can delete — not even root.
  14. KMS keys are regional — cross-region needs a key in the target region.
  15. CloudWatch doesn't collect memory/disk — needs CloudWatch Agent.
  16. CloudTrail data events cost extra — not logged by default.
  17. GuardDuty detects, doesn't prevent — pair with EventBridge + Lambda for remediation.
  18. Secrets Manager auto-rotates; Parameter Store doesn't — choose based on rotation needs.
  19. Security Groups allow only; NACLs allow + deny — block IPs with NACLs.
  20. Dedicated Host for BYOL; Dedicated Instance for compliance — different use cases.
