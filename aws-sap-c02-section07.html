1. Amazon SQS

Simple Queue Service is a fully managed message queuing service for decoupling and scaling microservices, distributed systems, and serverless applications.

SQS ARCHITECTURE Producer ──► SQS Queue ──► Consumer (EC2, Lambda, ECS) │ ├── Standard Queue │ • At-least-once delivery │ • Best-effort ordering │ • Nearly unlimited TPS │ └── FIFO Queue • Exactly-once processing • First-In-First-Out ordering • 3,000 messages/sec with batching • 300 messages/sec without batching Message Lifecycle: 1. Producer sends message (max 256 KB) 2. Message becomes "in flight" when consumer receives it 3. Consumer processes → deletes message 4. If NOT deleted within VisibilityTimeout → message reappears 5. After maxReceiveCount failures → message goes to DLQ

SQS Key Settings

SettingDescriptionExam Note
Visibility TimeoutTime consumer has to process before message reappears (0s–12hr, default 30s)Set > max processing time to avoid duplicate processing
Message Retention1 min to 14 days (default 4 days)Set max (14 days) for DR scenarios
Max Message Size256 KB (use S3 Extended Client Library for larger)Large payloads → store in S3, put S3 reference in SQS message
Delivery Delay0–900 seconds (15 min) per message or queue-wideDelay processing by set time
Long PollingWait up to 20 seconds for messages (reduces empty responses)Use long polling to reduce cost and false empty responses
Dead Letter Queue (DLQ)Queue for messages that fail processing N timesAlways set DLQ for production. Use DLQ Redrive to replay.

2. Amazon SNS

Simple Notification Service is a pub/sub messaging service for fan-out patterns — one message to multiple subscribers.

SNS FAN-OUT PATTERN Publisher → SNS Topic → Subscriptions ├── SQS Queue 1 (Email Service) ├── SQS Queue 2 (Order Service) ├── SQS Queue 3 (Inventory Service) ├── Lambda function (Real-time notification) ├── HTTP/HTTPS endpoint (webhook) ├── Email (direct email notification) └── SMS (mobile phone) Fan-out use case: Order placed → SNS → SQS (Payment) + SQS (Warehouse) + Lambda (Notification) All happen independently, decoupled, no dependencies between consumers

SNS Key Features

  • Max message size: 256 KB (use S3 for larger payloads)
  • FIFO Topics: For ordered delivery to SQS FIFO queues
  • Message Filtering: Subscribers can filter messages by attributes — only receive relevant messages
  • Dead Letter Queue: Can set DLQ for failed deliveries (Lambda/SQS/HTTP subscriptions)
  • Message archiving: Not built-in (use SQS DLQ or S3 subscription for persistence)
  • Cross-region delivery: SNS can deliver to SQS queues in different regions
SNS vs SQS: SNS = push (publish once, notify many). SQS = pull (consumer polls for messages). SNS does NOT store messages. For persistence, subscribe SQS to SNS (fan-out pattern).

3. Amazon EventBridge

EventBridge is a serverless event bus that makes it easy to build event-driven architectures. It connects AWS services, SaaS applications, and custom applications.

EVENTBRIDGE ARCHITECTURE Event Sources: AWS Services (EC2, S3, ECS, Lambda, etc.) SaaS Partners (Zendesk, Datadog, PagerDuty, Stripe) Custom Applications (PutEvents API) │ ▼ ┌─────────────────────────────────────────────┐ │ EVENT BUS │ │ Default Bus: AWS service events │ │ Partner Bus: SaaS partner events │ │ Custom Bus: Your app events │ └──────────────────┬──────────────────────────┘ │ RULES (filter events) Pattern matching: service, event type, detail │ ┌─────────┼─────────────────┐ │ │ │ Lambda SQS Step Functions ECS Task SNS API Gateway EventBridge Bus (cross-acct)

4. Amazon MQ

Amazon MQ is a managed message broker service for Apache ActiveMQ and RabbitMQ. Use it when migrating from on-premises message brokers with AMQP, MQTT, STOMP, OpenWire, WSS protocols.

Amazon MQ vs SQS/SNS: New cloud-native apps → SQS/SNS (simpler, more scalable, cheaper). Migrating from on-premises ActiveMQ/RabbitMQ/JMS apps → Amazon MQ (protocol compatibility, minimal code change).

5. AWS Step Functions

Step Functions is a serverless workflow orchestration service for coordinating multiple AWS services into business processes.

STEP FUNCTIONS WORKFLOW EXAMPLE: Order Processing Order Received │ ▼ [Validate Order]──FAIL──► [Send Failure Notification] │ SUCCESS ▼ [Charge Payment]──FAIL──► [Refund & Notify] │ SUCCESS ▼ [Reserve Inventory] │ ▼ ├── PARALLEL │ ├── [Update ERP System] │ └── [Send Confirmation Email] │ ▼ [Ship Order] │ ▼ [Order Complete] State Types: • Task: Call Lambda, ECS, SQS, Batch, etc. • Choice: Conditional branching • Parallel: Execute branches simultaneously • Map: Process each item in array • Wait: Pause for time or event • Pass: Pass input to output unchanged • Succeed/Fail: Terminal states

6. API Gateway

Amazon API Gateway is a fully managed service to create, publish, maintain, monitor, and secure APIs at any scale.

API Gateway Types

TypeProtocolUse Case
REST APIHTTP/HTTPSTraditional REST APIs, full feature set, caching, usage plans
HTTP APIHTTP/HTTPSLower latency, lower cost (up to 71%), OIDC/JWT auth, simpler
WebSocket APIWebSocketReal-time two-way communication (chat, gaming, live dashboards)

API Gateway Key Features

  • Caching: Cache responses up to 1 hour — reduces backend calls
  • Throttling: Account-level (10,000 rps), stage-level, usage plan-level
  • Usage Plans + API Keys: Rate limit and quota individual customers
  • Lambda Authorizer: Custom auth logic in Lambda function (validate JWT, call database)
  • Cognito Authorizer: Validates Cognito User Pool JWTs
  • VPC Link: Connect API Gateway to private resources in VPC (NLB → private EC2/ECS)
  • Stage Variables: Configuration per stage (dev, prod) — like environment variables
  • Canary deployments: Route % of traffic to new stage version

7. Event-Driven Architecture Patterns

PATTERN 1: SAGA PATTERN (Distributed Transactions) Order Service → [Place Order] → SQS → Payment Service │ Success → SQS → Inventory Service │ Failure → SQS → Compensation (Cancel Order) Step Functions choreographs the saga workflow. Each service publishes success/failure events. Compensating transactions roll back on failure. PATTERN 2: EVENT SOURCING User Actions → EventBridge → SQS → Event Store (DynamoDB) │ Event Bus → Multiple Projections │ (Read models) ├── Search Index (OpenSearch) └── Analytics (Kinesis → Redshift) PATTERN 3: CQRS (Command Query Responsibility Segregation) Write Path: API → Lambda → DynamoDB (Command) │ Stream ▼ Read Path: API → Lambda → ElastiCache (Query, pre-built read models)

Real-World: E-Commerce Event-Driven Architecture

Customer Places Order │ ▼ API Gateway → Lambda (validate) → EventBridge │ ┌────────────────────┼─────────────────────┐ │ │ │ SQS Queue SQS Queue SQS Queue (Payment Svc) (Warehouse Svc) (Email Service) │ │ │ Lambda Fn Lambda Fn Lambda Fn (charge card) (reserve item) (send email) │ DynamoDB → Streams → Lambda → EventBridge │ Step Functions (shipping workflow)

CLI — Create SQS Queue with DLQ

# Create DLQ first
aws sqs create-queue \
  --queue-name order-processing-dlq \
  --attributes MessageRetentionPeriod=1209600

DLQ_ARN=$(aws sqs get-queue-attributes \
  --queue-url https://sqs.us-east-1.amazonaws.com/123/order-processing-dlq \
  --attribute-names QueueArn \
  --query 'Attributes.QueueArn' --output text)

# Create main queue with DLQ
aws sqs create-queue \
  --queue-name order-processing \
  --attributes '{
    "VisibilityTimeout": "300",
    "MessageRetentionPeriod": "86400",
    "ReceiveMessageWaitTimeSeconds": "20",
    "RedrivePolicy": "{\"deadLetterTargetArn\":\"'$DLQ_ARN'\",\"maxReceiveCount\":\"3\"}"
  }'

# Create EventBridge rule
aws events put-rule \
  --name OrderCreatedRule \
  --event-pattern '{"source":["myapp.orders"],"detail-type":["OrderCreated"]}' \
  --state ENABLED

# Add Lambda target to rule
aws events put-targets \
  --rule OrderCreatedRule \
  --targets 'Id=1,Arn=arn:aws:lambda:us-east-1:123:function:process-order'

Terraform — SNS + SQS Fan-Out

resource "aws_sns_topic" "orders" {
  name = "order-events"
}

resource "aws_sqs_queue" "payment" {
  name                       = "payment-queue"
  visibility_timeout_seconds  = 300
  message_retention_seconds   = 86400
  receive_wait_time_seconds   = 20
  redrive_policy = jsonencode({
    deadLetterTargetArn = aws_sqs_queue.payment_dlq.arn
    maxReceiveCount     = 3
  })
}

resource "aws_sqs_queue" "payment_dlq" {
  name                      = "payment-dlq"
  message_retention_seconds = 1209600
}

resource "aws_sns_topic_subscription" "payment_sub" {
  topic_arn = aws_sns_topic.orders.arn
  protocol  = "sqs"
  endpoint  = aws_sqs_queue.payment.arn
  filter_policy = jsonencode({
    eventType = ["OrderCreated", "OrderUpdated"]
  })
}

# Allow SNS to send to SQS
resource "aws_sqs_queue_policy" "payment" {
  queue_url = aws_sqs_queue.payment.id
  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Effect    = "Allow"
      Principal = { Service = "sns.amazonaws.com" }
      Action    = "sqs:SendMessage"
      Resource  = aws_sqs_queue.payment.arn
      Condition = {
        ArnEquals = { "aws:SourceArn" = aws_sns_topic.orders.arn }
      }
    }]
  })
}

8. Exam Tips & Cheat Sheet

SAP-C02 Application Integration — Critical Points

  • SQS FIFO: Exactly-once processing, ordered. Max 3,000 msg/sec. Queue name ends in .fifo.
  • SQS Visibility Timeout: Must be longer than your processing time to avoid duplicate processing.
  • Long polling: Set ReceiveMessageWaitTimeSeconds = 20 to reduce empty responses and cost.
  • SNS fan-out: Send to SQS queues from one SNS topic. SQS provides durability (SNS doesn't store).
  • EventBridge vs SNS: EventBridge for AWS service events, SaaS, complex filtering, schema registry. SNS for simple pub/sub fan-out.
  • Amazon MQ: Only when existing on-prem JMS/AMQP/MQTT code must work unchanged.
  • Step Functions Standard: Long-running (1 year), exactly-once, human approval tasks.
  • Step Functions Express: High-rate (100k/sec), 5-minute max, IoT/streaming.
  • API Gateway REST vs HTTP: HTTP API = 71% cheaper, lower latency. REST API = more features (caching, usage plans, full request transformation).
  • API Gateway Throttling: 10,000 rps default account limit, 5,000 burst. Can request increase.
  • VPC Link: Use when API Gateway needs to reach private resources (NLB in VPC).
Message Service Selection
  • Decoupling: SQS (pull model)
  • Fan-out/notify: SNS (push)
  • Complex event routing: EventBridge
  • JMS/AMQP legacy: Amazon MQ
  • Workflow orchestration: Step Functions
SQS Critical Settings
  • Standard: unlimited TPS, at-least-once
  • FIFO: 3000/sec, exactly-once
  • Visibility timeout: 0s–12hrs
  • Retention: 1min–14days
  • Long poll: up to 20 seconds
  • DLQ: after maxReceiveCount failures
EventBridge Patterns
  • Schedule: cron/rate expressions
  • Pattern: filter by event source/type
  • Pipe: point-to-point enrichment
  • Archive: store events, replay later
  • Cross-acct: resource-based policy
API Gateway Auth
  • IAM auth: AWS SigV4
  • Cognito: JWT from User Pool
  • Lambda Authorizer: custom logic
  • API Key: throttling/quota only
  • Resource policy: IP/VPC restriction
