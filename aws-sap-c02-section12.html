1. Multi-Region Architecture

GLOBAL MULTI-REGION APPLICATION ARCHITECTURE Users (global) │ ▼ Route 53 (Latency routing) │ ├── us-east-1 (primary, 60% traffic) │ ├── CloudFront → WAF → ALB │ ├── ECS Fargate (Auto Scaling) │ ├── Aurora Global Primary (R/W) │ ├── DynamoDB Global Table │ ├── ElastiCache Redis │ └── S3 with CRR → eu-west-1 │ └── eu-west-1 (secondary, 40% EU traffic) ├── CloudFront → WAF → ALB ├── ECS Fargate (Auto Scaling) ├── Aurora Global Secondary (Read) ├── DynamoDB Global Table (local R/W) ├── ElastiCache Redis └── S3 replica Shared Services (us-east-1): ├── IAM Identity Center (global) ├── Route 53 Private Hosted Zones └── Transit Gateway (hub)

Multi-Region Design Considerations

  • Data consistency: DynamoDB Global Tables = multi-active, eventually consistent. Aurora Global = active-passive, consistent.
  • Session state: Use DynamoDB or ElastiCache for distributed session (not local memory)
  • DNS TTL: Low TTL (30-60s) for faster failover. Higher TTL reduces DNS query load.
  • Cost: Inter-region data transfer charges apply. Design to minimize cross-region data movement.
  • Compliance: Data sovereignty laws may restrict where data can be stored. Use SCPs to prevent data leaving approved regions.

3. SaaS Multi-Tenant Architecture

SAAS MULTI-TENANT PATTERNS SILO MODEL (Separate stack per tenant): Tenant A: VPC-A, RDS-A, ECS-A, S3-A Tenant B: VPC-B, RDS-B, ECS-B, S3-B Pros: Strong isolation, per-tenant customization Cons: Expensive, harder to manage at scale POOL MODEL (Shared infrastructure): All tenants → Single ECS cluster → Shared Aurora Tenant isolation: Row-level security (tenant_id column) Pros: Cost-efficient, easier updates Cons: Noisy neighbor risk, shared blast radius BRIDGE MODEL (Hybrid): Shared: ALB, ECS, Lambda, API Gateway, SQS Isolated: Per-tenant DynamoDB tables or RDS schemas Tenant routing: JWT claim → tenant_id → data isolation TYPICAL ENTERPRISE SAAS STACK: Route 53 → CloudFront → API Gateway → ALB → ECS Fargate (tenant-aware application) → DynamoDB (tenant_id as partition key) → S3 (prefix per tenant: s3://bucket/tenant-id/...) → Cognito User Pools (per-tenant or pooled) → KMS (per-tenant CMK for data encryption)

9. Exam Tips

SAP-C02 Advanced Architecture — Key Points

  • Multi-Region DB: Active/Active writes → DynamoDB Global Tables. Active/Passive → Aurora Global.
  • SaaS isolation: Silo = separate stack (expensive but isolated). Pool = shared (cheaper, noisy neighbor). Bridge = hybrid.
  • Serverless cost: Pay per request, zero when idle. Best for event-driven, variable traffic.
  • IRSA (IAM Roles for Service Accounts): Pod-level AWS credentials in EKS — not instance profile.
  • Lake Formation: Column/row level security on data lake. Controls Athena and Redshift Spectrum access.
  • Kinesis vs SQS: Kinesis = ordered streaming, replay, multiple consumers. SQS = queue, one consumer per message.
  • AppFlow: No-code integration for SaaS to S3/Redshift (Salesforce, ServiceNow, etc.).
  • Global Accelerator vs CloudFront: GA = TCP/UDP, static IPs. CF = HTTP/HTTPS, caching.
  • Glue vs EMR: Glue = serverless Spark ETL (simpler). EMR = managed Hadoop/Spark cluster (more control, larger workloads).
