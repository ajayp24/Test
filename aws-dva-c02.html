Expect 15–20 questions directly or indirectly about Lambda.

⚡

AWS Lambda

Run code without provisioning or managing servers
📚 Definition

AWS Lambda is a serverless, event-driven compute service that lets you run code for virtually any type of application or backend service without provisioning or managing servers. You upload your code as a deployment package (zip file or container image up to 10 GB), configure a trigger, and Lambda automatically runs your code in response to events. You pay only for the compute time consumed — billed per millisecond in 1ms increments.

Lambda supports runtimes for Node.js, Python, Java, .NET, Go, Ruby, and custom runtimes via the Runtime API. Each function execution runs in an isolated execution environment (a micro VM powered by Firecracker). Lambda manages all the compute infrastructure including server and OS maintenance, capacity provisioning, auto-scaling, logging, and monitoring.

💡 Key Concepts for the Exam
  • Handler: The method in your code that Lambda calls to begin execution. Format: filename.method_name (e.g., index.handler).
  • Execution Role: An IAM role that grants the Lambda function permissions to access AWS services and resources. This is the most common exam question pattern.
  • Timeout: Maximum execution time. Default 3 seconds, max 15 minutes (900 seconds). If your function exceeds this, it is terminated.
  • Memory: 128 MB to 10,240 MB (10 GB) in 1 MB increments. CPU scales proportionally with memory — more memory = more CPU = faster execution.
  • Ephemeral storage (/tmp): 512 MB to 10,240 MB. Persists across warm invocations of the same execution environment.
  • Environment Variables: Key-value pairs available to your function code at runtime. Can be encrypted with KMS. Max 4 KB total.
  • Deployment package: Zip upload max 50 MB compressed / 250 MB uncompressed. Container image max 10 GB.
  • Invocation types: Synchronous (RequestResponse), Asynchronous (Event), and Event Source Mapping (polling).
💻 Invocation Models (Critical for Exam)
Synchronous Invocation (RequestResponse)

Caller waits for the response. If Lambda fails, the caller must handle retries. No built-in retry.

Triggers: API Gateway, ALB, CloudFront (Lambda@Edge), Cognito, Alexa, Lex, SDK direct invoke.

Asynchronous Invocation (Event)

Caller gets 202 immediately. Lambda handles retries: 2 automatic retries (total 3 attempts). Events go to an internal queue. On failure after all retries, send to a Dead Letter Queue (DLQ) or Destination.

Triggers: S3, SNS, EventBridge, CloudWatch Events, CodeCommit, CodePipeline, CloudFormation, Config, IoT, SES.

Event Source Mapping (Poll-Based)

Lambda polls the source. Used for stream/queue-based sources. Lambda reads records in batches.

Triggers: SQS, SQS FIFO, Kinesis Data Streams, DynamoDB Streams, Amazon MQ, MSK, self-managed Kafka.

Key difference for SQS: Lambda deletes the message from the queue after successful processing. On failure, message becomes visible again after the visibility timeout expires.

Key difference for Streams (Kinesis/DynamoDB): On failure, the entire batch is retried (blocks the shard). Use BisectBatchOnFunctionError to split failed batches, or configure MaximumRetryAttempts and DestinationConfig for failures.

⚠ DVA-C02 Exam Traps
Trap 1: Execution Role vs Resource-Based Policy

The execution role controls what the Lambda function can do (e.g., write to DynamoDB). The resource-based policy controls who can invoke the function (e.g., allowing API Gateway or S3 to trigger it). The exam loves asking which one to modify when adding a new trigger vs. accessing a new service.

Trap 2: DLQ vs Destinations

DLQ (Dead Letter Queue) only captures failed async invocations and only supports SQS or SNS as targets. Destinations (newer, recommended) capture both success and failure outcomes and support SQS, SNS, Lambda, and EventBridge as targets. The exam prefers Destinations for new architectures.

Trap 3: Environment Variables are NOT Encrypted by Default at Rest

Lambda environment variables are encrypted at rest using an AWS-managed KMS key by default. But if you need encryption helpers (encrypt values before they reach Lambda), you must use a customer-managed KMS key and encrypt/decrypt in code. The exam tests whether you know the difference between "at rest encryption" (automatic) and "in transit to the function" (requires extra KMS steps).

Trap 4: Timeout Errors Are Not Retried for Sync Invocations

When Lambda is invoked synchronously (e.g., via API Gateway) and times out, the caller gets a 504 error. Lambda does NOT retry. The client/caller must retry. This is a common exam scenario: "function timing out behind API Gateway" → increase timeout or optimize code, NOT add a DLQ.

Trap 5: /tmp Is Shared Across Warm Invocations

The /tmp directory persists between invocations in the same execution environment (warm start). This means cached data from a previous invocation may still be there. Great for caching, but be careful about stale data. The exam tests whether you understand this warm-start behavior.

🔬 Example Scenario
A developer has a Lambda function that processes images uploaded to S3. The function occasionally fails due to transient errors. The developer wants failed events to be captured for later analysis without losing any data. What should the developer do?
Answer: Configure a Lambda Destination for the OnFailure condition pointing to an SQS queue
S3 → Lambda is an asynchronous invocation. Lambda automatically retries twice on failure. After all retries are exhausted, a Destination (preferred over DLQ) captures the failure event with full context (request payload, error info, stack trace) and sends it to SQS for later analysis. Destinations are the modern best practice over DLQs because they capture richer metadata and support success callbacks too.

Lambda Layers

Package and share libraries, custom runtimes, and dependencies
📚 Definition

A Lambda Layer is a .zip archive that contains supplementary code (libraries, dependencies, custom runtimes, or configuration files). Layers are extracted to the /opt directory in the execution environment. A function can use up to 5 layers at a time. The total unzipped deployment package size (function code + all layers) cannot exceed 250 MB.

✅ When to Use
  • Shared dependencies: Common libraries (e.g., AWS SDK, pandas, Pillow) used across multiple functions.
  • Custom runtimes: Package a runtime for a language not natively supported by Lambda.
  • Reduce deployment size: Keep function code small; heavy dependencies go in layers.
  • Separation of concerns: Update libraries independently of function code.
⚠ Exam Traps
Layers are versioned and immutable

Each time you publish a layer, you get a new version number. You cannot update a version in place. When you update a layer, functions using the old version are NOT automatically updated — you must update the function configuration to point to the new layer version.

Max 5 layers per function

If asked about a function already using 5 layers needing another dependency, the answer is to merge layers or include the dependency in the deployment package.

Lambda Concurrency & Scaling

Reserved concurrency, provisioned concurrency, and burst limits
📚 Key Concepts
  • Concurrency: The number of function instances serving requests at a given time. Each concurrent execution = 1 execution environment.
  • Account-level default: 1,000 concurrent executions per region (soft limit, can be increased).
  • Unreserved concurrency: The pool shared by all functions without reserved concurrency. AWS keeps a minimum of 100 unreserved for other functions.
  • Reserved concurrency: Guarantees a maximum number of concurrent instances for a function AND throttles it beyond that limit. It reserves from the account pool. Setting reserved concurrency to 0 disables the function (throttles all invocations).
  • Provisioned concurrency: Pre-initializes a requested number of execution environments so they are warm and ready to respond immediately. Eliminates cold starts. Costs money even when idle. Can be configured on a Lambda alias or version (NOT on $LATEST).

⚠ Exam Traps
Reserved Concurrency = Throttle + Guarantee

Setting reserved concurrency to 200 means the function can never exceed 200 concurrent executions (throttling), but it also guarantees 200 from the account pool that other functions cannot consume. This is a two-edged sword — the exam tests both sides.

Provisioned Concurrency Cannot Be Set on $LATEST

You MUST publish a version or create an alias and then configure provisioned concurrency on it. The exam may offer "$LATEST with provisioned concurrency" as a distractor — this is always wrong.

Throttling Returns 429 (TooManyRequestsException)

For sync invocations: caller gets 429. For async invocations: Lambda retries throttled events for up to 6 hours, then sends to DLQ/destination. For event source mappings (SQS): messages return to the queue.

Lambda in VPC

Access private resources like RDS and ElastiCache from Lambda
📚 How It Works

By default, Lambda runs in an AWS-managed VPC with internet access but no access to your private resources (RDS, ElastiCache, etc.). When you configure Lambda to connect to your VPC, it creates an Elastic Network Interface (ENI) in your specified subnets using Hyperplane (shared ENI technology).

  • Lambda in VPC = no internet access by default. To access the internet, you need a NAT Gateway in a public subnet + route table configuration.
  • Lambda needs the execution role permissions: ec2:CreateNetworkInterface, ec2:DescribeNetworkInterfaces, ec2:DeleteNetworkInterface (provided by AWSLambdaVPCAccessExecutionRole).
  • For accessing AWS services (DynamoDB, S3, SQS) from VPC-connected Lambda without internet: use VPC Endpoints (Gateway endpoints for S3/DynamoDB, Interface endpoints for others).
⚠ Critical Exam Trap
Lambda in VPC Cannot Reach Internet or Public AWS Endpoints

This is the #1 most tested Lambda networking question. "Developer puts Lambda in a VPC to access RDS, but now the function can't reach DynamoDB/S3/external API." The fix is either: (1) Add a NAT Gateway for internet access, or (2) Add VPC Endpoints for specific AWS services. NEVER put Lambda in a public subnet with an IGW — Lambda doesn't get a public IP even in a public subnet.

Lambda Event Source Mappings

Poll-based triggers for SQS, Kinesis, and DynamoDB Streams
📚 How It Works

An event source mapping is a Lambda resource that reads from a stream or queue and invokes your function with batches of records. Lambda manages the polling infrastructure. The function's execution role must have permissions to read from the source.

SourceBatch BehaviorOn FailureOrdering
SQS Standard Up to 10,000 msgs/batch, long polling Message returns to queue after visibility timeout No ordering guarantee
SQS FIFO Up to 10 msgs/batch per message group Blocks the message group until resolved Strict FIFO per message group
Kinesis Data Streams Up to 10,000 records or 6MB per batch Retries entire batch, blocks shard Ordered within shard
DynamoDB Streams Up to 10,000 records per batch Retries entire batch, blocks shard Ordered within partition key
⚠ Stream Error Handling (Very Common on Exam)
Stream Failure = Shard Blocked

When a Lambda function fails processing a batch from Kinesis or DynamoDB Streams, the entire shard is blocked — no new records are processed from that shard until the batch succeeds or ages out. Solutions:

  • BisectBatchOnFunctionError: Splits the failed batch in half and retries each half, helping isolate the bad record.
  • MaximumRetryAttempts: Limit retries (default is infinite for streams). After exhausting retries, the batch is discarded or sent to a destination.
  • MaximumRecordAgeInSeconds: Skip records older than this age.
  • DestinationConfig (OnFailure): Send failed event metadata to SQS or SNS for later analysis.
⚠ SQS + Lambda Trap
Visibility Timeout Must Be 6x Lambda Timeout

AWS recommends setting the SQS queue's visibility timeout to at least 6 times the Lambda function timeout. If the visibility timeout is too short, the message becomes visible again while Lambda is still processing it, causing duplicate processing. This is a high-frequency exam question.

🏗 Integration Types
  • Lambda Proxy (AWS_PROXY): Most common. API Gateway passes the entire HTTP request as a JSON event to Lambda. Lambda must return a specific response format (statusCode, headers, body). No mapping templates.
  • Lambda Custom (AWS): API Gateway applies mapping templates (VTL — Velocity Template Language) to transform request/response. More control but more complex.
  • HTTP Proxy (HTTP_PROXY): Passes request to an HTTP backend directly.
  • HTTP Custom (HTTP): HTTP backend with mapping templates for request/response transformation.
  • AWS Service (AWS): Direct integration with AWS services (e.g., put message to SQS, write to DynamoDB) without Lambda. Uses mapping templates.
  • Mock: Returns a response without sending the request to any backend. Useful for testing and CORS preflight.
Exam Tip: Lambda Proxy vs Custom

If the question mentions mapping templates or request/response transformation, it's using custom integration (AWS type). If the question says "pass the request directly to Lambda," it's proxy integration (AWS_PROXY). Proxy integration is the default and most commonly used.

⚠ DVA-C02 Exam Traps
Trap 1: API Gateway Timeout is 29 Seconds Max

The maximum integration timeout for API Gateway is 29 seconds. Even though Lambda can run for 15 minutes, if invoked through API Gateway, the response must return within 29 seconds or the client gets a 504 Gateway Timeout. For long-running tasks, return 202 immediately and process asynchronously.

Trap 2: CORS Must Be Enabled Explicitly

If a browser-based app calls your API and gets a CORS error, you need to enable CORS on the API Gateway. For Lambda proxy integration, you must also return CORS headers from your Lambda function (Access-Control-Allow-Origin, etc.) because proxy integration passes headers through unchanged.

Trap 3: Caching Is REST API Only

HTTP API does NOT support response caching. If the question requires API-level caching, the answer must use REST API, not HTTP API.

Trap 4: 10 MB Payload Limit

API Gateway has a 10 MB maximum payload size. For larger payloads, use S3 pre-signed URLs to upload/download directly.

Trap 5: Throttling Limits

Default: 10,000 requests per second per region (account level), with a burst of 5,000. Per-method throttling can be configured via Usage Plans. Exceeding the limit returns 429 Too Many Requests.

API Gateway Stages, Deployments & Canary

Version and deploy APIs safely with stage variables and canary releases
📚 Key Concepts
  • Deployment: A snapshot of the API configuration. Changes to the API do NOT take effect until you create a new deployment.
  • Stage: A named reference to a deployment (e.g., dev, staging, prod). Each stage has its own URL: https://{api-id}.execute-api.{region}.amazonaws.com/{stage}.
  • Stage Variables: Key-value pairs associated with a stage. Act like environment variables. Common use: point to different Lambda aliases per stage (e.g., stageVariables.lambdaAlias → dev points to DEV alias, prod points to PROD alias).
  • Canary Deployment: Split traffic between the current deployment and a new canary deployment. Configure what percentage of traffic goes to the canary (e.g., 10%). If the canary is healthy, promote it to replace the current deployment.

API Gateway Caching & Throttling

Reduce backend calls and protect against overload
📚 Caching (REST API Only)
  • Cache capacity: 0.5 GB to 237 GB. TTL default 300 seconds, max 3600s.
  • Caching is per stage. Can be overridden per method.
  • Cache invalidation: Client sends Cache-Control: max-age=0 header. You can require authorization for cache invalidation.
  • Cache key: By default, the full request URL. Can customize to include headers, query strings, or path parameters as cache keys.
  • Costs extra — the cache is a dedicated resource.
📚 Throttling
  • Account-level: 10,000 RPS across all APIs in a region (soft limit). Burst: 5,000.
  • Usage Plans + API Keys: Throttle per-client. Create a usage plan that defines throttle rate and burst limits, associate API keys with the plan, and require API key on methods.
  • When throttled: returns 429 Too Many Requests.
  • API keys are for identification and throttling, NOT for authentication. Never use API keys as the sole auth mechanism.
Exam Trap: API Keys Are Not Security

DynamoDB

DynamoDB is the second most important service on the DVA-C02 exam after Lambda. You must understand partition keys, sort keys, indexes (LSI vs GSI), capacity modes, streams, DAX, transactions, TTL, and optimistic locking with conditional writes.

🗃

Amazon DynamoDB

Fully managed, serverless, key-value and document NoSQL database
📚 Core Concepts
  • Table: A collection of items. No fixed schema beyond the primary key.
  • Item: A single record (like a row). Maximum size 400 KB.
  • Attribute: A data element on an item (like a column, but flexible per item).
  • Primary Key: Two types:
    • Partition Key (PK) only: Must be unique per item. DynamoDB uses the PK to determine the physical partition.
    • Partition Key + Sort Key (PK + SK): Composite key. The combination must be unique. Allows multiple items with the same PK but different SK. Enables range queries on the sort key.
  • Capacity Modes:
    • Provisioned: You specify Read Capacity Units (RCU) and Write Capacity Units (WCU). Can use Auto Scaling. Cheaper for predictable workloads.
    • On-Demand: Pay per request. No capacity planning. Up to 2.5x more expensive per request but ideal for unpredictable or spiky workloads.
💻 Read/Write Capacity Units (Must Memorize)
RCU Calculation
  • Strongly Consistent Read: 1 RCU = 1 read of up to 4 KB per second.
  • Eventually Consistent Read: 1 RCU = 2 reads of up to 4 KB per second (half the cost).
  • Transactional Read: 1 RCU = 0.5 reads of up to 4 KB per second (double the cost).

Formula: Round up item size to nearest 4 KB multiple, then divide by 4 KB, multiply by reads/second, and adjust for consistency mode.

WCU Calculation
  • Standard Write: 1 WCU = 1 write of up to 1 KB per second.
  • Transactional Write: 1 WCU = 0.5 writes of up to 1 KB per second (double the cost).

Formula: Round up item size to nearest 1 KB, multiply by writes/second, double for transactions.

⚠ DVA-C02 Exam Traps
Trap 1: Hot Partition / Throttling

If one partition key is accessed much more than others, that partition gets throttled even if the table has enough overall capacity. Solution: Design the partition key for high cardinality (e.g., user_id, not status). For write-heavy workloads, consider adding a random suffix to the PK (write sharding).

Trap 2: Query vs Scan

The exam will present scenarios where a developer uses Scan to find items and asks how to improve performance. The answer is almost always to redesign the data model (add a GSI or change the PK/SK design) to allow Query instead of Scan.

Trap 3: FilterExpression Does NOT Reduce RCU Cost

A FilterExpression on a Query or Scan is applied after the data is read from the table. You still consume RCUs for all items read, even those filtered out. To reduce RCU consumption, you need to narrow the Query using key conditions, not FilterExpression.

Trap 4: 400 KB Item Size Limit

Each DynamoDB item can be at most 400 KB. This includes attribute names and values. For large objects, store the data in S3 and keep only a pointer (S3 URL) in DynamoDB.

Trap 5: Optimistic Locking with Condition Expressions

DynamoDB supports optimistic concurrency control using condition expressions on writes. Add a version number attribute; before updating, check that the version hasn't changed: ConditionExpression: "version = :expected_version". If another writer changed the version, the write fails with ConditionalCheckFailedException.

🔬 Example Scenario
A developer's application needs to read 80 items per second from a DynamoDB table. Each item is 6 KB. The application can tolerate eventually consistent reads. How many RCUs are needed?
Answer: 80 RCUs
Item size: 6 KB → round up to next 4 KB multiple = 8 KB → 8 / 4 = 2 RCUs per item for strongly consistent.
Eventually consistent = half the RCUs = 1 RCU per item.
80 items/sec × 1 RCU = 80 RCUs.

⚠ GSI Throttling Trap

If a GSI's WCU is under-provisioned, writes to the GSI throttle, which causes writes to the base table to throttle as well (because DynamoDB needs to propagate the write to the GSI). Always ensure GSI WCU is adequate for the write throughput. This is a very common exam scenario.

DynamoDB Streams

Capture table changes and trigger real-time processing
📚 Definition

DynamoDB Streams captures a time-ordered sequence of item-level changes (INSERT, MODIFY, DELETE) in a DynamoDB table. Records are stored for 24 hours. You configure the StreamViewType to control what data is captured:

  • KEYS_ONLY: Only the key attributes of the modified item.
  • NEW_IMAGE: The entire item as it appears after the change.
  • OLD_IMAGE: The entire item as it appeared before the change.
  • NEW_AND_OLD_IMAGES: Both old and new versions of the item.

Common use cases: trigger Lambda on data changes (event-driven architectures), replicate data across tables, maintain materialized views, send notifications, audit/compliance logging.

⚠ Exam Trap
Streams + Lambda = Event Source Mapping

Lambda polls DynamoDB Streams using an event source mapping. The Lambda execution role needs dynamodb:GetRecords, dynamodb:GetShardIterator, dynamodb:DescribeStream, dynamodb:ListStreams. On failure, the batch blocks the shard (same behavior as Kinesis). Use BisectBatchOnFunctionError, MaximumRetryAttempts, and OnFailure destination.

DynamoDB Advanced Features

TTL, Transactions, Global Tables, PartiQL, and Conditional Writes
📚 Key Features
  • TTL (Time-to-Live): Automatically deletes expired items at no WCU cost. Set a TTL attribute containing a Unix epoch timestamp. DynamoDB deletes the item within 48 hours after expiry (not instantaneous). Deleted items also appear in DynamoDB Streams (with a system marker). Common use: expire sessions, temporary data, soft deletes.
  • Transactions: TransactWriteItems and TransactGetItems provide ACID transactions across up to 100 items in up to 100 tables. All-or-nothing. Uses 2x the WCU/RCU of standard operations. Use cases: financial transactions, inventory management, any "transfer from A to B" pattern.
  • Global Tables: Multi-region, multi-active (active-active) replication. Tables are replicated across chosen regions. Writes in any region propagate automatically. Requires DynamoDB Streams enabled. Conflict resolution: last writer wins.
  • PartiQL: SQL-compatible query language for DynamoDB. Can use SELECT, INSERT, UPDATE, DELETE syntax. Available in the console and SDK. Under the hood, it translates to DynamoDB API calls.
  • Conditional Writes: Add ConditionExpression to PutItem/UpdateItem/DeleteItem to write only if a condition is met. Enables optimistic locking. If the condition fails: ConditionalCheckFailedException.

📦

Amazon S3

Object storage built to retrieve any amount of data from anywhere
📚 Key Facts for the Exam
  • Object size: 0 bytes to 5 TB. Single PUT max 5 GB. Use multipart upload for objects > 100 MB (required for > 5 GB).
  • Bucket names: Globally unique, 3-63 characters, no uppercase, no underscores, must start with letter/number.
  • Key: The full path of the object (e.g., photos/2024/sunset.jpg). S3 is a flat namespace; "folders" are just prefixes.
  • Versioning: Enabled per bucket. Once enabled, cannot be disabled (only suspended). Each version has a unique Version ID. Deleting a versioned object creates a delete marker (soft delete).
  • Storage Classes: Standard, Standard-IA, One Zone-IA, Glacier Instant Retrieval, Glacier Flexible Retrieval, Glacier Deep Archive, Intelligent-Tiering.
  • Consistency: S3 provides strong read-after-write consistency for all operations (since December 2020). All reads immediately reflect the latest write.

S3 Security

Bucket policies, IAM policies, encryption, access points
📚 Access Control
  • Bucket Policy: JSON resource-based policy attached to the bucket. Controls access for IAM users, IAM roles, other AWS accounts, and public access. Most common way to manage S3 access.
  • IAM Policy: Attached to IAM users/roles. Controls what S3 actions the identity can perform. Use when managing access for specific IAM entities.
  • ACLs: Legacy mechanism. Disabled by default for new buckets (bucket owner enforced). Avoid using unless you need cross-account object-level access in specific legacy scenarios.
  • S3 Access Points: Named network endpoints with their own access policies. Simplify managing access for shared datasets. Each access point has its own DNS name and policy.
  • Block Public Access: Account-level and bucket-level settings to prevent public access. Overrides any bucket policy or ACL that would grant public access. Enabled by default for new buckets.

S3 Pre-Signed URLs & Pre-Signed POST

Grant temporary access to private objects without changing permissions
📚 How It Works
  • A pre-signed URL grants temporary permission to download (GET) or upload (PUT) an S3 object. The URL includes the credentials of the IAM entity that generated it.
  • Expiration: Default 3,600 seconds (1 hour). Max depends on the signer:
    • IAM instance profile credentials: up to 6 hours.
    • STS temporary credentials: up to 36 hours.
    • IAM user credentials: up to 7 days (168 hours).
  • Pre-Signed POST: Used for browser-based uploads. Returns a POST policy and form fields. The client POSTs the file directly to S3 with the signed form data. More secure for web apps as it allows server-side control over upload conditions (size limits, content type, key prefix).

Decision Rule

"Allow a user to upload a file directly to S3 from a browser" → Pre-signed POST (or pre-signed PUT URL).
"Bypass the 10 MB API Gateway payload limit" → Generate a pre-signed URL, let the client upload directly to S3.

S3 Event Notifications

S3 Advanced Features

Multipart upload, Transfer Acceleration, S3 Select, CORS
📚 Key Features
  • Multipart Upload: Upload objects in parts in parallel. Recommended for files > 100 MB, required for > 5 GB. Parts can be uploaded in any order and retried independently. Improves throughput.
  • S3 Transfer Acceleration: Uses CloudFront edge locations to accelerate uploads. Data travels from the edge to S3 over AWS's optimized network backbone. Enable per bucket; uses a special endpoint: bucketname.s3-accelerate.amazonaws.com.
  • S3 Select / Glacier Select: Retrieve a subset of data from an object using SQL-like queries. Works on CSV, JSON, Parquet. Reduces data transferred and speeds up queries. Cost savings by transferring less data out.
  • S3 Object Lambda: Add your own code (Lambda) to transform data as it's retrieved by GET requests. Use cases: redact PII, convert data formats, resize images on-the-fly.

If a web app hosted at example.com fetches images from mybucket.s3.amazonaws.com, the CORS configuration must be set on the S3 bucket, not on the web server. The CORS headers must include AllowedOrigins listing http://example.com.

Application Integration

Decoupling is a core theme on the DVA-C02 exam. SQS, SNS, EventBridge, Step Functions, and Kinesis are the building blocks for event-driven, loosely coupled architectures. Know the differences between Standard vs FIFO queues, fan-out patterns, and orchestration vs choreography.

📩

Amazon SQS

Fully managed message queuing for decoupling microservices
📚 Core Concepts
  • Standard Queue: Nearly unlimited throughput. Best-effort ordering. At-least-once delivery (possible duplicates). Default.
  • FIFO Queue: Exactly-once processing. Strict ordering within message groups. Throughput: 300 msg/sec without batching, 3,000 msg/sec with batching (per API action). High-throughput mode: up to 70,000 msg/sec. Queue name must end with .fifo.
  • Visibility Timeout: After a consumer receives a message, the message is hidden from other consumers for this duration. Default 30 seconds, max 12 hours. If not deleted before timeout expires, message becomes visible again (reprocessing). Consumer can call ChangeMessageVisibility to extend.
  • Message Retention: Default 4 days, configurable from 1 minute to 14 days.
  • Message Size: Max 256 KB. For larger messages, use SQS Extended Client Library (stores payload in S3, sends pointer via SQS). Up to 2 GB.
  • Long Polling: WaitTimeSeconds up to 20 seconds. Reduces empty responses and API calls. Always enable long polling (set at queue level or per-request).
  • Dead Letter Queue (DLQ): Messages that fail processing after maxReceiveCount attempts are sent to the DLQ. The DLQ must be the same type as the source queue (Standard DLQ for Standard queue, FIFO DLQ for FIFO queue). Set up the Redrive Policy on the source queue.
  • Delay Queue: Delay delivery of new messages. Default 0, max 15 minutes. Can also set per-message delay (Standard only).
💻 FIFO: Message Group ID & Deduplication
FIFO Ordering & Deduplication
  • MessageGroupId: Required for FIFO. Messages with the same Group ID are processed in order. Different Group IDs can be processed in parallel. Think of it as a "sub-queue" within the FIFO queue.
  • MessageDeduplicationId: Prevents duplicate messages within a 5-minute deduplication window. Either provide it explicitly, or enable content-based deduplication (SHA-256 hash of the body).

Exam Pattern: "Ensure ordering per customer" → FIFO queue with MessageGroupId = customerId. Each customer's messages are ordered; different customers are processed in parallel.

⚠ Exam Traps
Trap 1: SQS + Lambda Visibility Timeout

Set the SQS visibility timeout to at least 6x the Lambda function timeout. If Lambda takes longer than the visibility timeout, the message becomes visible and is processed again — causing duplicates.

Trap 2: DLQ Must Match Queue Type

A Standard queue's DLQ must be Standard. A FIFO queue's DLQ must be FIFO. Mismatching types is invalid and the exam may present it as a distractor.

Trap 3: SQS Is Pull-Based, Not Push-Based

SQS does NOT push messages to consumers. Consumers must poll (pull) messages using ReceiveMessage. Lambda event source mapping handles polling automatically, but under the hood it's still pull-based. If asked "push messages to consumers," that's SNS, not SQS.

Trap 4: Purge Queue for Testing

To delete all messages from a queue: PurgeQueue API. This takes up to 60 seconds. You cannot purge a queue more than once per 60 seconds. The exam may ask how to empty a queue during testing.

🔬 Example Scenario
An application processes orders. Each order must be processed exactly once and in the order received per customer. Multiple customers' orders can be processed simultaneously. Which SQS configuration is correct?
Answer: FIFO queue with MessageGroupId set to the customer ID
FIFO queue ensures exactly-once processing and strict ordering. Setting MessageGroupId to the customer ID ensures orders for the same customer are processed in sequence, while orders for different customers can be processed in parallel by different consumers. Content-based deduplication (or explicit DeduplicationId) prevents duplicate order submissions.

📚 Core Concepts
  • Publisher → Topic → Subscribers: A publisher sends a message to an SNS topic. The topic pushes the message to all subscribers simultaneously (fan-out).
  • Subscribers: SQS, Lambda, HTTP/HTTPS endpoints, Email, SMS, Kinesis Data Firehose, mobile push.

  • FIFO Topics: SNS FIFO topics can only deliver to SQS FIFO queues. Provide ordering and deduplication. Use MessageGroupId for ordering.
  • Fan-Out Pattern: SNS + SQS fan-out = publish once, deliver to multiple independent SQS queues for parallel processing. This is the most common architecture pattern on the exam.

AWS Step Functions

Visual workflow orchestration for distributed applications
📚 Core Concepts
  • State Machine: A workflow defined using Amazon States Language (ASL) — JSON-based. Contains states that perform work, make choices, wait, or branch execution.
  • Standard Workflows: Long-running (up to 1 year). Exactly-once execution. Priced per state transition. Best for durable, auditable workflows.
  • Express Workflows: Short-duration (up to 5 minutes). Higher throughput. At-least-once (async) or at-most-once (sync) execution. Priced per execution + duration. Best for high-volume event processing, streaming data, IoT.
  • State Types:
    • Task: Execute work (invoke Lambda, call AWS SDK API, run ECS task, send SQS message, etc.).
    • Choice: Branching logic (if/else).
    • Parallel: Execute branches concurrently.
    • Map: Iterate over a collection (like for-each). Supports inline mode (up to 40 parallel iterations) and distributed mode (up to 10,000 parallel child executions).
    • Wait: Pause for a specified duration or until a timestamp.
    • Succeed / Fail: Terminal states.
    • Pass: Pass input to output (or inject fixed data). Useful for prototyping.
  • Error Handling: Retry (with exponential backoff) and Catch (route to fallback state). Configured per state. Can catch specific error codes like States.TaskFailed, States.Timeout, Lambda.ServiceException, etc.
  • Service Integrations: Direct SDK integrations with 200+ AWS services. Three patterns: Request-Response (fire-and-forget), .sync (wait for completion), .waitForTaskToken (pause until external callback).
⚠ Exam Traps
Trap: Standard vs Express Workflows

"Long-running, needs exactly-once, auditable" → Standard.
"High volume, short duration, can tolerate duplicates" → Express.
The exam will present a high-throughput streaming scenario with Standard Workflow as a distractor (too expensive, not designed for high volume).

Trap: .waitForTaskToken Pattern

Used when Step Functions needs to pause and wait for an external process (human approval, third-party callback). The state machine generates a task token, passes it to the external system, then pauses. The external system calls SendTaskSuccess or SendTaskFailure with the token to resume. This is a very common exam scenario for "human approval workflow."

🔬 Example Scenario
An order processing system needs to: validate the order, charge the payment, update inventory, and send a confirmation email. If payment fails, the order should be cancelled. Each step calls a different Lambda function. What is the best way to orchestrate this workflow?
Answer: AWS Step Functions Standard Workflow
Step Functions provides visual workflow orchestration with built-in error handling. Use Task states to invoke each Lambda function in sequence. Add a Catch on the payment step to route to a cancellation state on failure. The standard workflow provides exactly-once execution semantics and a full audit trail in the execution history. This is much better than chaining Lambdas directly (which loses state and is harder to debug).

  • Shared (Classic) Fan-Out: All consumers share the 2 MB/s read throughput per shard. Uses GetRecords API (pull model). Max 5 GetRecords calls per shard per second.
  • Enhanced Fan-Out: Each consumer gets its own dedicated 2 MB/s per shard. Uses SubscribeToShard API (push model via HTTP/2). Supports up to 20 consumers per stream. Lower latency (~70ms vs ~200ms).
Exam Decision: Kinesis vs SQS

"Real-time, ordered, multiple consumers read same data, replay" → Kinesis Data Streams.
"Decouple producer from consumer, delete after processing, no ordering needed" → SQS Standard.
"Load data into S3/Redshift/OpenSearch" → Kinesis Data Firehose.

⚠ Exam Traps
Trap: ProvisionedThroughputExceededException

Caused by exceeding the shard's write (1 MB/s or 1,000 records/s) or read (2 MB/s or 5 GetRecords/s) limits. Solutions: increase shards (resharding), use exponential backoff for retries, distribute partition keys for better shard distribution, or use enhanced fan-out for read throughput.

Trap: Kinesis + Lambda Shard Blocking

Same as DynamoDB Streams: if Lambda fails processing a batch from KDS, the shard is blocked. Use BisectBatchOnFunctionError, MaximumRetryAttempts, and OnFailure destination to handle this.

AWS CloudFormation

📚 Core Concepts
  • Template: JSON or YAML file describing AWS resources. Key sections: AWSTemplateFormatVersion, Description, Parameters, Mappings, Conditions, Resources (required), Outputs, Transform.

⚠ Exam Traps
Trap: Stack Deletion Fails

Common causes: S3 bucket is not empty, security group is in use by another resource, resource is protected by DeletionPolicy: Retain. Fix: empty the bucket, remove dependencies, or update the deletion policy before deleting the stack.

Trap: DeletionPolicy

Retain — keep the resource when the stack is deleted (useful for S3, RDS). Snapshot — take a snapshot before deleting (RDS, ElastiCache, EBS). Delete — default for most resources. For S3 buckets, you must empty the bucket first (use a Custom Resource Lambda).

Trap: Rollback Behavior

If stack creation fails, CloudFormation rolls back all resources by default (everything deleted). If stack update fails, it rolls back to the previous successful state. You can disable rollback for debugging with --disable-rollback.

AWS CDK (Cloud Development Kit)

Define cloud infrastructure using familiar programming languages
📚 Core Concepts
  • CDK App: A program written in TypeScript, Python, Java, C#, or Go that defines cloud infrastructure using constructs.
  • Constructs: Cloud components. Three levels:

🐳

Amazon ECS

Run and manage Docker containers at scale
📚 Core Concepts
  • Cluster: Logical grouping of container instances or Fargate tasks.
  • Task Definition: Blueprint for your application (like a Dockerfile on steroids). Defines container image, CPU/memory, port mappings, environment variables, IAM roles, volumes, logging configuration.
  • Task: A running instance of a task definition. Can have 1 to 10 containers.
  • Service: Maintains a desired count of tasks. Integrates with ELB (ALB or NLB) for load balancing. Supports rolling updates and blue/green deployments.
  • Launch Types:
    • EC2 Launch Type: You manage EC2 instances. More control, you handle scaling the instances.
    • Fargate Launch Type: Serverless. AWS manages the infrastructure. You only define CPU/memory per task. Simpler but less customizable.
  • Task Role: IAM role that the containers in the task can assume (like Lambda execution role). Grants permissions to access AWS services from within the container.
  • Task Execution Role: IAM role that the ECS agent uses to pull container images from ECR and publish logs to CloudWatch. Different from Task Role.
⚠ Exam Traps
Trap: Task Role vs Task Execution Role

Task Role: Permissions for your application code (e.g., access DynamoDB, S3). Set at task definition level, assumed by the containers.
Task Execution Role: Permissions for the ECS agent (pull images from ECR, write to CloudWatch Logs, fetch secrets from SSM/Secrets Manager). This distinction is heavily tested.

Trap: ECS Environment Variables & Secrets

Inject secrets into containers using: (1) SSM Parameter Store references in task definition, (2) Secrets Manager references in task definition, or (3) S3-based environment files. The Task Execution Role needs permission to access these secrets. Never put secrets directly in the task definition.

Trap: ALB Dynamic Port Mapping

When running multiple tasks on the same EC2 instance, use ALB with dynamic host port mapping (set host port to 0 in task definition). The ALB automatically routes to the correct random port. Classic Load Balancer does NOT support dynamic port mapping — ALB or NLB only.

🔐

IAM for Developers

Policies, roles, and the principle of least privilege
📚 Key Concepts
  • IAM Policy Types:
    • Identity-based: Attached to users, groups, or roles. Controls what the identity can do.
    • Resource-based: Attached to a resource (S3 bucket, SQS queue, Lambda function). Controls who can access the resource. Includes a Principal field.
    • Permission Boundary: Sets the maximum permissions an IAM entity can have. Used for delegation — allow admins to create roles but limit what those roles can do.
  • Policy Evaluation Logic: Default deny → Explicit deny wins → Allow → Implicit deny. If any policy explicitly denies, access is denied regardless of allows.
  • Policy Variables: Use ${aws:username}, ${aws:PrincipalTag/department} in policies for dynamic access control (ABAC — Attribute-Based Access Control).
  • IAM Roles for Services: EC2 instance profiles, Lambda execution roles, ECS task roles. Always use roles instead of access keys in AWS services.
⚠ Exam Traps
Trap: Cross-Account Access

For cross-account access, the target account creates a role with a trust policy allowing the source account. The source account's IAM entity uses sts:AssumeRole to assume that role. Resource-based policies (S3, SQS, etc.) can also grant cross-account access directly without assuming a role — the key difference is that with resource-based policies, the principal retains its original permissions PLUS gains the resource access.

Trap: Access Keys vs IAM Roles

Never embed access keys in code, Lambda environment variables, or EC2 user data. Always use IAM roles. If the exam mentions "access keys in code" or "credentials in environment variables," the correct fix is to use an IAM role.

AWS STS & AssumeRole

📚 Key APIs
  • AssumeRole: Assume a role in the same or different account. Returns temporary credentials (access key, secret key, session token). Max duration: 1 hour (default) to 12 hours.
  • AssumeRoleWithSAML: Assume a role using SAML 2.0 assertion from an identity provider. For enterprise SSO.
  • AssumeRoleWithWebIdentity: Assume a role using a web identity token (Google, Facebook, Amazon). AWS recommends using Cognito Identity Pools instead of calling this directly.
  • GetSessionToken: Get temporary credentials for an IAM user. Useful for MFA-protected API access. Returns credentials with MFA context.
  • GetCallerIdentity: Returns the AWS account ID, IAM user/role ARN, and user ID of the caller. Useful for debugging "who am I?"
  • DecodeAuthorizationMessage: Decode an encoded authorization error message to understand why access was denied.

Cognito Identity Pools can grant unauthenticated (guest) access to AWS resources by mapping unauthenticated identities to a specific IAM role with limited permissions. Useful for anonymous read access to S3 or DynamoDB.

AWS KMS

Create and manage encryption keys for your applications
📚 Core Concepts
  • CMK Types:
    • AWS Managed Keys: Created automatically by AWS services (e.g., aws/s3, aws/ebs). Free. Auto-rotated every year. You cannot manage or delete them.
    • Customer Managed Keys (CMK): Created by you. $1/month. Full control over key policy, rotation (optional, every year), enable/disable, deletion. Can be used cross-account.
    • AWS Owned Keys: Used by AWS internally. Not visible in your account.
  • Envelope Encryption: KMS encrypts your data key. The data key encrypts your data. This allows encrypting data larger than 4 KB (KMS direct encryption limit). The GenerateDataKey API returns a plaintext and encrypted data key. Use the plaintext key to encrypt data, store the encrypted data key alongside the ciphertext, discard the plaintext key.
  • Key Policies: Resource-based policy on the KMS key. Controls who can use and manage the key. Default policy gives the account root user full access. Must explicitly allow IAM policies to work (unlike most other resource policies).
  • API Calls: Encrypt, Decrypt, GenerateDataKey (for envelope encryption), GenerateDataKeyWithoutPlaintext, ReEncrypt (re-encrypt without exposing plaintext).
  • Quotas: KMS API request quotas vary by region (5,500 to 30,000 RPS for cryptographic operations). Exceeding quota returns ThrottlingException. Solutions: exponential backoff, request quota increase, or use S3 Bucket Keys / data key caching.
⚠ Exam Traps
Trap: Envelope Encryption

If asked "how to encrypt a 10 MB file using KMS," the answer is envelope encryption with GenerateDataKey. You cannot use KMS Encrypt directly for data larger than 4 KB. The exam frequently tests this distinction.

Trap: KMS Key Rotation

Automatic rotation: Rotates key material every year (configurable 90-2560 days). The key ID and ARN stay the same; only the backing key changes. Old key material is kept to decrypt previously encrypted data. Manual rotation: Create a new key, update applications. Use aliases to abstract the key ID so you only update the alias pointer.

AWS Secrets Manager

Rotate, manage, and retrieve secrets throughout their lifecycle
📚 Key Facts
  • Store and automatically rotate secrets (database credentials, API keys, tokens).
  • Automatic Rotation: Uses a Lambda function to rotate secrets on a schedule. Built-in rotation support for RDS (MySQL, PostgreSQL, Oracle, SQL Server, MariaDB), Redshift, and DocumentDB. Custom Lambda for other secrets.
  • Encrypted with KMS. Pay per secret per month ($0.40) + per 10,000 API calls ($0.05).
  • Cross-region replication: Replicate secrets to other regions for DR.
  • Versioning: AWSCURRENT (current version), AWSPREVIOUS (previous version), AWSPENDING (during rotation).

SSM Parameter Store

Centralized store for configuration data and secrets
📚 Key Facts

  • Integration: Lambda, ECS, CodeBuild, CloudFormation all support native Parameter Store references.

Monitoring & Troubleshooting

Domain 4 (18%) covers CloudWatch, X-Ray, and CloudTrail. You must know how to instrument Lambda and ECS with X-Ray, write metric filters, create alarms, and use CloudWatch Logs Insights.

📊

Amazon CloudWatch

Monitor, observe, and act on AWS resources and applications
📚 Core Components
  • Metrics: Time-ordered data points. Default metrics are published by AWS services (e.g., EC2 CPUUtilization, Lambda Duration). Resolution: Standard (1 minute) or High-resolution (1 second, custom metrics).
  • Custom Metrics: Publish your own metrics using PutMetricData API. Useful for application-level metrics (active users, order counts, error rates). Support dimensions (up to 30 per metric) for filtering.
  • Alarms: Watch a metric and trigger actions when a threshold is breached. States: OK, ALARM, INSUFFICIENT_DATA. Actions: SNS notification, Auto Scaling action, EC2 action (stop, terminate, reboot). Composite alarms combine multiple alarms with AND/OR logic.
  • Dashboards: Customizable visualizations. Can include metrics from multiple regions and accounts. Global service.
  • CloudWatch Events / EventBridge: EventBridge is the evolution of CloudWatch Events. Same underlying service. Use EventBridge for new development.
⚠ Exam Traps
Trap: EC2 Memory & Disk Metrics

CloudWatch does NOT collect memory utilization, disk space usage, or swap usage for EC2 by default. These require the CloudWatch Agent installed on the instance (or the unified CloudWatch Agent). This is a very common exam question.

Trap: Lambda Metrics

Lambda publishes: Invocations, Duration, Errors, Throttles, ConcurrentExecutions, UnreservedConcurrentExecutions, IteratorAge (for stream sources). Lambda does NOT publish memory utilization as a CloudWatch metric (visible only in logs via MAX Memory Used). Use Lambda Insights for memory/CPU metrics.

📜

CloudWatch Logs & Logs Insights

Centralized log management, analysis, and querying
📚 Core Concepts
  • Log Group: A collection of log streams that share the same settings (retention, encryption, access). Example: /aws/lambda/my-function.
  • Log Stream: A sequence of log events from a single source. Example: one Lambda invocation creates events in a stream.
  • Retention: Configurable per log group. Default: never expire. Can set 1 day to 10 years.
  • Metric Filters: Define patterns to search log data and create CloudWatch metrics from matches. Example: count occurrences of "ERROR" in logs and create an alarm on it.
  • Logs Insights: Interactive query service for analyzing log data. SQL-like query language. Can query across multiple log groups. Supports visualization.
  • Subscription Filters: Stream log data in real-time to Kinesis Data Streams, Kinesis Firehose, Lambda, or OpenSearch. Can filter which log events to stream.
  • Export to S3: Batch export log data to S3 (not real-time, can take up to 12 hours). For real-time, use Subscription Filters to Firehose → S3.
  • Log Agent vs Unified Agent: The older CloudWatch Logs Agent only sends logs. The Unified Agent sends both logs AND system-level metrics (memory, disk, swap, netstat, processes). Use Unified Agent for new deployments.
⚠ Exam Trap
Trap: Lambda Logging Permissions

Lambda needs logs:CreateLogGroup, logs:CreateLogStream, logs:PutLogEvents permissions in its execution role to write to CloudWatch Logs. The managed policy AWSLambdaBasicExecutionRole provides these. If Lambda isn't logging, check the execution role.

AWS X-Ray

Distributed tracing for analyzing and debugging microservices
📚 Core Concepts
  • Trace: An end-to-end request across all services it touches.
  • Segment: A portion of the trace representing one service. Contains timing, status, and subsegments.
  • Subsegment: Granular detail within a segment (e.g., individual AWS SDK calls, HTTP calls, SQL queries).
  • Service Map: Visual representation of all services and their connections. Shows latency, error rates, and request counts.
  • Annotations: Key-value pairs that are indexed and searchable. Use for filtering traces (e.g., user_id = "123").
  • Metadata: Key-value pairs that are NOT indexed. For storing additional data without needing to search by it.
  • Sampling Rules: Control the percentage of requests that are traced. Default: 1 request per second + 5% of additional requests. Customize to reduce cost and noise.

Trap: Annotations vs Metadata

If the question says "filter traces by" or "search traces for," use Annotations (indexed). If it just says "store additional debug info," use Metadata (not indexed). This is a frequent exam question.

Trap: X-Ray SDK vs X-Ray Daemon

The SDK goes in your application code (instruments HTTP calls, AWS SDK calls, SQL queries). The daemon is a separate process that receives segments from the SDK and sends them to the X-Ray service in batches. Both are needed. On Lambda, the daemon runs automatically; you only need the SDK.

Trap: X-Ray Environment Variable

AWS_XRAY_DAEMON_ADDRESS tells the SDK where to send trace data. On ECS, set this to xray-daemon:2000 (the sidecar container name). If X-Ray traces aren't appearing, check this variable and the IAM permissions.

AWS CloudTrail

Governance, compliance, and audit trail for AWS API calls
📚 Key Facts
  • Records API calls made in your AWS account. Every action in AWS is an API call — console, CLI, SDK, service-to-service.
  • Event Types:
    • Management Events: Operations on AWS resources (CreateBucket, AttachRolePolicy, RunInstances). Enabled by default.
    • Data Events: Operations on data within resources (S3 GetObject/PutObject, Lambda Invoke, DynamoDB GetItem/PutItem). Not enabled by default (high volume, extra cost).
    • Insights Events: Detect unusual activity (e.g., spike in API calls, unusual error rates).
  • Event delivery: Events appear in CloudTrail within 15 minutes. Stored for 90 days in Event History (free). For longer retention, create a Trail that delivers events to S3 and optionally CloudWatch Logs.
  • Exam tip: "Who did what and when?" → CloudTrail. "How is the application performing?" → CloudWatch/X-Ray.

💻 Caching Strategies
Lazy Loading (Cache-Aside)
  • Application checks cache first. On cache miss, reads from database, writes result to cache.
  • Pros: Only requested data is cached. Cache doesn't fill with unused data.
  • Cons: Cache miss = 3 round trips (check cache, read DB, write cache). Data can become stale.
Write-Through
  • Application writes to cache AND database simultaneously (on every write).
  • Pros: Cache data is always current. No stale data.
  • Cons: Write penalty (2 writes for every operation). Cache may contain data that is never read.
Best Practice: Combine Both

Use Lazy Loading as the base strategy with TTL on cache entries. Add Write-Through for frequently updated and read data. This gives you the best of both worlds.

⚠ Exam Trap
ElastiCache for Sessions

"Application has sticky sessions on the load balancer; how to make it stateless?" → Store sessions in ElastiCache (Redis). Remove sticky sessions from the ALB. Any instance can then serve any user by looking up the session in ElastiCache. DynamoDB is also valid for session storage but ElastiCache is faster (microsecond latency).

Amazon CloudFront

Global content delivery network (CDN)
📚 Key Facts for Developers
  • Origins: S3 bucket, ALB, EC2, HTTP backend, API Gateway, MediaStore.
  • S3 + CloudFront: Use Origin Access Control (OAC) to restrict S3 access to only CloudFront (replaces the older OAI). The S3 bucket policy only allows the CloudFront distribution.
  • Cache Behavior: Configure per-path cache behavior (e.g., /api/* → ALB, /static/* → S3). Control which headers, cookies, and query strings are forwarded to the origin and included in the cache key.
  • Cache Invalidation: Remove files from edge caches before TTL expires. Use CreateInvalidation API. Wildcards supported (/*). Costs per invalidation request. Alternative: use versioned file names (app-v2.js).
  • CloudFront Functions vs Lambda@Edge:
    • CloudFront Functions: Lightweight JavaScript, viewer request/response only, sub-millisecond, millions of RPS. Use for: URL rewrites, header manipulation, cache key normalization, simple auth.
    • Lambda@Edge: Full Lambda (Node.js/Python), viewer and origin request/response, up to 30 seconds, regional edge. Use for: complex auth, A/B testing, dynamic origin selection, image transformation.
  • Signed URLs / Signed Cookies: Restrict access to content. Signed URL = one file. Signed Cookie = multiple files. Use a CloudFront key pair or trusted key group. Not the same as S3 pre-signed URLs.

Amazon RDS & Aurora

Managed relational databases for developers
📚 Key Facts for DVA-C02
  • RDS Proxy: Fully managed database proxy for RDS. Pools and shares database connections. Reduces failover time by 66%. Critical for Lambda — Lambda functions can open many connections rapidly, exhausting the database connection pool. RDS Proxy solves this by connection pooling. Must be in the same VPC as the database.
  • IAM Database Authentication: Authenticate to RDS (MySQL, PostgreSQL) using IAM roles and tokens instead of passwords. Short-lived auth tokens (15 minutes). SSL required. No need to store database credentials.
  • Aurora Serverless: Auto-scaling Aurora that adjusts capacity based on demand. Pay per ACU (Aurora Capacity Unit) per second. Great for infrequent or unpredictable workloads. V2 supports scaling to zero.
  • Read Replicas: Offload read traffic. Up to 15 read replicas for Aurora, 5 for RDS. Async replication (eventually consistent). Can be promoted to standalone DB. Cross-region read replicas available.
  • Multi-AZ: Synchronous standby replica in different AZ. Automatic failover (DNS endpoint stays the same). For high availability, NOT for read scaling.
⚠ Exam Trap
Lambda + RDS = Use RDS Proxy

Lambda functions can rapidly create and destroy database connections. Without connection pooling, this can exhaust the database's max_connections. The solution is RDS Proxy, which manages a pool of database connections and reuses them across Lambda invocations. The Lambda function must be in the VPC (same as RDS Proxy). This is a high-frequency exam scenario.

Real DVA-C02 Scenario Walkthroughs

Practice with exam-style questions and detailed explanations
Scenario 1: A developer's Lambda function processes messages from an SQS queue. The function takes 5 minutes to process each message but the visibility timeout is 30 seconds. Messages are being processed multiple times. How should this be fixed?
Set the SQS visibility timeout to at least 30 minutes (6x the Lambda timeout)
AWS recommends setting the visibility timeout to at least 6x the Lambda function timeout. With a 5-minute function timeout, the visibility timeout should be at least 30 minutes. This prevents the message from becoming visible while Lambda is still processing it.
Scenario 2: A web application allows users to upload profile pictures. The API Gateway has a 10 MB payload limit but users need to upload files up to 50 MB. How should the developer architect this?
Generate an S3 pre-signed URL via Lambda, return it to the client, and have the client upload directly to S3
API Gateway has a hard 10 MB payload limit. The solution is to bypass API Gateway for the upload: the client calls the API to get a pre-signed PUT URL for S3, then uploads the file directly to S3 using that URL. S3 supports objects up to 5 TB. The Lambda function generates the pre-signed URL with appropriate permissions and expiration.
Scenario 3: A developer deployed a Lambda function in a VPC to access an RDS database. Now the function cannot write to a DynamoDB table. What is the issue?
Lambda in VPC has no internet access. Add a VPC Gateway Endpoint for DynamoDB.
When Lambda is placed in a VPC, it loses internet access. DynamoDB is a public AWS service accessed over the internet. Without internet access (NAT Gateway) or a VPC Endpoint, Lambda cannot reach DynamoDB. The best solution is a VPC Gateway Endpoint for DynamoDB (free, no NAT Gateway needed).
Scenario 4: A developer needs to deploy a new version of a Lambda function behind API Gateway. They want to send 10% of traffic to the new version for 10 minutes, then shift all traffic if no errors are detected. How?
Use Lambda aliases with weighted traffic shifting (CodeDeploy Canary10Percent10Minutes)
Create a Lambda alias pointing to the current version. Use CodeDeploy with the Canary10Percent10Minutes deployment preference to shift 10% of traffic to the new version. After 10 minutes with no CloudWatch Alarm triggers, CodeDeploy shifts 100% of traffic. API Gateway stage variables point to the alias, abstracting the version change.
Scenario 5: An application stores user session data in DynamoDB. Some items are read thousands of times per second while others are rarely accessed. The table is experiencing throttling. What optimization should be applied?
Add DynamoDB Accelerator (DAX) for microsecond read latency and to reduce RCU consumption
DAX is perfect for read-heavy workloads with hot keys. It provides microsecond latency for reads and reduces the RCU load on the underlying DynamoDB table. DAX is a write-through cache, so writes are automatically reflected. The application only needs to switch to the DAX client SDK — no code logic changes required.

Top 20 DVA-C02 Exam Traps

The most commonly tested gotchas and distractors
