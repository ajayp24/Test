1. AWS Migration Strategy — 7 Rs

THE 7 Rs OF MIGRATION 1. RETIRE - Decommission. No migration needed. ~10-20% of portfolio. "This app is no longer used." 2. RETAIN - Keep on-premises (for now). Too complex, compliance, not migrating yet. "We'll revisit in 2 years." 3. REHOST - Lift and Shift. Move to EC2 without changes. (Lift & Shift) Fast, low risk. Use AWS MGN (Application Migration Service). "Move as-is to AWS EC2." 4. REPLATFORM - Lift, Tinker, Shift. Minor optimizations. (Move & Improve) e.g., Oracle DB → RDS (managed). App server → Elastic Beanstalk. "Managed database but same app." 5. REPURCHASE - Drop and Shop. Move to SaaS. (Drop & Shop) e.g., CRM → Salesforce. Email → MS365. HR → Workday. "Buy instead of migrate." 6. REFACTOR - Re-architect. Cloud-native redesign. (Re-architect) Monolith → Microservices + Lambda. Most expensive, highest ROI. "Rebuild using cloud-native services." 7. RELOCATE - Move to cloud without changes using VMware Cloud on AWS. (Hypervisor level) Same VMware environment, move VMs to AWS. "VMware vMotion to AWS VMware Cloud."

2. AWS Application Migration Service (MGN)

AWS MGN (formerly CloudEndure Migration) is the primary recommended service for Rehost migrations. It performs block-level replication of servers to AWS.

MGN MIGRATION FLOW On-Premises Server AWS ┌──────────────────┐ ┌──────────────────────────┐ │ Source Server │ │ MGN Service │ │ ┌─────────────┐ │ │ ┌──────────────────────┐ │ │ │ MGN Agent │──│──continuous──────►││ Replication Server │ │ │ │ (installed) │ │ block-level │ │ (EC2, EBS volumes) │ │ │ └─────────────┘ │ replication │ └──────────────────────┘ │ └──────────────────┘ │ │ │ │ Cutover/Launch │ │ ▼ │ │ Target EC2 Instance │ │ (same data, AWS infra) │ └──────────────────────────┘ Steps: 1. Install MGN agent on source server 2. Initial sync (full copy to staging area) 3. Continuous replication (delta changes) 4. Test launch (non-disruptive, test env) 5. Cutover (stop source → launch target) 6. Cleanup (decommission source)

MGN Key Features

  • Continuous block-level replication (RPO ~ minutes)
  • No-downtime cutover (minimal cutover window)
  • Supports: Windows/Linux, physical servers, VMware, Hyper-V, Azure, GCP
  • Auto-converts boot from BIOS to UEFI, changes storage drivers
  • Test launches before actual cutover
  • Pricing: Free for 2,048 hours per server

3. AWS Database Migration Service (DMS)

DMS migrates databases to AWS quickly and securely. The source database remains fully operational during migration, minimizing downtime.

DMS Task Types

Task TypeWhat It DoesUse Case
Full LoadCopy all existing dataInitial migration, small databases
CDC OnlyCapture ongoing changes onlyAlready seeded target, minimal lag
Full Load + CDCFull load then switch to CDCLive migration with minimal cutover window
Schema Conversion Tool (SCT): DMS moves data; SCT converts schema. For heterogeneous migrations (Oracle → Aurora), you need SCT to convert stored procedures, triggers, and schema. DMS does NOT convert schema.

DMS Use Cases

  • Homogeneous: MySQL → RDS MySQL (no schema conversion needed)
  • Heterogeneous: Oracle → Aurora PostgreSQL (SCT + DMS)
  • Consolidation: Multiple source DBs → single target
  • Continuous replication: On-prem DB → RDS (ongoing sync for hybrid)
  • NoSQL migration: DynamoDB, MongoDB source
  • Data lake ingestion: Relational DB → S3 (Parquet format)

4. AWS DataSync for Migration

DataSync accelerates online data transfer to/from AWS. Up to 10x faster than standard Linux tools with built-in integrity checks.

  • Source: NFS/SMB on-premises, S3, EFS, FSx, HDFS, Azure Blob Storage, Google Cloud Storage
  • Destination: S3, EFS, FSx (Windows, Lustre, ONTAP, OpenZFS)
  • Agent: Deploy DataSync agent VM on-premises — connects via Direct Connect or VPN
  • Scheduling: One-time or recurring transfers
  • Pricing: $0.0125/GB transferred

6. Enterprise Migration Case Studies

Case Study 1: Banking — Oracle to Aurora PostgreSQL

BANKING CORE MIGRATION Phase 1: Assessment (2 months) AWS Migration Evaluator → Understand on-prem footprint AWS Schema Conversion Tool → Assess Oracle → Aurora PostgreSQL Identify: 12 stored procedures, 3 triggers need rewriting Phase 2: Schema Conversion (1 month) SCT converts 85% automatically Manual rewrite: 15% complex PL/SQL Test in dev Aurora cluster Phase 3: Data Migration (2 months) DMS Full Load → copy 2 TB Oracle data to Aurora DMS CDC → continuous replication (lag < 5 sec) Validation: Row count checks, data checksums Phase 4: Cutover Saturday 2 AM maintenance window Stop Oracle writes → wait DMS lag = 0 Switch JDBC connection string to Aurora endpoint Test application → confirm success Total downtime: < 30 minutes Result: License cost: -$1.2M/year (Oracle → Aurora) Performance: +30% query performance HA: Multi-AZ automatic (was manual Oracle Data Guard)

Case Study 2: E-Commerce — Lift and Shift (Rehost)

REHOST MIGRATION On-Premises: 200 VMs running LAMP stack Storage: NetApp NAS (50 TB) DB: MySQL 5.7 cluster Migration Strategy: Step 1: Direct Connect (1 Gbps) — establish private connectivity Step 2: AWS MGN — install agent on all 200 VMs, start replication Step 3: DataSync — sync 50 TB NAS data to EFS Step 4: DMS — replicate MySQL → RDS MySQL (Full Load + CDC) Step 5: DNS cutover via Route 53 (gradual weighted routing: 10% → 50% → 100%) Timeline: 6 weeks Downtime per app: < 15 minutes Immediate Wins: • Infrastructure managed by AWS (patching, hardware) • Cost: -35% (Reserved Instances vs on-prem hardware refresh) • Elasticity: Auto Scaling for peak traffic

7. Exam Tips & Cheat Sheet

SAP-C02 Migration — Critical Points

  • 7 Rs: Rehost = lift and shift (MGN). Replatform = minor changes (RDS). Refactor = cloud-native redesign. Retire = decommission. Retain = keep on-prem. Repurchase = SaaS. Relocate = VMware on AWS.
  • MGN vs DMS: MGN = server/VM migration (any workload). DMS = database migration specifically.
  • DMS + SCT: Heterogeneous migration (Oracle → Aurora) needs BOTH DMS (data) and SCT (schema conversion).
  • Snow Family: Large offline data: <80 TB → Snowball Edge Storage. >10 PB → Snowmobile. Need edge compute → Snowball Edge Compute Optimized.
  • DataSync: Online bulk transfer (faster than rsync). NOT for ongoing hybrid access (use Storage Gateway for that).
  • DMS CDC: Captures ongoing changes. Use Full Load + CDC for live migrations with minimal cutover.
  • Migration Evaluator: Assess and build business case before migration. Understand on-prem costs.
  • Migration Hub: Central tracking of migration status across DMS, MGN, and other migration tools.
7 Rs Quick Reference
  • Rehost → MGN (lift & shift)
  • Replatform → RDS, Beanstalk
  • Refactor → Lambda, containers
  • Repurchase → SaaS products
  • Relocate → VMware Cloud on AWS
  • Retain → keep on-prem
  • Retire → decommission
Migration Tools
  • Server migration → MGN
  • DB migration → DMS
  • Schema conversion → SCT
  • Online file transfer → DataSync
  • Offline large scale → Snow Family
  • SFTP partners → Transfer Family
  • Ongoing hybrid → Storage Gateway
Snow Family Selection
  • Remote/small: Snowcone (8-14 TB)
  • Standard: Snowball Edge Storage 80 TB
  • Edge compute: Snowball Edge Compute
  • Exabyte: Snowmobile (100 PB)
  • Rule: >1 week to transfer online → Snow
DMS Migration Types
  • Full Load: initial copy
  • CDC only: ongoing changes
  • Full Load + CDC: live migration
  • Homogeneous: no SCT needed
  • Heterogeneous: DMS + SCT both needed
