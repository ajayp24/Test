▶ OOP, Value Types vs Reference Types, Structs vs Classes Core

Value Types vs Reference Types

This is the single most foundational concept in C#. Value types (struct, enum, primitives like int, bool, double) are stored on the stack (or inline within objects) and copied on assignment. Reference types (class, interface, delegate, string, arrays) are stored on the heap with a reference pointer on the stack. Understanding this determines how you reason about performance, equality, and memory in enterprise applications.

Tricky: What is boxing and why is it a performance concern?
Boxing wraps a value type in an object on the heap. This happens implicitly when you assign a value type to object, dynamic, or an interface variable. Each box allocates ~12-16 bytes on the heap plus the value, and creates GC pressure. In hot paths (loops processing millions of records), boxing causes massive allocations. Avoid it by using generic collections (List<int> not ArrayList), generic constraints, and Span<T> for slicing. 
// Boxing happens here:
int x = 42;
object boxed = x;     // BOXING: allocates on heap
int y = (int)boxed;   // UNBOXING: copies back to stack

// No boxing with generics:
List<int> nums = new() { 1, 2, 3 }; // No boxing!
Tricky: When should you use record vs record struct vs class?
  • record (C# 9+): Reference type with value-based equality. Perfect for DTOs, API responses, and event payloads. Supports with expressions for non-destructive mutation. Gets auto-generated Equals, GetHashCode, ToString, and deconstruction.
  • record struct (C# 10+): Value type with value-based equality. Ideal for small value objects (Money, Coordinate) where you want stack allocation AND value semantics. Use readonly record struct to guarantee immutability.
  • class: When you need identity-based equality (two Customer objects with the same name are still different entities), inheritance hierarchies, or mutable state with encapsulated behavior.

Delegates & Events — Observer Pattern Built Into C#

A delegate is a type-safe function pointer. An event is a delegate with restricted access (only the declaring class can invoke it). This is the backbone of the observer pattern in .NET — UI frameworks, domain events, and messaging all use it.

Tricky: What is the difference between IEnumerable<T> and IQueryable<T>?
IEnumerable<T> executes in memory using delegates. IQueryable<T> builds expression trees that are translated to SQL by the ORM. If you return IEnumerable from a repository, the entire table is loaded into memory first, then filtered. With IQueryable, the WHERE clause becomes SQL WHERE and runs on the database. This difference can mean loading 10 rows vs 10 million rows. In enterprise apps, always keep queries as IQueryable until the very last moment, then materialize with .ToListAsync().
▶ async/await, Task, ValueTask, CancellationToken Interview Favorite

The Async Model in .NET

C#'s async/await is a compiler-generated state machine. When you await, the method is split at the await point. The thread is released back to the pool while waiting for I/O. When the I/O completes, a thread picks up execution after the await. This allows a single web server to handle thousands of concurrent requests with very few threads.

// Proper async pattern in a service
public class OrderService
{
    private readonly IOrderRepository _repo;
    private readonly IPaymentGateway _payments;
    private readonly ILogger<OrderService> _logger;

    public async Task<OrderResult> PlaceOrderAsync(
        CreateOrderRequest request,
        CancellationToken ct = default)
    {
        // CancellationToken: lets the caller cancel long-running work
        ct.ThrowIfCancellationRequested();

        var order = Order.Create(request);
        await _repo.AddAsync(order, ct);

        // Parallel I/O calls with timeout
        using var cts = CancellationTokenSource
            .CreateLinkedTokenSource(ct);
        cts.CancelAfter(TimeSpan.FromSeconds(10));

        var paymentTask = _payments.ChargeAsync(order.Total, cts.Token);
        var inventoryTask = _inventory.ReserveAsync(order.Items, cts.Token);

        await Task.WhenAll(paymentTask, inventoryTask);

        return new OrderResult(order.Id, await paymentTask);
    }
}

Tricky: Why should you never use async void except for event handlers?
async void methods cannot be awaited, so the caller has no way to know when they complete or catch their exceptions. If an async void method throws, the exception goes directly to the SynchronizationContext and will crash the application. Always use async Task instead. The only exception is event handlers (e.g., button click handlers in WPF/WinForms) because the event delegate signature requires void. 
// WRONG: Exception crashes the app, no way to await
async void ProcessPayment() { await gateway.ChargeAsync(); }

// CORRECT: Caller can await and handle exceptions
async Task ProcessPaymentAsync() { await gateway.ChargeAsync(); }
Tricky: What does ConfigureAwait(false) do and when should you use it?
By default, await captures the SynchronizationContext and resumes on the same context (e.g., the UI thread in WPF). ConfigureAwait(false) says "I don't need to resume on the original context." Use it in library code to avoid deadlocks and improve performance. Do NOT use it in ASP.NET Core (there's no SynchronizationContext) or in UI code where you need to update the UI after the await. In ASP.NET Core, it's technically harmless but unnecessary.

Middleware Pipeline

Every HTTP request flows through a pipeline of middleware components in order. Each middleware can process the request, pass it to the next, and then process the response on the way back. Think of it as a series of nested Russian dolls.

// Order matters! Each middleware wraps the next.
var app = builder.Build();
app.UseExceptionHandler("/error");  // 1. Outermost: catch all errors
app.UseHttpsRedirection();              // 2. Redirect HTTP to HTTPS
app.UseCors("AllowFrontend");           // 3. CORS headers
app.UseAuthentication();                // 4. Who are you?
app.UseAuthorization();                 // 5. What can you do?
app.UseRateLimiter();                   // 6. Too many requests?
app.MapControllers();                   // 7. Terminal: route to controller

// Custom middleware
app.Use(async (context, next) =>
{
    var sw = Stopwatch.StartNew();
    context.Response.Headers.Append("X-Request-Id",
        Guid.NewGuid().ToString());
    await next(context);
    sw.Stop();
    logger.LogInformation("Request {Path} took {Ms}ms",
        context.Request.Path, sw.ElapsedMilliseconds);
});

Tricky: What is the "captive dependency" problem?
When a Singleton service depends on a Scoped or Transient service, the shorter-lived dependency is "captured" and kept alive for the lifetime of the Singleton. A Scoped DbContext injected into a Singleton will be shared across all requests, causing thread-safety issues and stale data. ASP.NET Core throws an InvalidOperationException in Development mode if you enable ValidateScopes. Fix: inject IServiceScopeFactory into the Singleton and create a new scope manually when you need the Scoped service.

Tricky: Why should you use AsNoTracking() for read-only queries?
EF Core's change tracker creates a snapshot of every entity loaded. This consumes memory and CPU. For read-only scenarios (API GET endpoints, reports, dashboards), AsNoTracking() skips the tracking snapshot, giving 30-50% performance improvement on large result sets. It also prevents accidental updates — if you modify an untracked entity and call SaveChanges(), nothing happens. Best practice: use AsNoTracking() by default and only track entities when you intend to update them.

// Pipeline behavior (cross-cutting: logging, validation)
public class ValidationBehavior<TReq, TRes> :
    IPipelineBehavior<TReq, TRes>
{
    private readonly IEnumerable<IValidator<TReq>> _validators;

    public async Task<TRes> Handle(TReq request,
        RequestHandlerDelegate<TRes> next, CancellationToken ct)
    {
        var failures = _validators
            .Select(v => v.Validate(request))
            .SelectMany(r => r.Errors)
            .Where(f => f != null)
            .ToList();

        if (failures.Any())
            throw new ValidationException(failures);

        return await next();
    }
}

50 SE-Level .NET Interview Questions

▼

C# Language (1-15)

1. What is the difference between string and StringBuilder?
string is immutable — every modification creates a new string on the heap. Concatenating in a loop creates N intermediate strings, causing O(n²) memory. StringBuilder maintains a mutable internal buffer and is O(n). Use StringBuilder when building strings in loops (e.g., CSV export, HTML generation). For simple concatenation of a few strings, string interpolation ($"Hello {name}") is fine — the compiler optimizes it.
2. Explain ref, out, and in parameter modifiers.
ref: passes by reference, must be initialized before call, can read and write. out: passes by reference, must be assigned inside the method, used for returning multiple values. in: passes by read-only reference, prevents copying large structs while guaranteeing no modification. in is particularly useful for readonly struct parameters in hot paths to avoid stack copies of large value types. In modern C#, prefer returning tuples or records over out parameters for cleaner APIs.
3. What is the difference between const and readonly?
const: compile-time constant, inlined at every usage site, only primitive types and strings. If you change a const in library A, all consumers must recompile. readonly: runtime constant, set in constructor or declaration, can be any type including objects. static readonly is like a runtime constant. Use const for true constants (Pi, MaxRetries). Use readonly for values that won't change after construction but may differ per instance or need to be computed.
4. What is IDisposable and why is it important?
IDisposable provides deterministic cleanup of unmanaged resources (file handles, DB connections, sockets, locks). The GC handles managed memory but doesn't know about native resources. Always wrap IDisposable in using statements. In ASP.NET Core, the DI container automatically disposes Scoped and Transient services. Forgetting to dispose DbContext or HttpClient leads to connection pool exhaustion, which manifests as random timeouts under load.
5. Explain Span<T> and Memory<T>.
Span<T> is a stack-only, zero-allocation view over contiguous memory (arrays, strings, native memory). It allows slicing without copying. Memory<T> is the heap-friendly counterpart (can be stored in fields, used in async methods). Use cases: parsing large strings without allocating substrings, processing binary protocols, high-performance serialization. Span is a ref struct, so it cannot be used in async methods, captured by lambdas, or stored on the heap.
6. What is the difference between abstract classes and interfaces in C#?
Abstract classes can have state (fields), constructors, and both implemented and abstract members. A class can inherit only one abstract class. Interfaces define contracts with no state (until C# 8 default interface methods). A class can implement multiple interfaces. Since C# 8, interfaces can have default method implementations, blurring the line. Use abstract classes for "is-a" relationships with shared state. Use interfaces for "can-do" capabilities and when you need multiple inheritance of behavior.
7. What are nullable reference types and why were they introduced?
Introduced in C# 8 to combat NullReferenceException — Tony Hoare's "billion-dollar mistake." When enabled (<Nullable>enable</Nullable>), the compiler warns if you dereference a potentially null reference without checking. string means non-null, string? means nullable. This doesn't change runtime behavior (no actual null checks are added), but provides compile-time safety. Enterprise benefit: dramatically reduces null-related production bugs.
8. How does garbage collection work in .NET?
.NET uses a generational GC with three generations: Gen 0 (short-lived, collected frequently), Gen 1 (buffer between short and long-lived), Gen 2 (long-lived, collected rarely). Objects that survive a collection are promoted to the next generation. Large objects (>85KB) go directly to the Large Object Heap (LOH). The GC is concurrent and uses mark-sweep-compact. Background GC in .NET 6+ minimizes pause times. Avoid: frequent LOH allocations (fragments), finalizers (delay collection by one cycle), and static collections that grow unbounded.
9. What is pattern matching in C# and how has it evolved?
Pattern matching lets you test the shape and content of values. Evolution: C# 7 added is patterns and switch on type. C# 8 added switch expressions and property patterns. C# 9 added relational (>, <) and logical (and, or, not) patterns. C# 11 added list patterns ([1, 2, ..]). Real-world: replacing long if-else chains in payment processing, tax calculation, and validation logic with clear, exhaustive switch expressions.
10. What is the difference between Task.Run() and Task.Factory.StartNew()?
Task.Run() is a safe default: it queues work on the thread pool with sensible defaults. Task.Factory.StartNew() gives fine-grained control but has dangerous defaults (e.g., DenyChildAttach is not set, TaskScheduler.Current might not be the thread pool). Always use Task.Run() unless you need specific TaskCreationOptions. Never use either for I/O-bound work — use async/await instead.
11. What are extension methods and when should you use them?
Extension methods add functionality to existing types without modifying them. Defined as static methods in static classes with this on the first parameter. All of LINQ is extension methods on IEnumerable<T>. Good uses: utility methods for types you don't own (string formatting, enum display names), fluent APIs. Avoid: adding business logic as extensions (hard to mock), overusing them as a crutch for poor class design.
12. What is the difference between IEnumerable<T>, ICollection<T>, and IList<T>?
IEnumerable<T>: read-only forward iteration (foreach). ICollection<T>: adds Count, Add, Remove, Contains. IList<T>: adds index-based access (list[i]). Return the most restrictive type from your methods. If callers only iterate, return IEnumerable. If they need count, return ICollection. For DI contracts, prefer IReadOnlyList<T> to signal immutability.
13. What is covariance and contravariance in generics?
Covariance (out T): allows using a more derived type. IEnumerable<Dog> can be assigned to IEnumerable<Animal> because you're only reading (producing) values. Contravariance (in T): allows using a less derived type. Action<Animal> can be assigned to Action<Dog> because you're only writing (consuming) values. Remember: out = output/produce = covariant, in = input/consume = contravariant.
14. How do you handle exceptions in async code?
Exceptions in async Task methods are captured and placed on the returned Task. When you await that task, the exception is re-thrown. With Task.WhenAll(), only the first exception is thrown; access task.Exception.InnerExceptions for all. For async void, exceptions go to the SynchronizationContext and typically crash the process. Best practice: always await tasks, use try-catch around await, and log unobserved task exceptions via TaskScheduler.UnobservedTaskException.
15. What is record in C# and when should you use it?
A record is a reference type with value-based equality, immutability by default, and built-in ToString(), Equals, GetHashCode, and deconstruction. Use for: DTOs, API request/response models, domain events, CQRS commands/queries. Don't use for: entities with identity-based equality (two customers with the same name are different), mutable domain objects. record struct (C# 10) is the value-type variant for small, stack-allocated data.

ASP.NET Core (16-30)

16. How does the ASP.NET Core middleware pipeline work?
Middleware components are executed in order for the request and in reverse order for the response, forming a pipeline. Each middleware receives HttpContext and a RequestDelegate next. It can: (1) short-circuit (return without calling next), (2) modify the request before calling next, (3) modify the response after next returns. Order matters: Authentication must come before Authorization, Exception handling should be first (outermost), Static files should be early to skip unnecessary processing.
17. What are Minimal APIs and when would you use them?
Minimal APIs (introduced in .NET 6) let you define endpoints with lambdas instead of controller classes. Benefits: less boilerplate, faster startup, ideal for microservices with few endpoints. Drawbacks: no built-in model validation ([ApiController] auto-validation), no filters (use endpoint filters instead), can become messy for large APIs. Rule of thumb: Minimal APIs for microservices with <10 endpoints, controllers for larger APIs with complex routing, validation, and versioning.
18. What is the Options pattern in ASP.NET Core?
Strongly-typed configuration binding. Register with builder.Services.Configure<SmtpSettings>(config.GetSection("Smtp")), inject as IOptions<SmtpSettings> (singleton snapshot), IOptionsSnapshot<T> (scoped, reloads on change), or IOptionsMonitor<T> (singleton, notifies on change). Validate with .ValidateDataAnnotations().ValidateOnStart() to fail fast on bad config. Never inject IConfiguration directly into services.
19. How do you implement API versioning?
Use Asp.Versioning.Http package. Three strategies: (1) URL path: /api/v1/orders, (2) Query string: ?api-version=1.0, (3) Header: api-version: 1.0. Mark deprecated versions with [ApiVersion("1.0", Deprecated = true)]. Use [MapToApiVersion("2.0")] on specific actions. For Minimal APIs: group.MapGet(...).WithApiVersionSet(versionSet).MapToApiVersion(1.0).
20. Explain the difference between AddTransient, AddScoped, and AddSingleton.
Transient: new instance on every resolve. Use for lightweight, stateless services. Scoped: one instance per scope (HTTP request in web apps). Use for DbContext, unit of work, current-user services. Singleton: one instance for app lifetime. Use for HttpClient (via factory), caches, configuration. Critical rule: never inject Scoped into Singleton (captive dependency). ASP.NET Core validates this in Development by default.
21. How do you implement global exception handling in ASP.NET Core?
Three approaches: (1) app.UseExceptionHandler() middleware (recommended, handles all unhandled exceptions), (2) IExceptionHandler interface (.NET 8+, cleaner), (3) Exception filters (IExceptionFilter, only for MVC pipeline). Return RFC 7807 Problem Details format: Results.Problem() or ProblemDetails class. Always log the full exception server-side but return sanitized messages to the client (never leak stack traces in production).
22. What is output caching vs response caching?
Response caching: sets HTTP cache headers (Cache-Control, ETag). Caching happens in client browsers and CDN proxies. Output caching (.NET 7+): server-side cache of the full response. app.UseOutputCache() stores responses in memory (or Redis). More control: tag-based invalidation, vary by query/header. Use response caching for public static content, output caching for semi-dynamic content (product listings that change every few minutes).
23. How does model binding work in ASP.NET Core?
ASP.NET Core automatically maps HTTP request data to action parameters. Sources (checked in order): form values, route data, query strings. Attributes override: [FromBody] (JSON body), [FromRoute], [FromQuery], [FromHeader], [FromServices] (DI). [ApiController] attribute changes defaults: complex types from body, simple types from route/query. Custom binders implement IModelBinder for non-standard formats.
24. What is Health Checks and how do you implement them?
Health checks report app readiness for traffic. builder.Services.AddHealthChecks().AddSqlServer(connString).AddRedis(redisConn). Map endpoints: app.MapHealthChecks("/healthz"). Kubernetes uses these: liveness probe (is the app alive?) and readiness probe (can it accept traffic?). Custom health checks implement IHealthCheck. Use AspNetCore.HealthChecks.UI for a dashboard. Never expose detailed health info publicly.
25. How do you implement rate limiting in ASP.NET Core?
.NET 7+ has built-in rate limiting middleware. Four algorithms: Fixed Window, Sliding Window, Token Bucket, Concurrency limiter. Configure: builder.Services.AddRateLimiter(options => options.AddFixedWindowLimiter("api", o => { o.PermitLimit = 100; o.Window = TimeSpan.FromMinutes(1); })). Apply per-endpoint: .RequireRateLimiting("api"). Returns 503 with Retry-After header. For distributed rate limiting, use Redis-backed implementations.
26. What is the difference between IActionResult and ActionResult<T>?
IActionResult: can return any result type (Ok, NotFound, BadRequest) but Swagger can't infer the response type automatically. ActionResult<T>: typed result that supports implicit conversion from both T and ActionResult. Swagger automatically documents the 200 response type. Prefer ActionResult<T> with [ProducesResponseType] attributes for OpenAPI documentation.
27. How do you implement background tasks in ASP.NET Core?
IHostedService: low-level interface for long-running background work. BackgroundService: base class with ExecuteAsync (preferred). Use cases: queue processing, periodic cleanup, health monitoring. For DI, create a scope manually (IServiceScopeFactory) since hosted services are singletons. For complex job scheduling, use Hangfire or Quartz.NET. Never block the startup pipeline — return a running Task from ExecuteAsync.
28. What is SignalR and when would you use it?
SignalR is a library for real-time bidirectional communication. It abstracts WebSocket, Server-Sent Events, and Long Polling (auto-negotiates best transport). Use cases: live dashboards, chat, real-time notifications, collaborative editing, live order tracking. Hubs define server-callable methods. Clients can be grouped. For scale-out across multiple servers, use Redis backplane or Azure SignalR Service.
29. How do you configure CORS in ASP.NET Core?
builder.Services.AddCors(o => o.AddPolicy("Frontend", p => p.WithOrigins("https://app.example.com").AllowAnyMethod().AllowAnyHeader().AllowCredentials())). Apply globally with app.UseCors("Frontend") or per-endpoint with [EnableCors("Frontend")]. Common mistake: AllowAnyOrigin() with AllowCredentials() is rejected by browsers. For preflight caching, set SetPreflightMaxAge(TimeSpan.FromHours(1)).
30. What is the difference between filters and middleware?
Middleware: runs for every HTTP request, before/after the MVC pipeline. Access to HttpContext only. Filters: run within the MVC pipeline, have access to action context (controller, action, model state). Filter types: Authorization, Resource, Action, Exception, Result. Filters can be applied globally, per controller, or per action. Use middleware for cross-cutting concerns (logging, CORS). Use filters for MVC-specific concerns (validation, response caching, auditing).

Database & EF Core (31-40)

31. What is the N+1 query problem and how do you solve it in EF Core?
Loading N child entities for each of N parents results in N+1 database queries. Example: loading 100 orders and their customers fires 1 query for orders + 100 queries for each customer. Solutions: (1) .Include(o => o.Customer) eager loading (single JOIN query), (2) .AsSplitQuery() (separate queries, avoids cartesian explosion with multiple includes), (3) Projection with .Select() (loads only needed columns), (4) Explicit loading with Entry().Collection().LoadAsync(). Detect with EF Core logging or MiniProfiler.
32. Explain optimistic vs pessimistic concurrency in EF Core.
Optimistic: Add a [Timestamp] or byte[] RowVersion property. EF Core adds WHERE RowVersion = @original to UPDATE. If another transaction changed the row, DbUpdateConcurrencyException is thrown. Best for low-contention scenarios. Pessimistic: Use raw SQL SELECT ... FOR UPDATE or SET LOCK_TIMEOUT. Holds a DB lock until transaction commits. Best for high-contention (seat booking, inventory). EF Core doesn't have built-in pessimistic locking — use raw SQL or stored procedures.
33. What are EF Core migrations and how do you use them in production?
Migrations version-control your database schema. dotnet ef migrations add CreateOrdersTable generates C# code. dotnet ef database update applies it. In production: generate SQL scripts with dotnet ef migrations script --idempotent and run them in CI/CD or a Kubernetes init container. Never call Database.Migrate() in Program.cs in production — it causes startup delays and race conditions with multiple instances.
34. When should you use AsNoTracking()?
Use for all read-only queries (GET endpoints, reports, dashboards). Benefits: 30-50% faster, less memory, prevents accidental modifications. The change tracker creates identity map entries for every loaded entity; AsNoTracking() skips this entirely. Set globally: optionsBuilder.UseQueryTrackingBehavior(QueryTrackingBehavior.NoTracking). Only enable tracking when you intend to call SaveChangesAsync().
35. What is the Repository pattern debate in EF Core?
EF Core's DbContext is already a Unit of Work and DbSet<T> is a repository. Adding another layer is debated. Pro Repository: abstraction for testability, hides EF-specific details, encapsulates complex queries. Anti Repository: leaky abstraction (you can't abstract LINQ), adds boilerplate, DbContext is already testable with InMemory provider. Compromise: use thin repositories that expose IQueryable<T> for simple CRUD, and dedicated query services for complex queries.
36. How do you handle database transactions in EF Core?
SaveChangesAsync() is automatically wrapped in a transaction. For multiple SaveChanges calls or cross-context operations, use explicit transactions: await using var transaction = await db.Database.BeginTransactionAsync(); try { ... await db.SaveChangesAsync(); await transaction.CommitAsync(); } catch { await transaction.RollbackAsync(); throw; }. For distributed transactions across databases, use the Outbox pattern instead of TransactionScope.
37. What are compiled queries and when should you use them?
Compiled queries cache the LINQ-to-SQL translation. Normal queries re-translate expression trees on every call. private static readonly Func<AppDbContext, Guid, Task<Order?>> _getById = EF.CompileAsyncQuery((AppDbContext db, Guid id) => db.Orders.FirstOrDefault(o => o.Id == id)); Use for queries called thousands of times per second (hot paths). The translation overhead is ~0.5ms per call, so it only matters at very high throughput.
38. How do you handle soft deletes in EF Core?
Add bool IsDeleted property. Use Global Query Filters: modelBuilder.Entity<Order>().HasQueryFilter(o => !o.IsDeleted). All queries automatically exclude deleted records. To include deleted: .IgnoreQueryFilters(). Override SaveChanges to intercept Deleted entries and change them to Modified with IsDeleted = true. Consider: soft deletes make unique constraints harder (need composite index with IsDeleted).
39. What is the difference between Add, Attach, and Update in EF Core?
Add: marks entity as Added (INSERT). Attach: marks as Unchanged (starts tracking without changes). Update: marks as Modified (UPDATE all columns). Attach is useful when you have an entity from a disconnected scenario (e.g., deserialized from API) and want to change specific properties: db.Attach(entity); entity.Name = "new"; await db.SaveChangesAsync(); — only the Name column is updated.
40. How do you implement bulk operations in EF Core?
EF Core 7+ has built-in: await db.Orders.Where(o => o.Status == "Cancelled").ExecuteDeleteAsync() and ExecuteUpdateAsync(s => s.SetProperty(o => o.Status, "Archived")). These execute single SQL statements without loading entities. For bulk inserts, use EFCore.BulkExtensions NuGet: await db.BulkInsertAsync(orders). Without these, inserting 10K records fires 10K INSERT statements — bulk insert uses SQL bulk copy for orders-of-magnitude speed improvement.

Architecture & DevOps (41-50)

41. What is CQRS and when would you use it?
Command Query Responsibility Segregation: separate models for reads and writes. Commands (CreateOrder, TransferFunds) modify state through domain logic. Queries (GetOrderSummary, SearchProducts) read directly from optimized read models. Use when: read and write patterns differ drastically (e.g., complex writes + denormalized reads), high scalability needed, event sourcing. Overkill for simple CRUD apps. MediatR is the standard .NET implementation.
42. What is the Outbox pattern?
Solves reliable event publishing in distributed systems. Instead of updating DB then publishing to message bus (risk: app crashes between the two), write the event to an "outbox" table in the same DB transaction. A background process reads the outbox and publishes to Kafka/Service Bus. Guarantees at-least-once delivery. Libraries: MassTransit has built-in outbox support, or implement with BackgroundService polling.
43. How do you implement health checks in a microservices architecture?
Each service exposes /healthz (liveness: is the process running?) and /readyz (readiness: can it handle requests? checks DB, cache, dependencies). Kubernetes probes hit these endpoints. Implement with AddHealthChecks(). Check: database connectivity, Redis availability, disk space, downstream service availability. Don't check: things that would cause cascading failures (if service A goes unhealthy because B is down, traffic gets shifted but the problem was B).
44. Explain Docker multi-stage builds for .NET.
Stage 1 (SDK image, ~700MB): restore packages, build, publish. Stage 2 (runtime image, ~100MB): copy published output only. Result: production image is tiny, secure (no build tools), and contains only the runtime. Use mcr.microsoft.com/dotnet/sdk:8.0 for build, mcr.microsoft.com/dotnet/aspnet:8.0-alpine for runtime. Alpine-based images are even smaller (~50MB). Add USER app for non-root execution.
45. What is the difference between gRPC and REST?
REST: text-based (JSON), HTTP/1.1, human-readable, broad tooling. gRPC: binary (Protocol Buffers), HTTP/2, code-generated clients, streaming support. gRPC is 5-10x faster for service-to-service communication. Use REST for public APIs (browser-compatible). Use gRPC for internal microservice communication where performance matters. ASP.NET Core supports both simultaneously.
46. How do you manage configuration in .NET microservices?
Layers (highest priority wins): (1) Environment variables, (2) appsettings.{Environment}.json, (3) appsettings.json, (4) User secrets (dev only). For distributed config: Azure App Configuration or HashiCorp Consul. For secrets: Azure Key Vault with Managed Identity. Use the Options pattern (IOptions<T>) for strongly-typed configuration. IOptionsMonitor<T> for hot-reload without restart.
47. What is OpenTelemetry and how do you use it in .NET?
OpenTelemetry is a vendor-neutral observability standard providing three pillars: traces (request flow across services), metrics (counters, histograms), logs (structured events). .NET integration: builder.Services.AddOpenTelemetry().WithTracing(t => t.AddAspNetCoreInstrumentation().AddHttpClientInstrumentation().AddOtlpExporter()). Exports to Jaeger, Zipkin, Grafana Tempo, or Datadog. ASP.NET Core auto-instruments HTTP requests, EF Core queries, and HttpClient calls.
48. How do you implement CI/CD for .NET applications?
Pipeline stages: (1) Build + test: dotnet build, dotnet test with code coverage, (2) Static analysis: SonarQube or Roslyn analyzers, (3) Docker build: multi-stage image, (4) Push to registry: ACR, ECR, Docker Hub, (5) Deploy: Kubernetes rolling update or Azure App Service deployment slots. Blue-green deployment: deploy to inactive slot, run smoke tests, swap slots. Canary: gradually shift traffic percentage.
49. What is the Strangler Fig pattern?
Gradually migrate a monolith to microservices by routing new requests to new services while keeping existing functionality in the monolith. Place an API Gateway (YARP in .NET) in front. New feature? Build as microservice, route at gateway. Existing feature ready to migrate? Rewrite as microservice, redirect route, decommission monolith code. Continue until the monolith is empty. Much safer than big-bang rewrites.
50. How do you handle distributed transactions across microservices?
Traditional two-phase commit doesn't scale. Use the SAGA pattern: a sequence of local transactions with compensating actions. Two implementations: (1) Choreography: services publish events, others react (simple but hard to track). (2) Orchestration: a central coordinator manages the flow (clearer but single point of complexity). MassTransit provides saga state machines. Always design operations to be idempotent (safe to retry). Use the Outbox pattern for reliable event publishing.

20 Tricky C#/.NET Questions

▼
1. What is the output: string a = "hello"; string b = "hel" + "lo"; Console.WriteLine(a == b); Console.WriteLine(ReferenceEquals(a, b));
Both print True. The compiler evaluates "hel" + "lo" at compile time (constant folding) into "hello". String interning means both a and b reference the same string object in the intern pool. But if b were computed at runtime (e.g., string.Concat("hel", "lo")), ReferenceEquals would be False while == would still be True (because string overrides == for content comparison).
2. Why is async void dangerous?
Exceptions in async void methods can't be caught by the caller. They're posted to the SynchronizationContext and will crash the application with an unhandled exception. The caller has no Task to await, so it can't know when the work completes. This leads to race conditions in tests and fire-and-forget behavior in production. Only acceptable for UI event handlers where the delegate signature requires void.
3. What is a closure capture issue in loops?
var actions = new List<Action>();
for (int i = 0; i < 5; i++)
    actions.Add(() => Console.WriteLine(i));
actions.ForEach(a => a()); // Prints 5, 5, 5, 5, 5 (not 0,1,2,3,4!)
// The lambda captures the VARIABLE i, not its value.
// By the time lambdas execute, i is 5.
// Fix: var copy = i; actions.Add(() => Console.WriteLine(copy));
4. What happens when you call .Result or .Wait() on a Task in ASP.NET?
In ASP.NET Framework (not Core), this causes a deadlock. The async method captures the SynchronizationContext and tries to resume on the original thread, but .Wait() is blocking that thread. In ASP.NET Core, there's no SynchronizationContext, so it won't deadlock, but it still blocks a thread pool thread, reducing scalability. Always use await instead. If you must call async from sync (rare), use Task.Run(() => AsyncMethod()).GetAwaiter().GetResult().
5. What is the difference between throw and throw ex?
throw; re-throws the current exception preserving the original stack trace. throw ex; resets the stack trace to the current line, losing the information about where the error actually occurred. Always use throw; in catch blocks. If you need to wrap: throw new CustomException("message", ex); preserves the inner exception.
6. Can a struct have a default constructor in C#?
Since C# 10, yes. Before C# 10, structs always had an implicit parameterless constructor that zeroed all fields. With C# 10, you can define a custom default constructor, but be aware: new MyStruct[10] and default(MyStruct) still zero-initialize without calling your constructor. Only new MyStruct() calls it. This can lead to surprising bugs if your constructor sets non-zero defaults.
7. What is the volatile keyword in C#?
volatile prevents compiler and CPU reordering of reads/writes to a field. Without it, the JIT compiler may cache a field value in a register, so other threads never see updates. volatile ensures each read fetches from memory and each write goes to memory. However, it does NOT provide atomicity for compound operations (volatile int x; x++ is still not thread-safe). For atomic operations, use Interlocked class.
8. What is the difference between == and .Equals() for reference types?
== can be overloaded (and is for string and records). .Equals() can be overridden. For most reference types, == compares references by default. string overloads == for content comparison. Records generate both for value-based equality. Gotcha: if the compile-time type is object, == always does reference comparison even if the runtime type overloads it. .Equals() is virtual and dispatches correctly.
9. What happens if you modify a dictionary while iterating over it?
InvalidOperationException: Collection was modified. Even in single-threaded code. The enumerator checks a version counter on each MoveNext(). Solutions: iterate over a snapshot (dict.ToList()), collect keys to remove then remove after loop, or use ConcurrentDictionary which allows concurrent modification (but iteration may not see all changes).
10. What is the stackalloc keyword?
stackalloc allocates memory on the stack instead of the heap, avoiding GC pressure. Used with Span<T>: Span<byte> buffer = stackalloc byte[256];. The memory is automatically freed when the method returns. Danger: stack is limited (~1MB by default). Only use for small, known-size allocations in performance-critical code (parsing, serialization). Stack overflow if too large.
11. Can you catch and rethrow an exception in a different thread?
Yes, using ExceptionDispatchInfo.Capture(ex).Throw(). This preserves the original stack trace, unlike throw ex. This is exactly how await works internally — the exception from the async state machine is captured and re-thrown on the awaiting thread with the original stack trace intact.
12. Why should GetHashCode() be consistent with Equals()?
If two objects are equal (Equals() returns true), they must return the same hash code. If they don't, Dictionary and HashSet break: you can add an object but never find it because the lookup checks a different bucket. Records auto-generate consistent implementations. For classes: if you override Equals, always override GetHashCode. Use HashCode.Combine(field1, field2) for clean implementation.
13. What are the pitfalls of Task.WhenAll()?
WhenAll waits for all tasks even if one fails early. Only the first exception is thrown when awaited; others are in task.Exception.InnerExceptions. If a task is never awaited, its exception is silently swallowed (unless you subscribe to TaskScheduler.UnobservedTaskException). Performance: if task 1 of 5 fails immediately, you still wait for the other 4. Consider Task.WhenAll with CancellationToken to cancel remaining work on first failure.
14. What is the required modifier in C# 11?
required forces callers to set a property during initialization. public required string Name { get; init; }. Unlike constructor parameters, it works with object initializer syntax. The compiler enforces it at the call site. Useful for DTOs and configuration objects where you want required properties without constructor parameters. Works with [SetsRequiredMembers] attribute on constructors to opt out of the requirement.
15. What is the difference between Thread, Task, and ValueTask?
Thread: OS-level thread (expensive: ~1MB stack, kernel context switch). Task: work item on the thread pool (cheap, pooled threads, always heap-allocated). ValueTask: struct wrapper that avoids heap allocation when the result is already available (synchronous completion). Use Thread almost never (only for dedicated long-running work). Use Task for general async. Use ValueTask for hot paths with frequent synchronous completion (cache hits).
16. How does string interning work in .NET?
The CLR maintains an intern pool of unique string instances. All string literals are automatically interned. Runtime-created strings are not interned unless you call string.Intern(). string.IsInterned() checks without adding. Interning saves memory when the same string appears many times (e.g., country codes in a million-row dataset) but the interned strings are never garbage collected, so interning dynamic user input leaks memory.
17. What is the lock statement actually doing?
lock(obj) compiles to Monitor.Enter(obj) and Monitor.Exit(obj) in a try-finally. It's a mutual exclusion lock — only one thread can hold it. Lock on a dedicated private readonly object _lock = new(); Never lock on this (external code could also lock on your instance), typeof(T) (shared across AppDomains), or strings (interned, shared globally).
18. What is the CallerArgumentExpression attribute?
C# 10 feature that captures the text of an argument at compile time. Used in ArgumentNullException.ThrowIfNull(param) — it automatically includes the parameter name in the error message without nameof(). Also useful for custom guard clauses and assertion libraries: Guard.Against.Null(order.Customer) can say "order.Customer was null" without the caller passing the name.
19. What is the init accessor?
init (C# 9) makes a property settable only during object initialization (constructor or object initializer syntax). After construction, it's read-only. Enables immutable objects with object initializer syntax: var order = new Order { Id = 1, Total = 99.99m }; You can't later do order.Id = 2;. Internally, init uses a special modreq that the compiler enforces.
20. What happens when a finalizer throws an exception?
The exception is swallowed and the object is considered finalized. The runtime does not propagate finalizer exceptions — doing so would crash the finalizer thread and prevent other objects from being finalized. This is one reason why finalizers are discouraged: you can't reliably handle errors. Use IDisposable/IAsyncDisposable with using statements instead. If cleanup can fail, log the error in a try-catch inside Dispose.

20 ASP.NET Core Scenario-Based Questions

▼
1. Your API returns 500 errors under load but works fine with light traffic. How do you diagnose?
Likely causes: (1) Connection pool exhaustion — check DbContext disposal (are you using using/Scoped lifetime?), check HttpClient socket exhaustion (use IHttpClientFactory). (2) Thread pool starvation — check for .Result/.Wait() calls blocking async code. (3) Memory pressure — check for LOH allocations or missing Dispose. Diagnosis: Application Insights or Prometheus metrics for thread count, connection pool size, GC pauses. dotnet-counters monitor for live thread pool stats.
2. Your EF Core query takes 10 seconds. How do you optimize it?
(1) Enable EF Core query logging to see generated SQL, (2) Run EXPLAIN ANALYZE on the SQL in the database, (3) Check for N+1 (add .Include()), (4) Add .AsNoTracking() for read-only, (5) Use projection (.Select()) instead of loading full entities, (6) Add database indexes on WHERE/ORDER BY columns, (7) Consider .AsSplitQuery() if multiple Includes cause cartesian explosion, (8) For complex reports, use raw SQL or Dapper.
3. How do you implement multi-tenancy in ASP.NET Core?
Three strategies: (1) Separate databases: resolve connection string per tenant using middleware that reads tenant from JWT/subdomain/header, configure DbContext with tenant-specific connection. (2) Shared database, schema per tenant: set EF Core schema in OnModelCreating. (3) Shared schema, tenant column: add TenantId to all entities, use EF Core Global Query Filters to auto-filter. Inject ITenantAccessor (similar to IHttpContextAccessor) into DbContext.
4. How do you handle file uploads safely?
(1) Set size limits: options.MultipartBodyLengthLimit, (2) Stream to storage (S3/Blob) without buffering entire file in memory: use IFormFile.CopyToAsync(stream), (3) Validate file type by magic bytes (not extension), (4) Scan for viruses (ClamAV), (5) Store with random generated names (prevent path traversal), (6) Never serve user uploads from the same origin (use a separate CDN domain). For large files, use chunked uploads with resumability.
5. How do you implement distributed caching with Redis?
builder.Services.AddStackExchangeRedisCache(o => o.Configuration = "redis:6379"). Inject IDistributedCache. Use cache-aside pattern: check cache, miss → fetch from DB, store in cache with TTL. For complex objects, use IDistributedCache with JSON serialization. For high-throughput, use StackExchange.Redis directly with IConnectionMultiplexer. Cache invalidation: event-driven (publish invalidation events via Redis pub/sub or Kafka) or TTL-based.
6. Your deployed app has a memory leak. How do you find it?
(1) Enable heap dump on OOM or capture manually with dotnet-dump collect, (2) Analyze with dotnet-dump analyze or Visual Studio Diagnostics, (3) Look for growing object counts with dotnet-counters monitor, (4) Common causes: event handlers not unsubscribed, IDisposable not disposed, static collections growing, HttpClient instances not from factory, CancellationTokenSource not disposed, Timer instances not stopped. (5) Use dotnet-gcdump to see allocation patterns.
7. How do you implement API rate limiting per customer tier?
Use .NET 7+ built-in rate limiting with custom IRateLimiterPolicy: extract customer tier from JWT claims, apply different limits (Free: 100/hour, Pro: 1000/hour, Enterprise: unlimited). Store counters in Redis for distributed scenarios. Return 429 with Retry-After header and X-RateLimit-Remaining. Consider sliding window algorithm for fairness. Implement a fallback queue for burst traffic from premium customers instead of hard rejection.
8. How do you implement zero-downtime database migrations?
Expand-contract pattern: (1) Add new column (nullable), deploy. (2) Deploy code writing to both old and new columns, backfill. (3) Deploy code reading from new column. (4) Drop old column. Never rename or delete columns in one step. Generate idempotent migration scripts. Run migrations in a separate init container or CI/CD step, not in app startup. Test rollback scenarios. Use Flyway-style versioned migrations with checksums.
9. Your microservice calls 5 downstream services. One is slow. What happens?
Without resilience: thread pool exhaustion — all threads wait for the slow service, new requests queue up, cascading failure. Solution: (1) Timeouts on every HTTP call (5 seconds max), (2) Circuit breaker with Polly (stop calling after 50% failure rate), (3) Bulkhead isolation (limit concurrent calls to each downstream service), (4) Fallback responses (cached data or degraded response), (5) Parallel calls with Task.WhenAll() + per-task CancellationToken. This is why resilience patterns are critical in microservices.
10. How do you implement real-time notifications?
Three approaches: (1) SignalR: bidirectional, best for interactive features (chat, collaborative editing). Requires sticky sessions or Redis backplane for scale. (2) Server-Sent Events (SSE): unidirectional server-to-client, simpler, works with HTTP/2. (3) WebSocket: raw bidirectional, most control but most work. For a notification system: use SignalR with Azure SignalR Service for managed scaling. Group connections by user ID. Send from any service via IHubContext<NotificationHub>.
11. How do you handle long-running API requests?
Return 202 Accepted with a job ID and a location header for status polling: Location: /api/jobs/{jobId}. Process in background with BackgroundService or message queue. Client polls GET /api/jobs/{jobId} which returns progress (pending/processing/completed/failed). Alternative: use SignalR or SSE for push-based status updates. Store job status in Redis for fast reads. Set HTTP timeout higher on the client but always prefer async processing for anything over 5 seconds.
12. How do you implement feature flags in .NET?
Microsoft.FeatureManagement library: builder.Services.AddFeatureManagement(). Define in appsettings.json or Azure App Configuration. Check with IFeatureManager.IsEnabledAsync("NewCheckout"). Supports: percentage rollout, targeting (specific users/groups), time window activation. For dynamic updates without restart, use Azure App Configuration with sentinel key. In controllers: [FeatureGate("NewCheckout")]. Always clean up old flags to prevent tech debt.
13. How do you secure inter-service communication?
(1) mTLS: mutual TLS certificates between services (Kubernetes service mesh like Istio handles this automatically), (2) Internal JWT: API Gateway validates external JWT, issues internal tokens for downstream services, (3) API keys: simple but less secure, rotate regularly, (4) Network policies: Kubernetes network policies restrict which pods can talk to each other. Never rely solely on network isolation — defense in depth. Use Managed Identity in Azure to eliminate credentials.
14. How do you implement graceful shutdown in ASP.NET Core?
builder.WebHost.UseShutdownTimeout(TimeSpan.FromSeconds(30)). On SIGTERM: (1) Stop accepting new requests, (2) Complete in-flight requests (up to timeout), (3) Run IHostedService.StopAsync() for background services, (4) Dispose DI container. In Kubernetes: set terminationGracePeriodSeconds > shutdown timeout. Add preStop hook with sleep to allow load balancer to drain connections. Register IHostApplicationLifetime.ApplicationStopping for custom cleanup.
15. How do you handle database connection pool exhaustion?
Symptoms: random timeouts, "timeout expired" exceptions. Causes: long-running queries holding connections, missing using/Dispose on DbContext, blocking async code (.Result). Fix: (1) Ensure DbContext is Scoped (disposed per request), (2) Set Max Pool Size and Connection Lifetime in connection string, (3) Add query timeouts (CommandTimeout), (4) Monitor with dotnet-counters or Application Insights custom metrics. Default pool size is 100; rarely need more — fix the leak instead.
16. How do you implement audit logging?
Override SaveChangesAsync() in DbContext to intercept all entity changes. Log: who (from IHttpContextAccessor claims), what (entity type, changed properties), when (UTC timestamp), old values, new values. Store in a separate audit table or Elasticsearch. EF Core ChangeTracker.Entries() gives you entity state (Added/Modified/Deleted) and original/current values. Mask sensitive data (PII, card numbers). Make audit records immutable (append-only, no UPDATE/DELETE).
17. How do you implement CQRS with separate read/write databases?
Write side: normalized PostgreSQL with EF Core for commands. Read side: denormalized views in Elasticsearch, Redis, or a read replica. Sync via: (1) Domain events published to Kafka/Service Bus, consumed by read-side projections, (2) Change Data Capture (Debezium), (3) Database triggers (less recommended). Accept eventual consistency on the read side. Client handles: after a write, either read from the write DB briefly (read-your-own-writes) or show optimistic UI.
18. How do you handle bulk data imports (100K+ records)?
(1) Return 202 Accepted, process asynchronously, (2) Parse CSV/Excel with streaming (don't load entire file into memory), (3) Validate all records first, report errors, (4) Insert in batches: EFCore.BulkExtensions for EF Core or SqlBulkCopy for raw SQL, (5) Use Channels or a message queue for backpressure, (6) Provide progress endpoint with percentage complete, (7) Wrap in explicit transaction with savepoints for partial rollback.
19. How do you manage secrets in a .NET microservices environment?
(1) Development: User Secrets (dotnet user-secrets), (2) Production: Azure Key Vault with Managed Identity (no credentials in code), (3) Kubernetes: Secrets mounted as environment variables (encrypted at rest), External Secrets Operator for syncing from Key Vault, (4) CI/CD: GitHub Secrets or Azure DevOps variable groups. Never commit secrets to source control. Use .gitignore for appsettings.Development.json. Rotate secrets regularly with zero-downtime using IOptionsMonitor.
20. How do you implement a retry-with-exponential-backoff for external API calls?
Use Polly with IHttpClientFactory: exponential delay (500ms, 1s, 2s, 4s) with jitter to prevent thundering herd. Only retry on transient failures (5xx, network errors), never on 4xx (client errors). Add a circuit breaker that opens after 50% failures in a 30-second window, preventing requests to a service that's clearly down. Set an overall timeout as the outer policy. Log each retry attempt with the attempt number and delay. MassTransit provides retry policies for message consumers.

1. How would you design the migration strategy for moving a monolithic .NET Framework 4.8 application to .NET 8 microservices?

2. How do you identify and fix performance bottlenecks in a high-traffic .NET API?

(3) Common fixes: add AsNoTracking() to read queries, add database indexes (check EXPLAIN ANALYZE), add response caching or Redis cache for hot data, use Span<T> for string parsing, reduce allocations in hot paths. 5. How do you implement observability in a distributed .NET system?

(2) Outbox pattern for reliable event publishing (write event to outbox table in same DB transaction). (3) Idempotent consumers (deduplicate by message ID in Redis). (4) Read-your-own-writes: after a write command, query the write DB briefly instead of the read model. 10. How would you implement event sourcing in .NET?

Projections: Read models built by consuming events. When to use: Audit-heavy domains (finance, healthcare), complex domain logic, need to answer "what happened and when?" 19. How do you design idempotent APIs?
Why: Network retries, queue redeliveries, and client-side retries mean your API will receive duplicate requests. Implementation: (1) Client sends Idempotency-Key header (UUID). (2) Server checks Redis: if key exists, return cached response. (3) If not, process request, store result with the key (TTL 24h), return result. (4) Natural idempotency: GET is always idempotent, PUT (upsert) is idempotent by definition, DELETE should be idempotent (delete non-existent = 204). (5) POST with idempotency key makes create operations safe to retry. Essential for payment processing.
20. How do you approach breaking a monolithic database?
The hardest part of monolith-to-microservices. Steps: (1) Identify table ownership by bounded context. (2) Create views or APIs for cross-context reads. (3) Dual-write transition: new service writes to both old and new DB. Validate consistency. (4) Cutover reads: switch reads to new DB. (5) Stop writing to old DB. (6) Remove old tables. For shared tables: extract to a shared service or replicate via events. For joins across contexts: API composition or materialized views updated by events. Accept temporary data duplication as a migration cost.
21. How do you implement distributed locking?
Redis distributed lock (Redlock algorithm): SET key value NX PX 30000 (set if not exists, with 30s expiry). Libraries: RedLock.net. Use cases: preventing double-processing (payment dedup), leader election, rate limiting. Pitfalls: Always set TTL (prevent deadlock on crash). Use unique lock value (prevent accidental release by another process). Clock skew between Redis nodes can cause issues. Alternative: Database advisory locks for simpler cases.
22. How do you approach API design for a public developer platform?
(1) API-first design: write OpenAPI spec before code, review with stakeholders. (2) RESTful conventions: consistent naming, standard HTTP status codes, HATEOAS links. (3) Pagination: cursor-based for large datasets (keyset), offset for small. (4) Filtering/sorting: standardized query parameters. (5) Versioning: URL path, 2 versions active, clear deprecation timeline. (6) Rate limiting: per-API-key with tiered limits. (7) SDK generation: auto-generate from OpenAPI. (8) Developer portal: interactive docs (Swagger UI), quickstart guides, changelog. (9) Webhook support for event-driven integrations.
23. How do you implement a reliable messaging system?
At-least-once delivery with idempotent consumers. Implementation: (1) Outbox pattern: write event to DB in same transaction as business data. (2) Publisher reads outbox, publishes to Azure Service Bus/RabbitMQ, marks as published. (3) Consumer processes message idempotently (check processed message ID in Redis/DB). (4) Dead-letter queue for poison messages (max 5 retries with exponential backoff). (5) Monitoring: queue depth, processing latency, DLQ size with alerts. MassTransit provides all this out of the box with .UseMessageRetry() and .UseInMemoryOutbox().
24. How do you handle backward-compatible database migrations in production?
Expand-contract pattern: Phase 1 (Expand): add new column, nullable. Deploy migration. Phase 2 (Migrate): deploy code that writes to both old and new columns. Backfill old rows. Phase 3 (Contract): deploy code that reads from new column only. Phase 4 (Cleanup): drop old column in next release. Rules: Never rename columns. Never change column types without a new column. Always make new columns nullable initially. Generate idempotent scripts. Test rollback. Run migrations separate from application deployment (init container or CI step).

Framework: (1) Core competency test: does this differentiate our product? If no, buy. (2) Total cost of ownership: license + integration + maintenance + training vs. build + test + operate + on-call. (3) Time to market: buying is faster but may need customization. (4) Lock-in risk: assess vendor stability, data portability, contract terms. (5) Team capability: do we have expertise to build and maintain? (6) Evaluation process: POC with real requirements, not just demos. Examples: always buy auth (Auth0/Azure AD B2C), buy search (Elasticsearch), consider building domain-specific workflow engines, always buy monitoring (Datadog/Application Insights).

(4) Team factor: a technology the team knows well at 80% fit beats a perfect technology no one knows. (5) Document: ADR (Architecture Decision Record) capturing context, options considered, decision, and consequences. (6) Community: Stack Overflow activity, GitHub stars trend, conference talks — is this technology growing or dying?
3. How do you handle a major production incident?
During: (1) Declare incident commander (usually the lead). (2) Communicate to stakeholders: what's happening, ETA, customer impact. (3) Assign roles: investigation, communication, customer support liaison. (4) Fix forward or rollback — whichever is faster. (5) Status page updates every 30 minutes. After: (1) Blameless post-mortem within 48 hours. (2) Timeline of events. (3) Root cause analysis (5 Whys). (4) Action items with owners and deadlines. (5) Classify: detection time, mitigation time, customer impact. (6) Share learnings broadly. (7) Implement preventive measures. The goal is learning, not blame.
4. How do you drive adoption of new architectural patterns across a large team?
(1) Start with why: demonstrate the problem with current approach (metrics, pain points, developer survey). (2) Pilot project: implement in one non-critical service, document lessons learned. (3) Reference implementation: create a template/archetype project with best practices baked in. (4) Inner-source model: champions in each team who advocate and assist. (5) Documentation: ADRs, runbooks, video walkthroughs, lunch-and-learn sessions. (6) Gradual migration: new services use new pattern, retrofit existing services opportunistically. (7) Measure success: developer satisfaction, deployment frequency, incident rates.
5. How do you design an engineering org structure for a microservices platform?
Conway's Law: org structure mirrors system architecture. (1) Domain-aligned teams: each team owns 2-3 microservices in a bounded context (Payments team, Orders team, Customer team). (2) Platform team: provides shared infrastructure (CI/CD, observability, service mesh, developer experience). (3) Team Topologies: stream-aligned teams (feature delivery), platform teams (infrastructure), enabling teams (coaching), complicated subsystem teams (ML, security). (4) Two-pizza rule: 5-8 engineers per team. (5) API contracts between teams, not code dependencies. Teams deploy independently.
6. A key engineer wants to leave. How do you handle knowledge transfer?
Immediate: (1) Understand why — can you address the root cause? (2) Ask them to document the top 10 things only they know. (3) Pair programming sessions with remaining team members on critical systems. Long-term prevention: (1) Bus factor analysis: identify single points of knowledge, assign backup owners. (2) ADRs for all major decisions. (3) Runbooks for operational procedures. (4) Code ownership rotation. (5) Recorded design reviews. (6) Cross-training sprints. The goal: no single person should be irreplaceable for any system. The best time to fix bus factor is before someone leaves.
7. How do you evaluate and hire senior engineers?
Process: (1) Resume screen: look for impact, not just technologies. (2) Technical phone screen: problem-solving approach, communication. (3) System design round: open-ended problem, evaluate trade-off thinking and asking clarifying questions. (4) Code review round: give them real code to review, evaluate what they catch and how they communicate feedback. (5) Team fit: not culture fit (that leads to homogeneity), but values alignment. Evaluate: Do they ask questions or make assumptions? Can they explain complex concepts simply? Do they consider operational concerns? Can they say "I don't know"? Senior engineers should elevate the team, not just write good code.
8. How do you manage a platform that serves multiple product teams?
(1) Product mindset: treat internal platform as a product. Internal teams are your customers. (2) Self-service: templates, CLI tools, documentation that enables teams to work independently. (3) SLAs: define and publish platform reliability targets. (4) Intake process: prioritize requests by business impact, not who shouts loudest. (5) Inner-source: accept contributions from product teams with reviews. (6) Developer experience: golden path (paved road that's easiest to follow), measure developer satisfaction quarterly. (7) Avoid: becoming a bottleneck, building features product teams should own, mandating without enabling.
9. How do you make decisions with incomplete information?
Framework: (1) Reversibility: Is this a one-way or two-way door? Two-way doors: decide fast, iterate. One-way doors: invest more in analysis. (2) Time-box research: "We'll spend 2 days investigating, then decide with what we have." (3) Minimum viable decision: what's the smallest commitment that lets us learn? (4) Document assumptions: "We're choosing X because we assume Y. If Y turns out to be wrong, we'll switch to Z." (5) Disagree and commit: after discussion, the team aligns even if not everyone agrees. Revisit decision when new data arrives. Perfect information never arrives — 70% confidence is often enough to move.
10. How do you reduce deployment risk?
(1) Feature flags: deploy dark (code in production, feature disabled), enable gradually. (2) Canary deployments: 5% → 25% → 100% with automated rollback on error rate spike. (3) Blue-green: instant switch with instant rollback. (4) Automated testing: unit, integration, contract, E2E smoke tests in pipeline. (5) Preview environments: per-PR deployment for review. (6) Database migrations: backward-compatible, run separately from app deploy. (7) Observability: deployment markers on dashboards, automated alerts on error rate delta. (8) Deploy frequency: small, frequent deploys are safer than large, infrequent ones.
11. How do you define and track engineering metrics?
DORA metrics: (1) Deployment frequency (target: daily). (2) Lead time for changes (commit to production, target: <1 day). (3) Change failure rate (target: <15%). (4) Mean time to recovery (target: <1 hour). Additional: Sprint velocity trends, code review turnaround time, test coverage trends, developer satisfaction (quarterly survey), on-call burden distribution. Anti-patterns to avoid: Lines of code, number of commits, individual performance metrics. Metrics should drive team improvement, not individual evaluation. Share dashboards openly.
12. How do you manage technical strategy for a 3-year horizon?
(1) Tech radar: categorize technologies as Adopt, Trial, Assess, Hold. Review quarterly. (2) Architecture roadmap: aligned with product roadmap. What capabilities do we need in 12-18 months? (3) Investment areas: developer productivity, scalability, security, reliability. (4) Build alignment: regular architecture guild meetings across teams. (5) Manage risk: diversify technology bets, avoid single-vendor lock-in for critical components. (6) Communication: quarterly tech strategy presentations to engineering and product leadership. Keep it grounded in customer outcomes, not technology for its own sake.
13. How do you handle disagreements between team members on technical approach?
(1) Facilitate, don't dictate: ensure all perspectives are heard. (2) Data over opinions: run a time-boxed spike to gather evidence. (3) Decision criteria: agree on evaluation criteria before comparing options (performance, maintainability, team familiarity, time to implement). (4) Document the decision: ADR capturing all options, trade-offs, and the chosen path. (5) Disagree and commit: once decided, everyone aligns. Revisit if significant new information emerges. (6) Avoid HIPPO: "Highest Paid Person's Opinion" shouldn't automatically win.
14. How do you plan for disaster recovery and business continuity?
(1) RTO/RPO: define Recovery Time Objective (how fast to recover) and Recovery Point Objective (how much data loss is acceptable) per service. (2) Multi-region: active-passive (cheaper) or active-active (faster failover). (3) Backup strategy: automated daily backups, tested monthly, stored cross-region. (4) Runbooks: step-by-step recovery procedures for each failure scenario. (5) Chaos engineering: regularly inject failures (kill pods, simulate region failure). (6) Game days: quarterly DR drills. The plan you don't test is the plan that fails. (7) Communication plan: who contacts customers, what's the status page process.
15. How do you foster a culture of continuous improvement?
(1) Retrospectives: regular, action-oriented, follow up on previous actions. (2) Blameless post-mortems: every incident is a learning opportunity. (3) 20% time: dedicated time for exploration, learning, and innovation. (4) Tech talks: team members present what they've learned. (5) Book clubs: read and discuss engineering books together. (6) Conference budget: per-person annual budget for conferences and training. (7) Celebrate improvements: publicly recognize when someone improves a process, reduces tech debt, or mentors effectively. (8) Psychological safety: it's safe to ask "dumb" questions, propose wild ideas, and admit mistakes.
16. How do you handle legacy systems that "just work" but are unmaintainable?
(1) Risk assessment: bus factor (how many people understand it?), security vulnerabilities, scalability limits, cost of changes. (2) Business case: quantify the cost of status quo (developer hours spent working around issues, outage risk, opportunity cost). (3) Strangler fig: incrementally replace, not big-bang rewrite. (4) Add observability first: you can't migrate what you don't understand. (5) Characterization tests: wrap legacy system in tests that capture current behavior before changing anything. (6) Anti-corruption layer: new code talks to legacy via an adapter, not directly. (7) Timeline: realistic multi-quarter plan with intermediate milestones that deliver value.
17. How do you approach cost optimization for cloud infrastructure?
(1) Right-sizing: analyze actual CPU/memory utilization, downsize over-provisioned instances. (2) Reserved instances: commit to 1-3 year reservations for stable workloads (up to 72% savings). (3) Spot/preemptible: for batch processing, CI/CD runners, non-critical workloads. (4) Auto-scaling: scale down during off-hours and weekends for non-production environments. (5) Storage tiering: move old data to cold/archive storage. (6) FinOps practice: tag all resources by team/project, monthly cost review, set budget alerts. (7) Architecture: serverless for spiky workloads, reduce inter-region data transfer.
18. How do you manage on-call and incident response across the team?
(1) Fair rotation: weekly rotation, every engineer participates (including lead). (2) Runbooks: step-by-step guides for common alerts with decision trees. (3) Escalation policy: primary → secondary → lead → manager with auto-escalation timeouts. (4) Alert quality: every alert should be actionable. Review and tune monthly. Eliminate noisy alerts. (5) Compensation: on-call pay or compensatory time off. (6) Post-incident: blameless post-mortem, action items to prevent recurrence. (7) Burnout prevention: track per-person page volume, distribute evenly, adjust rotation if someone is disproportionately paged.
19. How do you onboard new engineers effectively?
(1) Pre-day-1: accounts, hardware, welcome email with reading list. (2) Week 1: architecture overview, dev environment setup (scripted/automated), pair with buddy on a small PR. (3) Week 2-3: own a small feature end-to-end with buddy support. (4) Month 1: first on-call shadow rotation, attend design review. (5) 30-60-90 plan: clear expectations and milestones. (6) Documentation: architecture diagrams, service catalog, ADRs, contribution guide. (7) Measure: time to first PR merged, time to first independent on-call. Target: productive in 2-3 weeks, fully autonomous in 2-3 months.
20. How do you drive engineering standards across multiple teams?
(1) Engineering guild: cross-team working group that proposes and reviews standards. (2) Template repositories: starter projects with best practices baked in (logging, health checks, CI/CD, testing). (3) Automated enforcement: linting, architecture tests (ArchUnitNET), dependency analysis in CI. (4) Golden path: make the right thing the easy thing. (5) RFCs: for significant changes, write a proposal, gather feedback, iterate. (6) Inner-source: shared libraries that teams contribute to. (7) Influence, not mandate: if a standard isn't worth automating enforcement for, it's probably not worth having.
21. How do you assess whether a team is healthy and performing well?
Signals: (1) Delivery: DORA metrics trending in the right direction. (2) Quality: declining incident rate, improving code review turnaround. (3) Morale: low attrition, high engagement survey scores, psychological safety (people challenge ideas openly). (4) Growth: team members are learning new skills, taking on new challenges, mentoring others. (5) Sustainability: reasonable work hours, on-call burden distributed evenly, tech debt is manageable. Red flags: hero culture (one person saving everything), blame culture, growing on-call burden, increasing deployment lead time.
22. How do you make the case for a major infrastructure investment to leadership?
(1) Quantify the problem: "We had 15 incidents in Q1 costing ~$200K in engineering time and lost revenue." (2) Propose the solution: clear scope, timeline, and cost. (3) Show ROI: "This investment reduces incident frequency by 80%, saving ~$160K/quarter." (4) Risk of inaction: "Without this, we'll hit scaling limits in Q3, blocking the product launch." (5) Phased approach: break into incremental milestones that deliver value along the way. (6) Comparable examples: what did similar companies do? (7) Align with business goals: reliability, customer satisfaction, developer productivity — whichever resonates most with leadership.
23. How do you manage a remote/distributed engineering team?
(1) Over-communicate: written communication by default, recorded meetings for async consumption. (2) Async-first: RFCs, PRs, Slack threads over synchronous meetings. (3) Overlap hours: establish 4-hour window where all time zones overlap for meetings and pairing. (4) Documentation: everything is written down (decisions, context, processes). (5) Social connection: virtual coffee chats, team offsites 2x/year, interest channels. (6) Trust: measure outcomes, not activity. (7) Tools: good video conferencing, collaborative whiteboarding (Miro), async standups (Slack/Notion).
24. How do you balance innovation with stability?
(1) Innovation sprints: quarterly hackathons or "innovation weeks" with demos. (2) Spike budget: 10% of sprint capacity for exploration and prototyping. (3) Boring technology club: Dan McKinley's principle — use proven tech for critical paths, save innovation budget for where it matters most. (4) Blast radius control: experiment in non-critical services or behind feature flags. (5) Pilot → scale: prove value in one service, then expand. (6) Kill criteria: define upfront what "failure" looks like for an experiment. Kill fast if it doesn't work. (7) Learning budget: each engineer gets time and budget for courses, conferences, and experimentation.
25. How do you prepare your team for a 10x scale increase?
(1) Load testing now: identify bottlenecks before they're urgent (k6, NBomber). (2) Database: read replicas, connection pooling, query optimization, consider sharding for writes. (3) Caching: multi-layer (CDN, Redis, in-memory) with proper invalidation. (4) Async processing: move non-critical work to message queues. (5) Auto-scaling: HPA in Kubernetes, right-size resource requests. (6) Observability: dashboards for saturation metrics, alerts at 70% capacity. (7) Architecture: identify single points of failure, add redundancy. (8) Team: hire ahead of the curve, build expertise in the bottleneck areas. (9) Game days: simulate 10x traffic and observe what breaks.

Round 1: SE Level — C# & ASP.NET Core (45 min)
Interviewer: Explain the difference between async/await and running code on a background thread with Task.Run().
Candidate: async/await is for I/O-bound work — when the method awaits a database call or HTTP request, the thread is released back to the thread pool while waiting for the I/O to complete. No thread is consumed during the wait. Task.Run() is for CPU-bound work — it queues a delegate to run on a thread pool thread, consuming a thread for the duration. In a web server, using Task.Run() for I/O just moves the blocking from one thread to another, which is worse because it adds thread pool overhead. Always use async/await with native async APIs for I/O (e.g., HttpClient.GetAsync(), DbContext.SaveChangesAsync()).
Interviewer: Write a method that processes a list of orders in parallel, calling an external payment API for each, with a maximum concurrency of 5 and a per-call timeout of 3 seconds.
Candidate: 
public async Task<List<PaymentResult>> ProcessPaymentsAsync(
    List<Order> orders, CancellationToken ct)
{
    var semaphore = new SemaphoreSlim(5);
    var tasks = orders.Select(async order =>
    {
        await semaphore.WaitAsync(ct);
        try
        {
            using var cts = CancellationTokenSource
                .CreateLinkedTokenSource(ct);
            cts.CancelAfter(TimeSpan.FromSeconds(3));
            return await _paymentGateway.ChargeAsync(order, cts.Token);
        }
        finally
        {
            semaphore.Release();
        }
    });
    return (await Task.WhenAll(tasks)).ToList();
}
I use SemaphoreSlim for concurrency control, linked CancellationTokenSource for per-call timeout that also respects the parent cancellation token, and Task.WhenAll to await all results.
Round 2: SSE Level — Architecture & Design (45 min)
Interviewer: Design a real-time order tracking system for a food delivery platform. Walk me through the architecture.
Candidate: I'd design this with five key services. Order Service manages the order lifecycle (created → accepted → preparing → picked up → delivered). Driver Service handles driver assignment and GPS location updates every 5 seconds. Tracking Service is the real-time component — it receives driver location events from Kafka, stores the latest position in Redis (key: driver:{id}:location, TTL 30s), and pushes updates to connected clients via SignalR groups (one group per active order). Notification Service sends push notifications at key state changes. API Gateway (YARP) handles routing and authentication. For the SignalR scaling challenge: I'd use Azure SignalR Service which manages the WebSocket connections and scales automatically. The Tracking Service publishes to Azure SignalR's Redis backplane, so any instance can push to any client's connection. For reliability: driver location updates go through Kafka (buffered), so if the Tracking Service is temporarily down, updates are replayed from the Kafka offset. The client app also has a polling fallback with 10-second interval if the WebSocket connection drops.

By now, the team should feel heard, the bleeding should be stopped, and there's a credible plan for improvement.
